# React State Management: Local State, Context, and External Stores

In early React development, global state management was frequently treated as an all-encompassing architectural layer. Development teams routinely configured monolithic client-side stores to hold every piece of dynamic data across an application: ephemeral modal toggles, draft form inputs, pagination offsets, user authentication tokens, and cached REST API responses.

Treating every piece of data as global state created brittle architectures. Applications suffered from widespread boilerplate, tight coupling between independent views, and difficult-to-diagnose rendering performance issues where small state updates triggered cascading re-renders across the component tree.

Modern React engineering abandons the monolithic store in favor of **categorization before tool selection**. React is not a framework that prescribes a single state container. Instead, it provides a set of primitives whose behavior depends directly on the lifetime, mutation frequency, and ownership of the data in question.

Choosing the right tool—whether `useState`, `useReducer`, React Context, an external store integrated via `useSyncExternalStore`, or a dedicated server cache—requires understanding the operational boundaries of each category.

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        REACT STATE TAXONOMY                            │
└────────────────────────────────────────────────────────────────────────┘
        │
        ├──► 1. LOCAL COMPONENT STATE
        │    ├─ Ephemeral UI interactions (modals, dropdowns, input drafts)
        │    └─ Primitives: useState, useReducer
        │
        ├──► 2. SHARED CLIENT UI STATE
        │    ├─ Cross-tree client preferences (theme, sidebar toggle, audio player)
        │    └─ Primitives: React Context (low frequency) / External Stores (high frequency)
        │
        ├──► 3. SERVER CACHE STATE
        │    ├─ Remote API data, asynchronous, cached snapshots of backend data
        │    └─ Primitives: React Server Components (RSC) / TanStack Query / SWR
        │
        └──► 4. URL / ROUTE STATE
             ├─ Shareable navigational view (pagination, search filters, active tabs)
             └─ Primitives: URL Search Params (useSearchParams, Router)
```

## 1. The 4-Category State Taxonomy

Before reaching for an external library, software architects classify application state into four distinct categories. Conflating these categories is the leading cause of accidental complexity in frontend systems.

### 1. Local / Component State
Local state belongs strictly to a single component or its immediate direct descendants. It is ephemeral and ceases to exist once the component unmounts from the DOM.
- **Typical Examples:** Modal open/closed booleans, dropdown open states, hover tooltips, and unsubmitted form input values.
- **Native Primitives:** `useState`, `useReducer`.
- **Core Rule:** Keep state colocated as close as possible to the UI element consuming it.

### 2. Shared Client UI State
Shared client UI state spans multiple disparate branches of the component tree but originates and lives entirely inside the client browser session. It does not reflect a database record and requires no asynchronous network synchronization.
- **Typical Examples:** Active color theme (`light`, `dark`, `system`), sidebar expansion state, notification toast queues, and modal stack managers.
- **Core Primitives:** React Context (for low-frequency updates paired with context splitting) or lightweight external subscription stores (such as Zustand) when selective subscriptions are necessary.

### 3. Server Cache State
Server cache state represents data that is fundamentally owned by a remote server or database and is temporarily mirrored in memory on the client. It is asynchronous, shared across multiple clients, and inherently subject to staleness.
- **Typical Examples:** User profile records, product catalogs, paginated feeds, and shopping cart line items fetched from a REST or GraphQL API.
- **The Architectural Anti-Pattern:** Manually managing server cache in client-side global stores (such as Redux or client-only stores) using manual `FETCH_INIT`, `FETCH_SUCCESS`, and `FETCH_ERROR` actions. This forces engineers to hand-craft cache invalidation, deduplication, retry logic, background refetching, and optimistic updates.
- **Modern Solutions:** React Server Components (RSC) paired with Server Actions in modern fullstack frameworks, or dedicated client-side cache managers like TanStack Query (React Query) and SWR. These tools treat server data as an asynchronous cache rather than static client state.

### 4. URL / Route State
URL state represents the active navigational context of the application. If a user expects to refresh the browser, copy the URL, or email a link to a colleague and see the exact same view, that state must live in the URL.
- **Typical Examples:** Search queries (`?q=react`), active pagination offsets (`?page=3`), faceted search filters (`?category=architecture&status=published`), and active tab identifiers (`?tab=security`).
- **Core Primitives:** `window.location`, router search parameters (`useSearchParams` in modern React frameworks).
- **Core Rule:** Never duplicate URL parameters into `useState` or external stores without strict synchronization, as this creates dual sources of truth and breaks browser history navigation.

## 2. Local Component State & The Colocation Invariant

The most effective state management strategy in React is often the simplest: **do not make state global unless it is strictly necessary**.

### The Colocation Invariant
The principle of state colocation establishes that state should always be placed as close to where it is used as possible. When state is lifted unnecessarily to an ancestor component, every update forces the ancestor and its entire subtree to evaluate their render functions, even if intermediate components do not consume the updated value.

When state must be shared between two sibling components, apply the **Lowest Common Ancestor (LCA)** rule: lift the state only to the immediate parent component that encompasses both consumers, and no higher.

```text
POOR ARCHITECTURE: Prematurely Lifted State
               ┌─────────────┐
               │ App (Root)  │ ◄── Holds searchQuery state (Forces entire app to re-render)
               └──────┬──────┘
       ┌──────────────┴──────────────┐
       ▼                             ▼
┌──────────────┐              ┌──────────────┐
│  Navigation  │              │  Dashboard   │
│  (No need)   │              │  (No need)   │
└──────────────┘              └──────┬───────┘
                                     ▼
                              ┌──────────────┐
                              │ SearchWidget │ ◄── Only consumer
                              └──────────────┘

COLOCATED ARCHITECTURE: State at Lowest Common Ancestor
               ┌─────────────┐
               │ App (Root)  │ ◄── Clean, no unnecessary state
               └──────┬──────┘
       ┌──────────────┴──────────────┐
       ▼                             ▼
┌──────────────┐              ┌──────────────┐
│  Navigation  │              │  Dashboard   │
└──────────────┘              └──────┬───────┘
                                     ▼
                              ┌──────────────┐
                              │ SearchWidget │ ◄── Owns and isolates searchQuery state
                              └──────────────┘
```

### Choosing Between `useState` and `useReducer`
Both `useState` and `useReducer` store state directly inside the React Fiber node associated with the component. The decision to use one over the other is an architectural decision based on state complexity:

- **Use `useState`** when dealing with independent primitives (strings, booleans, numbers) or simple objects where state updates are isolated and do not depend on complex validation rules.
- **Use `useReducer`** when:
  1. **Next state depends on multiple previous fields:** For example, managing a form state machine where transitioning from `idle` to `submitting` must atomically toggle `isSubmitting: true` while clearing `errorMessage: null`.
  2. **Decoupling intent from state transformation:** `useReducer` allows components to dispatch descriptive actions (`{ type: 'RESET_FORM' }`), keeping the state transition logic pure, deterministic, and easily testable outside of the React component tree.
  3. **Preserving stable callback references:** The `dispatch` function returned by `useReducer` is guaranteed by React to maintain reference identity across re-renders. Passing `dispatch` down to deeply nested children avoids breaking `React.memo` optimizations on child components.

### Implementation: State Colocation with Lowest Common Ancestor

The following TypeScript example demonstrates colocation. Sibling components `FilterInput` and `FilterBadge` share filter state at their lowest common ancestor `FilterToolbar`, ensuring that unrelated parts of the application remain unaffected by typing events:

```tsx
import React, { useState, ChangeEvent } from 'react';

interface FilterState {
  readonly query: string;
  readonly caseSensitive: boolean;
}

interface FilterInputProps {
  readonly query: string;
  readonly onQueryChange: (query: string) => void;
}

function FilterInput({ query, onQueryChange }: FilterInputProps) {
  const handleChange = (e: ChangeEvent<HTMLInputElement>) => {
    onQueryChange(e.target.value);
  };

  return (
    <input
      type="text"
      value={query}
      onChange={handleChange}
      placeholder="Filter records..."
      className="filter-input"
    />
  );
}

interface FilterBadgeProps {
  readonly activeCount: number;
}

function FilterBadge({ activeCount }: FilterBadgeProps) {
  if (activeCount === 0) return null;
  return <span className="filter-badge">{activeCount} active filter(s)</span>;
}

// Lowest Common Ancestor (LCA) managing shared local state
export function FilterToolbar() {
  const [filter, setFilter] = useState<FilterState>({
    query: '',
    caseSensitive: false,
  });

  const handleQueryChange = (newQuery: string) => {
    setFilter((prev) => ({ ...prev, query: newQuery }));
  };

  const activeCount = (filter.query ? 1 : 0) + (filter.caseSensitive ? 1 : 0);

  return (
    <div className="filter-toolbar">
      <FilterInput
        query={filter.query}
        onQueryChange={handleQueryChange}
      />
      <FilterBadge activeCount={activeCount} />
    </div>
  );
}
```

## 3. React Context: Dependency Injection vs. High-Frequency State

React Context is often misunderstood as a general-purpose state management engine. Architectural issues arise when teams treat Context as an event bus or reactive data store.

### The Architectural Purpose of Context
React Context is fundamentally a **Dependency Injection (DI)** mechanism. Its primary role is to broadcast ambient data down the component tree without manually threading props through intermediate layout components.

Ideal candidates for React Context include:
- Visual design tokens and themes (`dark` / `light` mode).
- Authenticated user session identity and permission scopes.
- Localization dictionaries and language preferences.
- Routing context and framework configuration.

### The Context Invariant & Re-render Cascades
Understanding how React handles Context updates is essential for preventing application-wide performance degradation:

1. **Reference Equality Check:** When a Context Provider renders, React compares its new `value` prop against its previous `value` using `Object.is` reference equality.
2. **Unconditional Consumer Invalidation:** If `Object.is(prevValue, nextValue)` evaluates to `false`, **every single component that calls `useContext(MyContext)` will re-render**.
3. **`React.memo` Ineffectiveness:** Wrapping a consumer component in `React.memo` *does not* prevent it from re-rendering when Context updates. `React.memo` only bails out on unchanged *props*. When a context value changes, React flags that fiber node directly, bypassing memoization boundaries.
4. **The Inline Object Trap:** Providing an inline object literal such as `<ThemeContext.Provider value={{ theme, toggleTheme }}>` creates a new object reference on every render of the Provider. This forces every consumer across the entire application to re-render, even if neither `theme` nor `toggleTheme` changed in value.

```text
MONOLITHIC CONTEXT: Single Value Change Triggers All Consumers
┌────────────────────────────────────────────────────────┐
│  CombinedContext.Provider ({ user, theme, cart })      │
└──────────────────────────┬─────────────────────────────┘
                           │
       ┌───────────────────┼───────────────────┐
       ▼                   ▼                   ▼
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ UserProfile  │    │ ThemeToggler │    │ ShoppingCart │
│ (Uses user)  │    │ (Uses theme) │    │ (Uses cart)  │
│ [RE-RENDERS] │    │ [RE-RENDERS] │    │ [RE-RENDERS] │
└──────────────┘    └──────────────┘    └──────────────┘
* Updating 'cart' causes UserProfile and ThemeToggler to re-render!

SPLIT CONTEXT ARCHITECTURE: Separating State and Dispatch
┌───────────────────────────┐    ┌───────────────────────────┐
│   ThemeStateContext       │    │   ThemeDispatchContext    │
└─────────────┬─────────────┘    └─────────────┬─────────────┘
              │                                │
              ▼                                ▼
       ┌──────────────┐                 ┌──────────────┐
       │ ThemePreview │                 │ ThemeToggler │
       │ (Consumes    │                 │ (Consumes    │
       │  State)      │                 │  Dispatch)   │
       │ [RE-RENDERS] │                 │ [NO RENDER]  │
       └──────────────┘                 └──────────────┘
```

### Mitigating Context Cascades: Context Splitting
To prevent unnecessary re-renders, production React applications apply **Context Splitting**:
- Split dynamic data into a **State Context** (which changes over time) and a **Dispatch Context** (which holds stable action functions).
- Components that only mutate state (such as a toggle button) consume the Dispatch Context. Because the dispatch reference is stable, action components never re-render when the state value changes.
- Components that render UI consume the State Context and update only when the data changes.

### Production Pattern: Split Context with Custom Hook Invariants

The following TypeScript implementation demonstrates Context Splitting with runtime invariant guards, ensuring that dispatchers do not trigger re-renders on consumers that only dispatch actions:

```tsx
import React, {
  createContext,
  useContext,
  useReducer,
  useMemo,
  ReactNode,
  Dispatch,
} from 'react';

// 1. Types & Discriminated Unions
type ThemeMode = 'light' | 'dark';

interface ThemeState {
  readonly mode: ThemeMode;
  readonly accentColor: string;
}

type ThemeAction =
  | { type: 'TOGGLE_MODE' }
  | { type: 'SET_ACCENT'; payload: string };

const initialThemeState: ThemeState = {
  mode: 'light',
  accentColor: '#0ea5e9',
};

function themeReducer(state: ThemeState, action: ThemeAction): ThemeState {
  switch (action.type) {
    case 'TOGGLE_MODE':
      return {
        ...state,
        mode: state.mode === 'light' ? 'dark' : 'light',
      };
    case 'SET_ACCENT':
      return {
        ...state,
        accentColor: action.payload,
      };
    default:
      return state;
  }
}

// 2. Separate Contexts for State and Dispatch
const ThemeStateContext = createContext<ThemeState | undefined>(undefined);
const ThemeDispatchContext = createContext<Dispatch<ThemeAction> | undefined>(
  undefined
);

// 3. Provider Component with Memoized State
interface ThemeProviderProps {
  readonly children: ReactNode;
}

export function ThemeProvider({ children }: ThemeProviderProps) {
  const [state, dispatch] = useReducer(themeReducer, initialThemeState);

  // Memoize state object to prevent reference churning if parent re-renders
  const memoizedState = useMemo(() => state, [state]);

  return (
    <ThemeStateContext.Provider value={memoizedState}>
      <ThemeDispatchContext.Provider value={dispatch}>
        {children}
      </ThemeDispatchContext.Provider>
    </ThemeStateContext.Provider>
  );
}

// 4. Custom Hooks with Invariant Guards
export function useThemeState(): ThemeState {
  const context = useContext(ThemeStateContext);
  if (context === undefined) {
    throw new Error('useThemeState must be used within a ThemeProvider');
  }
  return context;
}

export function useThemeDispatch(): Dispatch<ThemeAction> {
  const context = useContext(ThemeDispatchContext);
  if (context === undefined) {
    throw new Error('useThemeDispatch must be used within a ThemeProvider');
  }
  return context;
}

// 5. Isolated Consumer Components
export function ThemeToggleButton() {
  // Consumes only DispatchContext: will NOT re-render when ThemeState changes
  const dispatch = useThemeDispatch();

  return (
    <button
      type="button"
      onClick={() => dispatch({ type: 'TOGGLE_MODE' })}
      className="btn-toggle"
    >
      Toggle Theme
    </button>
  );
}

export function ThemeDisplay() {
  // Consumes StateContext: re-renders only when theme mode or accent changes
  const { mode, accentColor } = useThemeState();

  return (
    <div style={{ color: accentColor }}>
      Current Mode: <strong>{mode}</strong>
    </div>
  );
}
```

### Why Context Is Unsuitable for High-Frequency State
Context is ill-suited for streaming updates, such as mouse coordinate trackers, real-time audio playback meters, drag-and-drop animations, or high-throughput WebSocket feeds.

Because Context propagates changes through the component tree using React's standard reconciliation engine, updating Context at 60 frames per second forces the entire consuming subtree into reconciliation on every frame. This quickly exhausts the browser's main-thread budget (16.6ms per frame on standard 60Hz displays), causing noticeable user interface jank. High-frequency state demands an **external subscription store**.

## 4. External Stores & Concurrent Safety (`useSyncExternalStore`)

When client state updates rapidly or must be shared across many components with fine-grained selector subscriptions, moving state out of React's component tree into an **external store** is the standard architectural solution.

### The UI Tearing Hazard in Concurrent React 18+
In React 17 and earlier, the rendering phase was strictly synchronous: once React began rendering a tree of components, it ran to completion without yielding to the browser's event loop.

With the introduction of Concurrent React in React 18, rendering became **interruptible**. React can pause an ongoing render to handle high-priority browser events (such as user keystrokes) and resume rendering later across multiple microtasks.

If a component reads from a mutable external store using traditional `useEffect` and `useState` patterns, an architectural flaw known as **UI Tearing** can occur:

```text
SYNCHRONOUS RENDERING (React 17 & earlier)
[Render Starts] ──► Component A reads X1 ──► Component B reads X1 ──► [Commit DOM: Consistent]

CONCURRENT INTERRUPTIBLE RENDERING (React 18+ without useSyncExternalStore)
[Render Starts]
       │
       ▼
Component A reads X1
       │
       ├──► [RENDER YIELDS TO EVENT LOOP]
       │    External Event mutates store: X1 ──► X2
       │
       ▼
Component B reads X2
       │
       ▼
[Commit DOM: TORN UI] (Component A shows X1, Component B shows X2)
```

In a torn UI, two components in the same view display conflicting states simultaneously (for instance, a navigation bar displaying an account balance of $100 while the summary table displays $150) because the external store mutated while rendering was paused.

### How `useSyncExternalStore` Guarantees Consistency
To solve the tearing problem, React 18 introduced the `useSyncExternalStore` hook. This primitive is the official interface between React's concurrent scheduler and external mutable stores.

```typescript
function useSyncExternalStore<Snapshot>(
  subscribe: (onStoreChange: () => void) => () => void,
  getSnapshot: () => Snapshot,
  getServerSnapshot?: () => Snapshot
): Snapshot;
```

`useSyncExternalStore` provides two critical guarantees:
1. **Tearing-Free Synchronous Check:** When React processes components subscribed via `useSyncExternalStore`, it checks `getSnapshot()` synchronously. If React detects that the external store updated mid-render, it discards the incomplete concurrent render pass and restarts the render synchronously, ensuring that the entire committed UI observes a single, unified snapshot.
2. **Server-Side Rendering (SSR) Hydration Safety:** The optional `getServerSnapshot` argument provides the initial state during server-side rendering and client hydration. If the snapshot returned during client hydration differs from the server-rendered HTML, React flags a hydration mismatch, preventing hydration bugs.

### Fine-Grained Selectors and Algorithmic Complexity
Unlike React Context, which re-renders all consumers on any change, external stores implement **selector-based subscriptions**.

Subscribers register a callback in a listener set. Adding or removing a listener is an $O(1)$ operation on average when backed by a JavaScript `Set`. When an update occurs:
- The store iterates over its registered listeners in $O(S)$ time, where $S$ is the number of active subscribers.
- Each component evaluates its selector: `selector(currentState)`.
- If the selected slice is referentially identical (`Object.is(prevSlice, nextSlice)`), the component skips re-rendering entirely.

This isolates updates to the exact components that consume the modified slice, bypassing intermediate components completely.

### Implementation: Production-Ready External Store

The following self-contained TypeScript implementation demonstrates a typed external store with selector support built on `useSyncExternalStore`:

```tsx
import { useSyncExternalStore, useCallback } from 'react';

type Listener = () => void;

export interface Store<T> {
  getState: () => T;
  setState: (updater: Partial<T> | ((prevState: T) => Partial<T>)) => void;
  subscribe: (listener: Listener) => () => void;
}

/**
 * Creates a lightweight, concurrent-safe external store.
 */
export function createStore<T extends object>(initialState: T): Store<T> {
  let state: T = initialState;
  const listeners: Set<Listener> = new Set();

  const getState = (): T => state;

  const setState = (
    updater: Partial<T> | ((prevState: T) => Partial<T>)
  ): void => {
    const nextPartial =
      typeof updater === 'function' ? updater(state) : updater;
    const nextState = { ...state, ...nextPartial };

    // Prevent notifications if no fields changed
    let hasChanged = false;
    for (const key in nextPartial) {
      if (!Object.is(state[key], nextState[key])) {
        hasChanged = true;
        break;
      }
    }

    if (!hasChanged) return;

    state = nextState;
    // O(S) notification where S is active subscribers
    listeners.forEach((listener) => listener());
  };

  const subscribe = (listener: Listener): (() => void) => {
    listeners.add(listener);
    // O(1) unsubscription via Set deletion
    return () => {
      listeners.delete(listener);
    };
  };

  return { getState, setState, subscribe };
}

/**
 * Custom React hook subscribing to a specific slice of external state.
 */
export function useStore<T extends object, S>(
  store: Store<T>,
  selector: (state: T) => S
): S {
  // Stabilize snapshot retrieval for scalar values
  const getSnapshot = useCallback(() => {
    return selector(store.getState());
  }, [store, selector]);

  return useSyncExternalStore(
    store.subscribe,
    getSnapshot,
    getSnapshot // SSR snapshot fallback
  );
}

// ============================================================================
// Concrete Usage Example
// ============================================================================

interface AppState {
  readonly userCount: number;
  readonly activeProject: string;
}

export const applicationStore = createStore<AppState>({
  userCount: 0,
  activeProject: 'Alpha',
});

// Component A only subscribes to userCount
export function UserCounter() {
  const userCount = useStore(
    applicationStore,
    useCallback((s) => s.userCount, [])
  );

  return <div className="counter">Active Users: {userCount}</div>;
}

// Component B only subscribes to activeProject
export function ProjectTitle() {
  const activeProject = useStore(
    applicationStore,
    useCallback((s) => s.activeProject, [])
  );

  return <h2>Current Project: {activeProject}</h2>;
}

// Component C dispatches updates without subscribing to state
export function IncrementUsersButton() {
  const handleClick = () => {
    applicationStore.setState((prev) => ({
      userCount: prev.userCount + 1,
    }));
  };

  return (
    <button type="button" onClick={handleClick}>
      Increment Users
    </button>
  );
}
```

*Note on Selector Reference Stability:* When using selectors that return non-primitive references (e.g., arrays or derived objects), ensure the selector returns a memoized reference or use an equality comparison check. Returning a freshly created object reference on every `getSnapshot()` call will trigger an infinite re-render loop in `useSyncExternalStore`.

## 5. React Context vs. External Stores

Frontend architects frequently face the choice between React Context and external subscription stores (such as Zustand, Redux Toolkit, or Jotai).

The table below outlines their architectural trade-offs:

| Dimension | React Context | External Store (`useSyncExternalStore`) |
| :--- | :--- | :--- |
| **Primary Design Intent** | Dependency injection & ambient prop distribution | High-frequency, mutable, fine-grained state store |
| **Update Mechanism** | React fiber reconciliation pass | Direct store listener notification ($O(S)$) |
| **Subscription Granularity** | Subtree-level (all `useContext` consumers update) | Component-level (only slice-changed consumers update) |
| **Re-render Scope** | All consumers of the specific Context | Only components whose selector output changed |
| **Concurrent React Safety** | Native to React | Requires `useSyncExternalStore` to avoid UI tearing |
| **High-Frequency Suitability** | Poor (causes main-thread bottlenecks) | Excellent (bypasses intermediate fiber nodes) |
| **Bundle Footprint** | 0 KB (built into React core runtime) | 1 KB – 15 KB (depending on chosen library) |
| **Boilerplate & Ceremony** | Requires Providers, reducers, and context splitting | Minimal (often defined as a standalone module) |
| **DevTools & Inspection** | React DevTools component tree inspection | Redux DevTools, state logging, time-travel debugging |
| **Ideal Application** | Themes, Auth sessions, i18n, router params | Media players, drag-and-drop, large dashboards, forms |

## 6. Architectural Anti-Patterns & Common Failure Modes

When reviewing frontend architectures, senior engineers look for common patterns that introduce technical debt.

### Anti-Pattern 1: Server Cache Duplication in Client Global Stores
- **The Problem:** Fetching data from a REST API and manually inserting the response into a client store (e.g., Redux or Zustand). The store shape quickly mirrors the backend database schema, requiring dozens of reducers to handle loading spinners, error states, and pagination indices.
- **The Failure Mode:** Data becomes stale when another user mutates the record on the server. Navigating between views displays stale information or triggers duplicate network requests because the store lacks automated TTL (time-to-live) caching and background revalidation.
- **The Remedy:** Adopt React Server Components for server-rendered data, or TanStack Query / SWR for client-fetched data. Let the query library manage caching, deduplication, retry logic, and background synchronization.

### Anti-Pattern 2: The "Kitchen Sink" Monolithic Context
- **The Problem:** Creating a single `AppContext` containing `user`, `theme`, `cart`, `notifications`, `searchFilters`, and `audioState`.
- **The Failure Mode:** Whenever the audio player updates its playback timestamp (e.g., several times per second), the entire application re-renders—including navigation headers, user profiles, and product tables.
- **The Remedy:** Apply Context Splitting by domain. Separate state that updates frequently from state that is static. Keep layout state independent from domain data.

### Anti-Pattern 3: Ignoring URL State for Navigational Context
- **The Problem:** Storing search queries, active tabs, and pagination offsets in component `useState`.
- **The Failure Mode:** Users cannot share links to filtered tables, opening a link in a new tab resets all search criteria, and clicking the browser's "Back" button navigates away from the page rather than undoing the last filter change.
- **The Remedy:** Bind all shareable navigational parameters directly to the URL query string using `useSearchParams`.

### Anti-Pattern 4: Premature State Lifting
- **The Problem:** Moving state up to a top-level layout component under the assumption that "another component might need this data in the future."
- **The Failure Mode:** Root-level state creates wide re-render blast radiuses, increases prop drilling, and tightly couples components that should remain independent and modular.
- **The Remedy:** Maintain strict adherence to the Colocation Invariant. Keep state local until two components have a concrete, immediate requirement to share it.

## 7. A Practical Production State Architecture Checklist

Before approving a pull request or deploying a major frontend feature to production, verify the state architecture against this practical checklist:

- [ ] **State Classification Completed:** Is every dynamic data point explicitly categorized as Local State, Shared Client UI State, Server Cache, or URL State?
- [ ] **Colocation Respected:** Is state colocated to the Lowest Common Ancestor (LCA) rather than lifted prematurely to the root?
- [ ] **No Server Data in Client Stores:** Is server data managed via React Server Components (RSC) or a dedicated cache layer (TanStack Query / SWR) rather than a client-side global store?
- [ ] **Context Splitting Implemented:** Are high-frequency state updates separated from low-frequency actions? Does the Context separate `StateContext` from `DispatchContext`?
- [ ] **Context Values Memoized:** Are all Context Provider `value` props wrapped in `useMemo` to prevent reference churning on unrelated parent renders?
- [ ] **Runtime Invariant Guards Present:** Do custom context hooks (e.g., `useTheme()`) throw explicit developer errors when invoked outside their corresponding Provider?
- [ ] **External Stores Use `useSyncExternalStore`:** Are all mutable external subscriptions integrated via `useSyncExternalStore` to guarantee concurrent rendering safety?
- [ ] **SSR Snapshots Provided:** Does every `useSyncExternalStore` call supply a valid `getServerSnapshot` function to prevent hydration mismatch errors?
- [ ] **Selectors Return Stable Values:** Do store selectors return primitive values or memoized references to avoid infinite re-render loops?
- [ ] **URL Synchronized for Shareable Views:** Are all filter, tab, search, and pagination states synchronized with the URL query parameters?
- [ ] **Profiler-Verified Renders:** Has the component tree been profiled using the React DevTools Profiler to verify that typing or clicking does not trigger unnecessary renders in unrelated branches?

## Conclusion: Designing Predictable State Boundaries

State management in React is not a competition between libraries. It is an exercise in data categorization and boundary design.

A production-ready React architecture does not rely on a single global tool. Instead, it relies on strict boundaries:
- **Local Component State** (`useState`, `useReducer`) isolates ephemeral UI behavior to the exact elements that render it.
- **React Context** handles ambient dependency injection for low-frequency configuration when paired with Context Splitting.
- **External Stores** (`useSyncExternalStore`) provide fine-grained, tear-free reactivity for high-frequency client-side data.
- **Server Caches** (RSC, TanStack Query) decouple network synchronization from client state logic.
- **URL Parameters** turn application views into shareable, durable addresses.

By categorizing data before choosing tools, engineering teams build systems that remain performant, testable, and maintainable as the application scales.
