# Retrieval-Augmented Generation: How RAG Systems Work

Prototyping a Retrieval-Augmented Generation (RAG) system has become trivial: slice a collection of documents into arbitrary 500-token chunks, compute dense embeddings through an API, index them in a vector database, and query the top three results by cosine distance to inject into an LLM prompt.

In production, that naive architecture fails quickly.

Engineers moving beyond proof-of-concept demos encounter severe structural bottlenecks:
- **Retrieval Inaccuracy**: Dense vector similarity measures semantic proximity in an embedding space, not logical relevance or factual necessity. A document discussing network failure modes may score high cosine similarity against a query asking how to configure a successful TLS handshake, yet fail to provide the actual configuration flags.
- **Exact Identifier and Keyword Blind Spots**: Vector embeddings compress high-dimensional token relationships into continuous numerical manifolds. When users query specific error codes (`ERR_SSL_PROTOCOL_ERROR`), software version tags (`v2.4.18-rc1`), serial numbers, or function names (`Array.prototype.toSorted`), semantic vector search often fails to retrieve the exact match.
- **Context Distraction and "Lost in the Middle"**: Large language models do not process context tokens with uniform attention. Pushing 20 loosely relevant chunks into an extended context window degrades attention allocation, increases hallucination rates, and inflates API inference latency.
- **Hallucination and Verification Failures**: When an LLM receives ambiguous or incomplete context, its probabilistic generation mechanism often invents plausible-sounding justifications rather than admitting the answer is missing.

Production RAG is not a prompting trick; it is a distributed information retrieval system. It decouples **factual memory storage** from **language reasoning**. The database serves as the authoritative system of record, while the language model acts as a stateless reasoning engine constrained by retrieved evidence.

This guide explores the engineering mechanics required to build resilient RAG pipelines: dual-stage ingestion and inference architectures, hybrid retrieval combining dense vectors with sparse inverted indexes, Reciprocal Rank Fusion (RRF), cross-encoder neural reranking, context optimization, and quantitative evaluation using the RAG Triad.

## 1. Architectural Paradigms: Naive RAG vs. Advanced RAG vs. Fine-Tuning

When designing applications that require domain knowledge, engineering teams must decide between fine-tuning a model's parametric weights, implementing naive retrieval, or deploying an advanced multi-stage RAG architecture.

```text
+-------------------------------------------------------------------------------+
|                       KNOWLEDGE INTEGRATION PARADIGMS                         |
+-------------------------------------------------------------------------------+
| 1. Fine-Tuning: Modifies model internal weights (parametric memory).         |
|    Best for: Style, tone, syntax constraints, specialized task behaviors.    |
|    Limitation: High compute cost, knowledge cutoff, high hallucination risk.  |
+-------------------------------------------------------------------------------+
| 2. Naive RAG: Single-vector top-k retrieval directly into LLM prompt.         |
|    Best for: Quick demos, low-concurrency internal experimentation.          |
|    Limitation: Low precision, misses keywords, suffers from context dilution. |
+-------------------------------------------------------------------------------+
| 3. Advanced RAG: Hybrid retrieval + RRF + Cross-Encoder reranking + Grounding.|
|    Best for: Production enterprise search, compliance, technical docs.        |
|    Tradeoff: Multi-stage latency (+150-350ms), additional pipeline complexity.|
+-------------------------------------------------------------------------------+
```

The table below contrasts these three approaches across eight operational dimensions:

| Architectural Dimension | Naive RAG | Advanced Hybrid RAG | Model Fine-Tuning |
| :--- | :--- | :--- | :--- |
| **Primary Objective** | Basic context augmentation | High-precision grounded synthesis | Behavioral adaptation & style alignment |
| **Retrieval Topology** | Single vector cosine search (top-k) | Multi-stage: Hybrid (Dense + BM25) + Reranking | None (knowledge baked into weights) |
| **Exact Token / SKU Matching** | Poor (vector compression loses exact tokens) | High (sparse lexical index catches exact strings) | Variable (often hallucinates similar strings) |
| **Multi-Hop Query Handling** | Low (single-pass retrieval misses hops) | High (query decomposition & iterative retrieval) | Unpredictable (relies on parametric recall) |
| **Inference Latency Profile** | Fast vector lookup (~50–100ms) | Moderate multi-stage pipeline (~200–450ms) | Low external latency (model forward pass only) |
| **Data Freshness & Updates** | Immediate (database upsert) | Immediate (database upsert with metadata updates) | Expensive (requires dataset prep & training run) |
| **Evidence Attribution** | Low (no strict citation verification) | High (deterministic chunk-level citations `[^1]`) | None (black-box neural parameters) |
| **Operational Overhead** | Low (managed vector database) | Moderate (hybrid storage + reranker service) | High (GPU training clusters, versioning) |

### When to Fine-Tune vs. When to Retrieve

Fine-tuning changes **how the model speaks**; retrieval provides **what the model knows**. 

If a system needs to adopt a specific JSON schema, learn medical terminology syntax, or follow strict conversational protocols, fine-tuning or supervised instruction tuning is appropriate. However, using fine-tuning as an external knowledge base is brittle: training is computationally expensive, weights cannot be surgically updated when a single policy changes, and models cannot cite the exact paragraph from which a claim originated.

For dynamic, auditable, and security-governed enterprise data, retrieval architectures are necessary. For broader architectural patterns on integrating these systems into full-stack software, see [Building AI Features Into Existing Applications](/blog/building-ai-features-into-applications).

## 2. The Dual-Pipeline Architecture: Ingestion vs. Inference

A production RAG system operates as two decoupled pipelines running at different cadences: an asynchronous **Offline Ingestion Pipeline** (the write path) and a latency-critical **Online Inference Pipeline** (the read path).

```text
===================================================================================
                       OFFLINE INGESTION PIPELINE (WRITE PATH)
===================================================================================
Raw Documents        Extraction & Cleaning       Chunking Topology
[PDF / MD / HTML] -> [Strip Boilerplate]   ->    [Hierarchical: Child & Parent]
                                                        |
         +----------------------------------------------+
         |                                              |
         v                                              v
Dense Embedding Model                          Sparse Text Analyzer
[Bi-Encoder: text-embedding-3]                 [Stemming, Stopwords, tsvector]
         |                                              |
         v                                              v
Vector Index (HNSW Graph)                      Inverted Index (GIN / BM25)
[Continuous Semantic Space]                    [Exact Lexical Matching]

===================================================================================
                       ONLINE INFERENCE PIPELINE (READ PATH)
===================================================================================
User Query: "How do I resolve ERR_SSL_PROTOCOL_ERROR on v2.4?"
         |
         +-----------------------------+
         |                             |
         v                             v
Query Embedding Generation     Query Lexical Tokenization
[Bi-Encoder forward pass]      [Full-text query parser]
         |                             |
         v                             v
Dense ANN Search (HNSW)        Sparse Lexical Search (BM25)
[Top 50 Semantic Candidates]   [Top 50 Keyword Candidates]
         |                             |
         +--------------+--------------+
                        |
                        v
          Reciprocal Rank Fusion (RRF)
          [Normalizes & Merges Ranks: Top 50]
                        |
                        v
          Cross-Encoder Neural Reranking
          [Deep Token Attention Rescoring: Top 5]
                        |
                        v
          Context Layout Reordering
          ["Lost in the Middle" Strategic Sorting]
                        |
                        v
          Grounded Generation (LLM)
          [Strict Citation Prompting: [^1], [^2]]
                        |
                        v
          Final Verified Answer with Citations
```

### Decoupling the Ingestion and Inference Lifecycles

1. **The Ingestion Pipeline** processes raw, unstructured documents into structured retrieval artifacts. Because this runs asynchronously (via message queues or scheduled batch jobs), it can afford computationally heavy operations: OCR document extraction, metadata enrichment, parent-child chunk mapping, and dual indexing.
2. **The Inference Pipeline** operates synchronously within an HTTP request-response cycle. Every stage—query transformation, parallel dual search, fusion, reranking, and generation—must adhere to strict latency budgets. For detailed insights on API latency and network bottlenecks during generation, see [LLM APIs Explained: What Happens Between Prompt and Response](/blog/llm-api-architecture).

## 3. Offline Ingestion and Chunking Topologies

How documents are chunked determines the theoretical upper bound of retrieval quality. If a chunk is too small, it lacks surrounding context and becomes ambiguous. If a chunk is too large, it dilutes the specific facts needed to answer a focused query, crowding the LLM context window with irrelevant tokens.

### Comparison of Chunking Strategies

| Chunking Strategy | Boundary Mechanism | Strengths | Failure Modes / Tradeoffs |
| :--- | :--- | :--- | :--- |
| **Fixed-Size Sliding Window** | Fixed token count (e.g., 512 tokens) with overlap (e.g., 50 tokens) | Simple, deterministic, constant memory footprint | Splits sentences, breaks tables, severs semantic paragraphs |
| **Structural / Paragraph** | Splits on Markdown headers (`#`, `##`), double newlines, or HTML tags | Preserves natural human prose boundaries and formatting | Highly variable chunk sizes; oversized sections exceed model limits |
| **Semantic Distance** | Splits when cosine distance between consecutive sentences exceeds threshold | Groups conceptually unified thoughts together | High ingestion compute cost; sensitive to arbitrary distance thresholds |
| **Hierarchical (Parent-Child)** | Small child chunks (~128 tokens) indexed; parent sections (~1024 tokens) returned | High retrieval precision combined with rich generation context | Increased storage overhead; requires parent-child relational tracking |

### The Hierarchical (Small-to-Large) Retrieval Pattern

A frequent point of failure in naive RAG is the tension between **search granularity** and **generation context**:
- An embedding vector representing a compact 100-token chunk has high semantic density and accurately matches specific user questions.
- However, when that 100-token snippet is handed to an LLM, the model often lacks the wider background needed to formulate a complete answer.

Hierarchical chunking resolves this trade-off:
1. Ingest documents into large parent chunks (e.g., full sections of 1,024 tokens).
2. Decompose each parent into smaller child chunks (e.g., 128 to 256 tokens) with overlapping boundaries.
3. Compute embeddings **only for the child chunks** and store them with a reference pointer (`parent_id`).
4. At query time, the search engine matches against the compact child embeddings.
5. Once the top child chunks are retrieved, the pipeline replaces them with their parent chunks before constructing the prompt. The language model receives full, coherent context without sacrificing search precision.

### Vector Index Topology: HNSW vs. IVF

When storing embeddings, vector databases use Approximate Nearest Neighbor (ANN) indexes to avoid brute-force linear scans (which scale as `O(N · D)` where `N` is document count and `D` is vector dimensionality). The two dominant index families are:

- **Hierarchical Navigable Small World (HNSW)**: Constructs a multi-layer graph where upper layers feature long-range links for fast exploration, and lower layers contain dense, short-range connections for local routing.
  - *Key Parameters*:
    - `M`: Maximum number of bidirectional connections per node (typically 16 to 64). Higher values improve search recall at the expense of memory consumption and build time.
    - `efConstruction`: The size of the dynamic candidate list evaluated during index construction (typically 64 to 200).
    - `efSearch`: The candidate list size evaluated during runtime queries. Increasing `efSearch` improves recall at the cost of query latency.
  - *Tradeoff*: Exceptional query throughput and recall, but higher RAM consumption because the entire graph must remain in memory.
- **Inverted File Flat (IVFFlat)**: Partitions the high-dimensional space into Voronoi cells using k-means clustering (`nlist`). Queries search only vectors belonging to the centroids closest to the query vector (`nprobe`).
  - *Tradeoff*: Significantly lower memory footprint than HNSW and faster index build times, but lower recall on high-dimensional data and vulnerable to accuracy degradation if data distributions shift without re-clustering.

For a deeper analysis of distance metrics, inner product math, and ANN data structures, refer to [Vector Databases and Embeddings Explained](/blog/vector-databases-and-embeddings).

## 4. Hybrid Search and Reciprocal Rank Fusion (RRF)

Dense vector search alone is insufficient for production technical documentation, legal contracts, or customer support catalogs.

### The Semantic Blind Spot

Dense embedding models project tokens into continuous latent vectors trained on semantic similarity. They excel at recognizing that "automobile maintenance" is related to "car repair".

However, they degrade when processing:
- **Error Codes & Traces**: Searching for `0xC0000005` or `ERR_CONNECTION_TIMED_OUT`.
- **Product SKUs & Serial Numbers**: Queries like `X-500-G2` vs. `X-500-G3`.
- **Exact Method Signatures**: Looking for `fs.readFileSync` vs. `fs.readFile`.
- **Proper Nouns & Rare Acronyms**: Specialized medical, legal, or proprietary names.

In an embedding space, these distinct tokens are often split into subword fragments whose composite vector lands in a generalized, unhelpful neighborhood.

### Sparse Lexical Search (BM25)

Sparse search algorithms like BM25 (and relational full-text search engines like PostgreSQL's `tsvector`) do not rely on dense latent dimensions. They maintain an inverted index mapping individual lexical tokens to the documents containing them, scoring documents based on:
1. **Term Frequency (TF)**: How often the term appears in the document (dampened to prevent keyword stuffing).
2. **Inverse Document Frequency (IDF)**: Penalizing ubiquitous words (like "the" or "system") while boosting rare, distinctive terms (like `ERR_SSL_PROTOCOL_ERROR`).
3. **Document Length Normalization**: Preventing long documents from dominating results simply because they contain more total words.

| Dimension | Dense Vector Search | Sparse Lexical Search (BM25) | Hybrid Search (Dense + Sparse) |
| :--- | :--- | :--- | :--- |
| **Mechanism** | Latent semantic distance (HNSW/IVF) | Inverted index token statistics (BM25/GIN) | Parallel execution merged via Rank Fusion |
| **Primary Strength** | Synonyms, concepts, intent, cross-lingual | Exact keywords, codes, SKUs, rare entities | Both conceptual meaning and exact tokens |
| **Primary Weakness** | Exact tokens, rare acronyms, numbers | Synonyms, vocabulary mismatch, typos | Requires managing dual indexes & scoring |
| **Query Latency** | ~15–60ms | ~5–25ms | ~25–75ms (parallel execution) |
| **Storage Overhead** | High (large vector float arrays + graph) | Moderate (inverted token posting lists) | Combined footprint of both index structures |

### The Score Calibration Problem

Combining dense and sparse results by naively adding their raw scores fails:
- Dense cosine similarity outputs values strictly bounded between `[-1.0, 1.0]` (or `[0.0, 1.0]` for normalized vectors).
- BM25 outputs unbounded positive real numbers in the range `[0.0, ∞)` where the magnitude depends on query length, term rarity, and collection size.

Linear combinations like `Score = α · DenseScore + (1 - α) · SparseScore` require min-max normalization on every query. If an extreme outlier appears in BM25 scores, it compresses all other sparse scores, destabilizing the ranking.

### The Reciprocal Rank Fusion (RRF) Algorithm

Reciprocal Rank Fusion (Cormack, Clarke, and Büttcher, SIGIR 2009) solves this by ignoring raw scores entirely. It evaluates only the **ordinal rank position** of each document across the retrieval systems.

The RRF score of a document `d` across a set of retrieval methods `M` is defined as:

```text
RRF(d) = Σ [ 1 / (k + r_m(d)) ]  for each ranker m in M
```

Where:
- `M` is the set of rankers (for example, dense vector search and sparse full-text search).
- `r_m(d)` is the 1-based rank position of document `d` within the sorted results of ranker `m` (from 1 to N).
- `k` is a smoothing constant, conventionally set to `k = 60`.

#### Why `k = 60`?
The smoothing parameter `k` prevents top-ranked documents from completely dominating the aggregate score. Consider document ranks without smoothing (`k = 0`): rank 1 yields a score of `1.0`, while rank 2 yields `0.5`—a 50% drop. With `k = 60`:
- Rank 1 receives `1 / 61 ≈ 0.01639`.
- Rank 2 receives `1 / 62 ≈ 0.01613`.

This controlled decay ensures that a document appearing moderately high in **both** systems (e.g., rank 4 in dense, rank 3 in sparse) easily outranks a document that ranked 1 in dense but was completely absent from the sparse results.

## 5. Production Storage: PostgreSQL with `pgvector`

Rather than operating a dedicated vector database alongside a separate relational database and full-text search engine, modern production systems frequently unify these workloads inside PostgreSQL using the `pgvector` extension. This provides ACID transactions, relational joins, row-level security (RLS), and unified backups.

### Database Schema and Indexes

The following SQL schema sets up a document and chunk hierarchy supporting both HNSW vector indexing (`vector_cosine_ops`) and GIN full-text search:

```sql
-- Enable the pgvector extension
CREATE EXTENSION IF NOT EXISTS vector;

-- Parent documents table
CREATE TABLE IF NOT EXISTS documents (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    title TEXT NOT NULL,
    source_uri TEXT NOT NULL,
    metadata JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Document chunks table supporting hybrid dense + sparse retrieval
CREATE TABLE IF NOT EXISTS document_chunks (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    document_id UUID NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    chunk_index INT NOT NULL,
    content TEXT NOT NULL,
    metadata JSONB NOT NULL DEFAULT '{}'::jsonb,
    -- 1536-dimensional dense embedding (e.g., OpenAI text-embedding-3-small)
    embedding vector(1536) NOT NULL,
    -- Generated tsvector for sparse lexical full-text search
    tsv tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED
);

-- HNSW index for sub-linear cosine vector similarity search
-- m: max connections per node; ef_construction: candidate list size during index build
CREATE INDEX IF NOT EXISTS idx_chunks_hnsw_cosine 
ON document_chunks 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- GIN index for inverted lexical full-text keyword search
CREATE INDEX IF NOT EXISTS idx_chunks_tsv_gin 
ON document_chunks 
USING gin (tsv);

-- Composite index for rapid document-scoped chunk lookups
CREATE INDEX IF NOT EXISTS idx_chunks_doc_chunk_idx 
ON document_chunks (document_id, chunk_index);
```

### Native PostgreSQL Hybrid Search with Reciprocal Rank Fusion

The query below executes dense vector search and sparse full-text search in parallel Common Table Expressions (CTEs), joins their candidate sets, and computes RRF scores entirely within the database engine:

```sql
-- Native SQL Hybrid Search with Reciprocal Rank Fusion (RRF)
-- Parameters:
--   $1: Target query embedding vector (e.g., '[0.014, -0.021, ...]'::vector)
--   $2: Target lexical search query text (e.g., 'ERR_SSL_PROTOCOL_ERROR v2.4')
--   $3: RRF smoothing constant k (standard: 60)
--   $4: Candidate retrieval depth per index (e.g., 50)
--   $5: Final returned chunk limit (e.g., 10)

WITH dense_candidates AS (
    SELECT 
        id,
        content,
        document_id,
        chunk_index,
        metadata,
        ROW_NUMBER() OVER (ORDER BY embedding <=> $1::vector) AS dense_rank
    FROM document_chunks
    ORDER BY embedding <=> $1::vector
    LIMIT $4
),
sparse_candidates AS (
    SELECT 
        id,
        content,
        document_id,
        chunk_index,
        metadata,
        ROW_NUMBER() OVER (ORDER BY ts_rank_cd(tsv, plainto_tsquery('english', $2)) DESC) AS sparse_rank
    FROM document_chunks
    WHERE tsv @@ plainto_tsquery('english', $2)
    ORDER BY ts_rank_cd(tsv, plainto_tsquery('english', $2)) DESC
    LIMIT $4
)
SELECT 
    COALESCE(d.id, s.id) AS id,
    COALESCE(d.content, s.content) AS content,
    COALESCE(d.document_id, s.document_id) AS document_id,
    COALESCE(d.chunk_index, s.chunk_index) AS chunk_index,
    COALESCE(d.metadata, s.metadata) AS metadata,
    d.dense_rank,
    s.sparse_rank,
    (
        COALESCE(1.0 / ($3 + d.dense_rank), 0.0) +
        COALESCE(1.0 / ($3 + s.sparse_rank), 0.0)
    ) AS rrf_score
FROM dense_candidates d
FULL OUTER JOIN sparse_candidates s ON d.id = s.id
ORDER BY rrf_score DESC
LIMIT $5;
```

## 6. Two-Stage Reranking and "Lost in the Middle" Optimization

Even with hybrid search and RRF, the top candidates often contain false positives: documents that match individual keywords or share general topic vocabulary, but do not directly answer the specific question.

To reach high precision, production architectures implement **two-stage retrieval**:
1. **Stage 1 (Bi-Encoder / Hybrid Retrieval)**: Efficiently scans millions of documents and returns ~50 candidate chunks in under 50ms.
2. **Stage 2 (Cross-Encoder Reranking)**: Uses a deep neural reranker to compute full cross-attention between the query and the 50 candidate chunks, sorting them down to the top 3–5 most relevant passages.

### Bi-Encoders vs. Cross-Encoders

The difference between retrieval and reranking lies in their attention mechanisms:

```text
BI-ENCODER (Embedding Model - Fast, Independent)
Query:    [Query Tokens]    --> [ Transformer Encoder ] --> Vector u                                                                       --> Cosine Sim(u, v)
Document: [Document Tokens] --> [ Transformer Encoder ] --> Vector v /
* No token-level interaction between query and document during encoding.

CROSS-ENCODER (Reranker Model - Deep, Joint Attention)
Input: [CLS] Query Tokens [SEP] Document Tokens [SEP]
            |             |            |
            v             v            v
    [ Full Self-Attention Across Every Token Layer ]
                          |
                          v
               Relevance Score: [0.0 - 1.0]
* Every query token directly attends to every document token.
```

- **Bi-encoders** encode query and document into separate vectors independently. Vector operations (dot product, cosine similarity) run in microseconds, but the model cannot evaluate fine-grained token interactions.
- **Cross-encoders** concatenate the query and document into a single token sequence. The model computes full all-to-all attention (`O((N_q + N_d)²)` complexity) across all transformer layers. While too slow to run across an entire database, running a cross-encoder (such as `bge-reranker-large` or Cohere Rerank) across 50 candidates requires only ~80–150ms and significantly improves ranking accuracy.

### The "Lost in the Middle" Attention Phenomenon

Once the top 5 chunks are selected, how should they be ordered inside the LLM prompt?

Research into transformer attention distribution (Liu et al., 2023, *"Lost in the Middle: How Language Models Use Long Contexts"*) demonstrates that decoder-only models exhibit a U-shaped recall curve across their context windows:
- Information placed at the **extreme beginning** (primacy effect) is attended to with high fidelity.
- Information placed at the **extreme end** (recency effect) is also recalled accurately.
- Information placed in the **middle 40% to 70%** of the context suffers significant degradation in attention weights.

```text
RECALL FIDELITY ACROSS CONTEXT POSITION
High  | *                                                      *
      |  *                                                    *
      |   *                                                  *
      |    *                                                *
      |     *                  "DEAD ZONE"                 *
Low   |      * * * * * * * * * * * * * * * * * * * * * * *
      +---------------------------------------------------------
      Start of Context           Middle                  End of Context
```

If a system naively sorts chunks in descending order of relevance `[c1, c2, c3, c4, c5]`:
- Chunk `c1` sits at the top (good).
- Chunks `c2` and `c3` end up in the middle "dead zone" (poor).
- Chunk `c5` (the least relevant) sits at the bottom, receiving disproportionately high attention simply due to recency.

### Strategic Context Reordering

To maximize attention on critical evidence, sort the reranked chunks so that the most relevant material sits at the two outer boundaries:

Given top-ranked chunks `[c1, c2, c3, c4, c5]` where `c1` has the highest score:
1. Place `c1` at the beginning of the context.
2. Place `c2` at the very end of the context.
3. Alternate placing remaining chunks inward: `c3` near the top, `c4` near the bottom, and `c5` in the center.

**Optimal Prompt Context Order**: `[c1, c3, c5, c4, c2]`

This guarantees that the model's strongest attention regions process the most reliable evidence.

## 7. Production TypeScript Implementation: `HybridRAGPipeline`

The following TypeScript implementation demonstrates an end-to-end orchestration module: performing Reciprocal Rank Fusion, "Lost in the Middle" context layout reorganization, and assembling a grounded prompt with required citation tags:

```typescript
/**
 * Production-grade Hybrid RAG Pipeline Module
 * Implements Reciprocal Rank Fusion, "Lost in the Middle" Context Reordering,
 * and Grounded Prompt Assembly with Source Citations.
 */

export interface DocumentChunk {
  id: string;
  documentId: string;
  chunkIndex: number;
  content: string;
  metadata: Record<string, unknown>;
}

export interface FusedChunk {
  chunk: DocumentChunk;
  rrfScore: number;
  denseRank: number | null;
  sparseRank: number | null;
}

export interface AssembledPrompt {
  systemPrompt: string;
  userPrompt: string;
  citationMap: Map<number, DocumentChunk>;
}

export class HybridRAGPipeline {
  /**
   * Reciprocal Rank Fusion (RRF)
   * Merges two sorted candidate lists into a single ranked list based on ordinal position.
   *
   * @param denseResults  Array of chunks ordered by vector similarity (rank 1 = highest)
   * @param sparseResults Array of chunks ordered by lexical score (rank 1 = highest)
   * @param k             Smoothing constant (standard: 60)
   */
  public static reciprocalRankFusion(
    denseResults: DocumentChunk[],
    sparseResults: DocumentChunk[],
    k: number = 60
  ): FusedChunk[] {
    const fusionMap = new Map<string, FusedChunk>();

    // Process Dense Rankings
    denseResults.forEach((chunk, index) => {
      const rank = index + 1;
      const existing = fusionMap.get(chunk.id) ?? {
        chunk,
        rrfScore: 0,
        denseRank: rank,
        sparseRank: null,
      };
      existing.rrfScore += 1 / (k + rank);
      existing.denseRank = rank;
      fusionMap.set(chunk.id, existing);
    });

    // Process Sparse Rankings
    sparseResults.forEach((chunk, index) => {
      const rank = index + 1;
      const existing = fusionMap.get(chunk.id) ?? {
        chunk,
        rrfScore: 0,
        denseRank: null,
        sparseRank: rank,
      };
      existing.rrfScore += 1 / (k + rank);
      existing.sparseRank = rank;
      fusionMap.set(chunk.id, existing);
    });

    // Return sorted by descending RRF score
    return Array.from(fusionMap.values()).sort(
      (a, b) => b.rrfScore - a.rrfScore
    );
  }

  /**
   * "Lost in the Middle" Context Reordering
   * Reorganizes chunks into a U-shaped distribution:
   * Rank 1 -> Start, Rank 2 -> End, Rank 3 -> Second from Start, etc.
   *
   * @param items Sorted array of items in descending order of relevance
   */
  public static reorderLostInTheMiddle<T>(items: T[]): T[] {
    if (items.length <= 2) {
      return [...items];
    }

    const reordered: T[] = new Array(items.length);
    let left = 0;
    let right = items.length - 1;

    for (let i = 0; i < items.length; i++) {
      if (i % 2 === 0) {
        reordered[left] = items[i];
        left++;
      } else {
        reordered[right] = items[i];
        right--;
      }
    }

    return reordered;
  }

  /**
   * Assembles a strictly grounded prompt with numbered source citations.
   *
   * @param query           User search query or instruction
   * @param reorderedChunks Chunks pre-ordered for optimal attention distribution
   */
  public static assembleGroundedPrompt(
    query: string,
    reorderedChunks: DocumentChunk[]
  ): AssembledPrompt {
    const citationMap = new Map<number, DocumentChunk>();
    const contextBlocks: string[] = [];

    reorderedChunks.forEach((chunk, index) => {
      const citationId = index + 1;
      citationMap.set(citationId, chunk);
      contextBlocks.push(
        `[Source ^${citationId}] (Doc: ${chunk.documentId}, Part: ${chunk.chunkIndex})\n${chunk.content.trim()}`
      );
    });

    const systemPrompt = [
      "You are an authoritative, factual technical assistant operating in a strictly grounded retrieval system.",
      "Your objective is to answer the user's question using ONLY the facts present in the provided sources.",
      "",
      "STRICT OPERATIONAL CONSTRAINTS:",
      "1. Every factual statement or claim MUST be attributed to its supporting source using footnote syntax [^n].",
      "2. If the provided sources do not contain sufficient evidence to answer the question truthfully and completely,",
      "   you MUST reply: 'The available documentation does not contain sufficient information to answer this question.'",
      "3. Do NOT extrapolate, speculate, or incorporate external world knowledge not present in the sources.",
      "4. Cite multiple sources if a statement synthesizes information across them (e.g., [^1][^3]).",
    ].join("\n");

    const userPrompt = [
      "CONTEXT SOURCES:",
      "==================================================================",
      contextBlocks.join("\n\n------------------------------------------------------------------\n\n"),
      "==================================================================",
      "",
      `USER QUESTION: ${query.trim()}`,
      "",
      "GROUNDED RESPONSE WITH CITATIONS:",
    ].join("\n");

    return { systemPrompt, userPrompt, citationMap };
  }
}
```

## 8. The RAG Triad: Quantitative Evaluation Framework

You cannot improve what you do not measure. A common error in AI engineering is adjusting chunk sizes, embedding models, or prompt instructions based on anecdotal checks. A change that improves one query may silently cause regressions across twenty others.

The **RAG Triad** (popularized by frameworks such as RAGAS and TruLens) decomposes evaluation into three orthogonal metrics:

```text
                      +-------------------+
                      |    USER QUERY     |
                      +-------------------+
                        /               \
                       /                 \
    Context Relevance /                   \ Answer Relevance
    (Retrieval Step) /                     \ (Fulfillment)
                    v                       v
         +--------------------+   Faithfulness    +--------------------+
         | RETRIEVED CONTEXT  | --------------->  |  GENERATED ANSWER  |
         +--------------------+  (Groundedness)   +--------------------+
```

### 1. Context Relevance (Retrieval Quality)

Context Relevance evaluates whether the retrieved chunks are focused and necessary for the query, without extraneous noise.

```text
Context Relevance = (Relevant Sentences in Retrieved Chunks) / (Total Sentences in Retrieved Chunks)
```

- **Failure Mode**: High cosine similarity retrieves a 1,000-token chunk where only one sentence is relevant and the remaining 950 tokens describe unrelated systems. This dilutes the LLM context window and degrades inference efficiency.

### 2. Groundedness / Faithfulness (Generation Trustworthiness)

Faithfulness measures whether every claim in the generated output can be directly inferred from the retrieved context.

```text
Faithfulness = (Statements Attributable to Context) / (Total Statements in Output)
```

- **Measurement Procedure**: Decompose the generated response into discrete atomic propositions. For each proposition, verify if it is logically entailed by the retrieved chunks.
- **Failure Mode**: The model answers the question correctly according to general internet knowledge, but references information absent from the internal context, indicating hallucination and lack of grounding.

### 3. Answer Relevance (Query Fulfillment)

Answer Relevance assesses whether the response directly addresses the user's question, rather than evading or drifting off-topic.

```text
Answer Relevance = CosineSimilarity(Embedding(Generated Answer), Embedding(User Query))
```

- **Failure Mode**: The user asks "How do I increase connection pool size in v3?", and the model responds with a 300-word paragraph explaining what connection pools are without providing the configuration directive.

### Automated Evaluation in CI/CD

To prevent regressions:
1. **Curate a Golden Evaluation Set**: Maintain a version-controlled dataset of 100+ representative query-context-answer triplets.
2. **Implement LLM-as-a-Judge**: Use automated grading prompts with strict JSON schemas to evaluate Context Relevance, Faithfulness, and Answer Relevance against the golden dataset.
3. **Set Quality Gates**: Block pull requests if an embedding model update, chunking modification, or prompt rewrite lowers average Faithfulness or Context Relevance below target baselines.

For comprehensive strategies on designing automated evaluation loops and fallback behaviors, see [Designing Reliable AI Features: Validation, Fallbacks, and Monitoring](/blog/reliable-ai-feature-design).

## 9. Common Production Failure Modes and Mitigations

| Failure Mode | Root Cause | Engineering Mitigation |
| :--- | :--- | :--- |
| **Boundary Truncation** | Important definitions or code blocks cut in half by fixed-size chunking | Use hierarchical chunking (small child, large parent) and markdown AST boundary splitting |
| **Vocabulary Mismatch** | User query uses colloquial phrasing; documents use formal legal or technical jargon | Implement **HyDE** (Hypothetical Document Embeddings) or multi-query expansion before retrieval |
| **Context Poisoning / Injection** | Malicious user input embedded into external docs overrides system instructions | Strict XML/Markdown delimiting of context blocks; sanitize retrieved text; enforce footnote citation checks |
| **Stale Vector Drift** | Relational records updated or deleted, but vector embeddings remain orphaned | Implement the Transactional Outbox pattern: write document updates and queue embedding refresh in one transaction |
| **Silent Retrieval Collapse** | Query yields zero sparse matches and low-confidence dense scores | Define explicit fallback paths: reject query gracefully rather than generating ungrounded speculative answers |

## 10. Production Engineering Checklist

Before deploying a RAG pipeline to production, verify that:

- [ ] **Document Ingestion Hygiene**: Strips boilerplate, navigation menus, and footers; preserves Markdown tables and code block integrity.
- [ ] **Hierarchical Chunking**: Small child chunks (~128–256 tokens) used for vector matching; linked parent sections (~1024 tokens) passed to the LLM.
- [ ] **Hybrid Search Activated**: Both dense HNSW vector search and sparse full-text search (BM25 or GIN `tsvector`) execute in parallel.
- [ ] **Score-Agnostic Fusion**: Ranks combined using Reciprocal Rank Fusion (RRF) with `k = 60`; no naive addition of uncalibrated raw scores.
- [ ] **Two-Stage Reranking**: Cross-encoder neural reranker filters initial candidates (~50) down to top relevant chunks (~3–5).
- [ ] **Attention Optimization**: Chunks reordered using the "Lost in the Middle" U-shaped distribution to place top evidence at context boundaries.
- [ ] **Strict Grounding Prompts**: System prompt explicitly mandates footnote citations (`[^1]`) and enforces refusal when context is insufficient.
- [ ] **Continuous Observability**: Pipeline logs query latency, dense vs. sparse candidate counts, reranker scores, and token consumption to tracing backends. For telemetry instrumentation patterns, see [Backend Observability: Logs, Metrics, Traces, and Alerts](/blog/backend-observability).
- [ ] **Automated CI Regression Gate**: The RAG Triad (Context Relevance, Faithfulness, Answer Relevance) is evaluated automatically against a golden test suite before releases.

## Conclusion

Retrieval-Augmented Generation is often introduced as a simple bridge between a vector database and an LLM prompt. In real-world software, that naive pattern breaks down under the weight of exact token queries, context dilution, and unverified hallucinations.

Building a production-ready RAG system requires treating retrieval as a first-class data engineering discipline:
1. **Decouple the write path from the read path** through asynchronous ingestion and latency-bounded inference.
2. **Combine dense semantic search with sparse lexical indexing** using Reciprocal Rank Fusion to handle both conceptual queries and exact identifiers.
3. **Filter candidates with cross-encoder rerankers** and optimize context layout to mitigate attention degradation.
4. **Enforce deterministic citation attribution** and continuously monitor system health with the RAG Triad.

By replacing unstructured vector lookups with verifiable multi-stage information retrieval, engineering teams can build AI features that provide accurate, auditable, and reliable answers at scale.
