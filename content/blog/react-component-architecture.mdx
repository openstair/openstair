# React Component Architecture for Large Applications

In small applications, component architecture rarely feels like a critical constraint. A developer can build a dashboard with a handful of stateful components, pass callbacks through three layers of props, and ship features rapidly. However, as an engineering organization scales to dozens of contributors, hundreds of routes, and complex shared state, informal patterns break down under their own weight.

Without clear architectural boundaries, codebases inevitably experience:

- **The Boolean Prop Explosion**: Single UI components accumulating dozens of conditional flags (`hasHeader`, `isCompact`, `showBadge`, `withAction`), resulting in unmaintainable JSX branching and fragile CSS overrides.
- **Uncontrolled Re-render Cascades**: Root-level contexts and naive prop structures that force extensive subtrees to re-evaluate on every keystroke or ticker update.
- **Tight Data-Coupling**: Presentational leaf components directly importing global stores or API client hooks, making them impossible to preview in design systems, test in isolation, or reuse across feature boundaries.
- **Cascading Failure Blast Radii**: Unhandled exceptions in non-critical sub-widgets (such as a metrics card or user avatar) unmounting the entire application shell.

Building scalable React applications requires treating component architecture as an engineering discipline centered on contracts, inversion of control, state colocation, and reconciliation mechanics.

## The Breakdown of Legacy Component Taxonomies

To build modern React systems, engineers must understand why earlier architectural paradigms were superseded.

### The 2015 "Container vs. Presentational" Binary

During the early Redux and class-component era (circa 2015), the primary pattern for structuring React applications was the **Container vs. Presentational** (or "Smart vs. Dumb") division. 

In this pattern:
- **Presentational components** were pure functions receiving data and event handlers strictly through `props`, returning JSX without dependencies on application stores.
- **Container components** wrapped presentational components to handle data subscriptions (via Redux `connect()` or lifecycle hooks like `componentDidMount`), managing state and passing down slices as props.

While this pattern brought order to class-based applications, it introduced friction as React evolved:
1. **Unnecessary Component Indirection**: Applications accumulated hundreds of thin wrapper components whose only task was invoking a store selector and forwarding ten props down to an inner component.
2. **Prop Drilling Across Intermediate Layers**: Refactoring a deep presentational child required updating the interface and prop-passing logic of every container and layout component in the chain.
3. **The Introduction of Custom Hooks**: With React 16.8, custom hooks allowed stateful logic, side effects, and store subscriptions to be encapsulated and reused directly within components without adding extra DOM nodes or wrapper layers.
4. **React Server Components (RSC)**: Modern React architectures decouple data retrieval by handling data fetching natively on the server, reserving client-side components primarily for interactivity and browser APIs.

Dan Abramov—who originally popularized the Container/Presentational distinction—formally revised his recommendation, noting that hooks allow developers to separate concerns without arbitrary component wrapping.

### The Modern 4-Tier Component Hierarchy

Instead of a rigid binary split, resilient frontends organize components into four distinct architectural tiers based on their stability, domain knowledge, and dependency requirements:

```text
┌─────────────────────────────────────────────────────────────┐
│ Tier 4: Page & Layout Shells (Route Boundaries & Hydration)  │
│ e.g., app/(dashboard)/billing/page.tsx, layout.tsx          │
└──────────────────────────────┬──────────────────────────────┘
                               │ passes route params & RSC streams
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ Tier 3: Composite Containers & Views (State Orchestration)  │
│ e.g., BillingOverviewPanel.tsx, InvoicesTableContainer.tsx  │
│ (Custom Hooks, Zustand/Query, Granular Error Boundaries)    │
└──────────────┬──────────────────────────────┬───────────────┘
               │ domain objects               │ raw layout props
               ▼                              ▼
┌──────────────────────────────┐ ┌────────────────────────────┐
│ Tier 2: Domain Primitives    │ │ Tier 1: Design System &    │
│ e.g., InvoiceStatusBadge.tsx │ │ Headless Primitives        │
│ UserAvatar.tsx, PriceTag.tsx │ │ e.g., Button, Modal, Tabs, │
│ (Pure typed UI, no network)  │ │ Accordion, VisuallyHidden  │
└──────────────┬───────────────┘ └────────────┬───────────────┘
               │                              │
               └───────────────┬──────────────┘
                               ▼
                        [ Browser DOM ]
```

#### Tier 1: Design System Tokens & Headless Primitives
- **Examples**: `Button`, `Input`, `DialogPrimitive`, `Tooltip`, `VisuallyHidden`.
- **Characteristics**: Completely decoupled from business models and API contracts. Focused on accessibility standards (WAI-ARIA specifications, keyboard focus traps), DOM event handling, and design token integration.
- **Implementation**: Styled through composition or headless primitives (such as Radix UI or React Aria). They contain zero domain knowledge.

#### Tier 2: Domain / Feature Primitives
- **Examples**: `UserAvatar`, `CurrencyDisplay`, `InvoiceStatusBadge`, `PlanQuotaBar`.
- **Characteristics**: Strongly typed against domain interfaces (such as a TypeScript `Invoice` or `UserProfile` model), but strictly presentational. They do not fetch data, manage network lifecycles, or connect to global stores.
- **Testing**: Highly suitable for visual regression testing and isolated Storybook environments because all variations can be driven directly via static props.

#### Tier 3: Composite Containers & Feature Views
- **Examples**: `BillingOverviewPanel`, `UserSecuritySettings`, `CheckoutCartView`.
- **Characteristics**: The operational orchestration layer. These components invoke custom hooks (such as TanStack Query or SWR hooks for data fetching, or Zustand slices for client state), coordinate mutations, manage local validation state, and compose Tier 1 and Tier 2 components into cohesive feature widgets.
- **Resilience**: Act as boundaries for `<Suspense>` fallbacks and granular `<ErrorBoundary>` wrappers.

#### Tier 4: Page & Layout Shells
- **Examples**: `app/(dashboard)/billing/page.tsx`, `layout.tsx`.
- **Characteristics**: Route entry points mapped directly to URLs. They parse URL parameters and search queries, generate SEO and metadata tags, coordinate route-level data loading or Server Component streams, and establish layout persistence across client-side transitions.

### Architectural Taxonomies Comparison

| Tier | Primary Responsibility | Data Source | Domain Knowledge | Reusability Scope | Typical Directory |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Tier 1: Design Primitives** | Accessibility, base interactions, tokens | Props only | None | Universal (Entire Org) | `components/ui/` |
| **Tier 2: Domain Primitives** | Consistent domain entity rendering | Domain props | Read-only Schema | Broad (Across Features) | `components/domain/` or `features/*/components/` |
| **Tier 3: Composite Views** | State orchestration, mutations, queries | Hooks, Stores, APIs | High (Feature Logic) | Limited (Feature Specific) | `features/*/views/` |
| **Tier 4: Page Shells** | Routing, metadata, layout persistence | Route params, RSC | Route Context | Page Specific | `app/` or `pages/` |

## Composition Patterns vs. Prop Explosion

As components absorb new feature requests, naive architectures tend to add configuration flags to existing components. This pattern is commonly known as **Boolean Prop Explosion**.

```text
Anti-Pattern: Boolean Prop Explosion (Combinatorial Branching)
┌─────────────────────────────────────────────────────────────────┐
│ <Card                                                           │
│   title="Monthly Metrics"                                       │
│   hasHeader={true}                                              │
│   isCompact={false}                                             │
│   showBadge={true}                                              │
│   badgeStatus="active"                                          │
│   withActions={true}                                            │
│   actionVariant="icon"                                          │
│   hasFooter={true}                                              │
│ />                                                              │
└─────────────────────────────────────────────────────────────────┘
  ↳ Problem: 2^n branches inside <Card />; fragile layout and styling conflicts.

Recommended: Inversion of Control & Slot Composition
┌─────────────────────────────────────────────────────────────────┐
│ <Card>                                                          │
│   <Card.Header>                                                 │
│     <Heading level={3}>Monthly Metrics</Heading>                │
│     <Badge variant="active">Live</Badge>                        │
│     <IconButton icon="download" aria-label="Export metrics" />  │
│   </Card.Header>                                                │
│   <Card.Body>                                                   │
│     <MetricChart data={chartData} />                            │
│   </Card.Body>                                                  │
│ </Card>                                                         │
└─────────────────────────────────────────────────────────────────┘
  ↳ Benefit: Parent controls layout; consumer controls structure and markup.
```

### The Cost of Boolean Prop Explosion
Consider a `<Card />` component designed initially for a simple summary. Over twelve months, different teams append `isCompact`, `withBadge`, `showActionMenu`, `hasFooterBorder`, and `alignRight`.

This design degrades along three axes:
1. **Exponential Complexity**: With $n$ boolean flags, there are theoretically $2^n$ distinct visual and behavioral permutations. Engineers cannot reliably predict how `isCompact={true}` interacts with `withActionMenu={true}` and `hasHeader={false}`.
2. **Leaky Styling Abstractions**: The inner implementation becomes cluttered with nested ternary operators and conditional CSS classes, making updates risky.
3. **Tight Coupling**: When a team needs a custom action icon inside the header, they must modify the core `<Card />` implementation rather than assembling it at the call site.

### Inversion of Control (IoC) and Named Slots
Instead of passing data flags that instruct a component *how* to assemble its interior, architecture should favor **Inversion of Control (IoC)**: the parent component manages structural containment, spacing, and layout boundaries, while delegating the content rendering back to the consumer.

React provides this out of the box through `children` and named slots:

```tsx
interface PanelLayoutProps {
  headerSlot: React.ReactNode;
  actionSlot?: React.ReactNode;
  children: React.ReactNode;
  footerSlot?: React.ReactNode;
}

export function PanelLayout({
  headerSlot,
  actionSlot,
  children,
  footerSlot,
}: PanelLayoutProps) {
  return (
    <section className="rounded-lg border border-slate-200 bg-white shadow-sm">
      <header className="flex items-center justify-between border-b border-slate-100 px-6 py-4">
        <div className="flex-1">{headerSlot}</div>
        {actionSlot && <div className="ml-4 shrink-0">{actionSlot}</div>}
      </header>
      <div className="p-6">{children}</div>
      {footerSlot && (
        <footer className="border-t border-slate-100 bg-slate-50 px-6 py-3">
          {footerSlot}
        </footer>
      )}
    </section>
  );
}
```

By turning layout slots into `React.ReactNode` props, consumers can render plain text, buttons, dropdowns, or complex forms without altering `PanelLayout`.

### The Compound Components Pattern
When a set of components must collaborate to form a cohesive, accessible widget—sharing implicit state without forcing the consumer to manually wire up event handlers and unique IDs—the **Compound Components Pattern** is the industry standard.

Compound components offer three distinct advantages:
1. **Declarative Flexibility**: Consumers control DOM structure and ordering. For instance, putting an icon before or after an accordion header label requires no prop configuration.
2. **Encapsulated State**: The root component coordinates open/closed states, active indexes, or keyboard focus, while subcomponents consume this state implicitly via React Context.
3. **Accessibility Compliance**: Coordinated components can automatically manage ARIA attributes (`aria-expanded`, `aria-controls`, `aria-labelledby`) using internal unique identifiers.

### Headless Controllers via Custom Hooks
For highly specialized UI, coupling state and accessibility directly to JSX can limit reuse across divergent brand themes or device form factors. The **Headless Component Pattern** resolves this by extracting state machines, keyboard event listeners, and ARIA attributes into a custom hook (a headless controller).

The hook returns prop-getters: functions that apply the appropriate event handlers and ARIA attributes to whatever JSX elements the developer chooses to render.

### Component Composition Patterns Comparison

| Pattern | Inversion of Control | State Sharing Mechanism | JSX Ergonomics | Typing Complexity | Re-render Blast Radius | Modern React Status |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Compound Components** | High | Internal React Context | Declarative, clean | Moderate | Scoped to provider subtree | **Standard** for complex UI widgets |
| **Slots / Children** | High | Props (`ReactNode`) | Minimal, direct | Low | Isolated to parent shell | **Standard** for layouts and cards |
| **Headless Hooks** | Maximum | Hook return values / getters | Custom per consumer | Moderate | Scoped to calling component | **Standard** for design system primitives |
| **Render Props** | High | Function arguments | Verbose callback nesting | Moderate to High | Scoped to callback | **Specialized** (virtualization, dynamic lists) |
| **Higher-Order Components** | Low | Injected wrapper props | Indirected, obscured | High (prop collision risks) | Subtree wrapper overhead | **Legacy** (discouraged in modern codebases) |

## Concrete Implementation: An Accessible Compound Component

Below is a production-grade, fully typed TypeScript implementation of an accessible `Accordion` system using compound components.

This implementation features:
- Dual-mode support (`allowMultiple` for independent toggling or single-item expansion).
- Runtime context invariant assertions to fail fast during development if subcomponents are rendered outside the provider.
- WAI-ARIA compliance: `aria-expanded`, `aria-controls`, `role="region"`, and `aria-labelledby` linked via deterministic IDs.

```tsx
import React, {
  createContext,
  useContext,
  useState,
  useId,
  type ReactNode,
} from "react";

// ---------------------------------------------------------------------------
// 1. Root Accordion Context & Invariant Guard
// ---------------------------------------------------------------------------
interface AccordionContextValue {
  expandedItems: Set<string>;
  toggleItem: (id: string) => void;
}

const AccordionContext = createContext<AccordionContextValue | null>(null);

function useAccordionContext(componentName: string): AccordionContextValue {
  const context = useContext(AccordionContext);
  if (!context) {
    throw new Error(
      `<${componentName}> must be rendered within an <Accordion> parent provider.`
    );
  }
  return context;
}

// ---------------------------------------------------------------------------
// 2. Root Component
// ---------------------------------------------------------------------------
export interface AccordionProps {
  children: ReactNode;
  allowMultiple?: boolean;
  defaultExpanded?: string[];
  className?: string;
}

export function Accordion({
  children,
  allowMultiple = false,
  defaultExpanded = [],
  className = "",
}: AccordionProps) {
  const [expandedItems, setExpandedItems] = useState<Set<string>>(
    () => new Set(defaultExpanded)
  );

  const toggleItem = (id: string) => {
    setExpandedItems((prev) => {
      const next = new Set(allowMultiple ? prev : []);
      if (prev.has(id)) {
        next.delete(id);
      } else {
        next.add(id);
      }
      return next;
    });
  };

  return (
    <AccordionContext.Provider value={{ expandedItems, toggleItem }}>
      <div className={`divide-y divide-slate-200 rounded-lg border border-slate-200 ${className}`}>
        {children}
      </div>
    </AccordionContext.Provider>
  );
}

// ---------------------------------------------------------------------------
// 3. Item Level Context & Component
// ---------------------------------------------------------------------------
interface AccordionItemContextValue {
  itemId: string;
  isExpanded: boolean;
  triggerId: string;
  panelId: string;
}

const AccordionItemContext = createContext<AccordionItemContextValue | null>(null);

function useAccordionItemContext(componentName: string): AccordionItemContextValue {
  const context = useContext(AccordionItemContext);
  if (!context) {
    throw new Error(
      `<${componentName}> must be rendered within an <AccordionItem> parent.`
    );
  }
  return context;
}

export interface AccordionItemProps {
  id?: string;
  children: ReactNode;
  className?: string;
}

export function AccordionItem({ id, children, className = "" }: AccordionItemProps) {
  const generatedId = useId();
  const itemId = id ?? generatedId;
  const { expandedItems } = useAccordionContext("AccordionItem");
  const isExpanded = expandedItems.has(itemId);

  const triggerId = `accordion-trigger-${itemId}`;
  const panelId = `accordion-panel-${itemId}`;

  return (
    <AccordionItemContext.Provider value={{ itemId, isExpanded, triggerId, panelId }}>
      <div className={`overflow-hidden ${className}`}>{children}</div>
    </AccordionItemContext.Provider>
  );
}

// ---------------------------------------------------------------------------
// 4. Trigger Component
// ---------------------------------------------------------------------------
export interface AccordionTriggerProps {
  children: ReactNode;
  className?: string;
}

export function AccordionTrigger({
  children,
  className = "",
}: AccordionTriggerProps) {
  const { toggleItem } = useAccordionContext("AccordionTrigger");
  const { itemId, isExpanded, triggerId, panelId } = useAccordionItemContext("AccordionTrigger");

  return (
    <button
      type="button"
      id={triggerId}
      aria-expanded={isExpanded}
      aria-controls={panelId}
      onClick={() => toggleItem(itemId)}
      className={`flex w-full items-center justify-between px-5 py-4 text-left font-medium text-slate-900 transition-colors hover:bg-slate-50 focus:outline-none focus-visible:ring-2 focus-visible:ring-cyan-500 ${className}`}
    >
      <span>{children}</span>
      <span
        aria-hidden="true"
        className={`ml-4 text-xs text-slate-500 transition-transform duration-200 ${
          isExpanded ? "rotate-180" : "rotate-0"
        }`}
      >
        ▼
      </span>
    </button>
  );
}

// ---------------------------------------------------------------------------
// 5. Content Panel Component
// ---------------------------------------------------------------------------
export interface AccordionContentProps {
  children: ReactNode;
  className?: string;
}

export function AccordionContent({
  children,
  className = "",
}: AccordionContentProps) {
  const { isExpanded, triggerId, panelId } = useAccordionItemContext("AccordionContent");

  if (!isExpanded) {
    return null;
  }

  return (
    <div
      id={panelId}
      role="region"
      aria-labelledby={triggerId}
      className={`px-5 pb-5 pt-1 text-sm leading-relaxed text-slate-600 ${className}`}
    >
      {children}
    </div>
  );
}
```

### Consumer Usage
Notice how clean the consumer syntax is. The caller is free to insert badges, subtext, or nested layout containers directly inside the trigger or content panels without modifying the accordion's state management:

```tsx

            <span className="rounded bg-emerald-100 px-2 py-0.5 text-xs font-semibold text-emerald-800">

        </AccordionTrigger>
        <AccordionContent>
          <p>Hardware keys and TOTP authenticator apps are active on this account.</p>
        </AccordionContent>
      </AccordionItem>

      <AccordionItem id="sessions">
        <AccordionTrigger>Active Device Sessions</AccordionTrigger>
        <AccordionContent>
          <p>Review and revoke credentials for external devices logged into your team.</p>
        </AccordionContent>
      </AccordionItem>
    </Accordion>
  );
}
```

## State Colocation and Context Discipline

One of the primary causes of degraded performance and unmaintainable complexity in large React codebases is mismanaging state ownership.

### The Kent C. Dodds State Colocation Principle
The core guiding rule for state architecture is straightforward:

> **Push state down as close as possible to the components that consume it.**

When two components require access to shared data, elevate that state only to their **Lowest Common Ancestor (LCA)**. Avoid promoting local UI state (such as modal open status, active tabs, or search input filters) into global application stores.

```text
The State Colocation Hierarchy
┌─────────────────────────────────────────────────────────────┐
│ 1. Leaf Local State (`useState`, `useReducer`)              │
│    Scoped to single component (input text, hover toggles)   │
└──────────────────────────────┬──────────────────────────────┘
                               │ needed by sibling
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. Lifted Ancestor State                                    │
│    Lowest common ancestor passes down to immediate consumers│
└──────────────────────────────┬──────────────────────────────┘
                               │ needed across compound subtree
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. Feature / Subtree Context                                │
│    Scoped to widget or route (Form context, Table context)  │
└──────────────────────────────┬──────────────────────────────┘
                               │ cross-feature domain sync
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 4. Atomic External Store (`useSyncExternalStore`, Zustand)  │
│    Global, selective subscriptions (Auth session, Cart)     │
└─────────────────────────────────────────────────────────────┘
```

### The "Context Hell" Anti-Pattern and Re-render Cascades
React Context was engineered for dependency injection (passing themes, locale, or authenticated identity across deep trees), not as a high-frequency state bus.

In React's reconciliation engine:
- When a Context Provider's `value` changes (evaluated via `Object.is`), **every single component that invokes `useContext(MyContext)` re-renders**.
- This re-render occurs **regardless of whether the component was wrapped in `React.memo`**, and regardless of whether the component actually uses the specific property that changed.

Consider a monolithic application context:

```tsx
// Anti-Pattern: Monolithic context value
interface AppState {
  user: User;
  theme: "light" | "dark";
  notifications: Notification[];
  activeFilter: string;
}

export const AppContext = createContext<AppState | null>(null);
```

Whenever a new notification arrives, `notifications` is updated. Because the context object reference changes, components reading only `theme` or `user` are forced to re-render. In an application with thousands of DOM nodes, this creates noticeable main-thread jank.

### Context Splitting
To prevent unnecessary re-render cascades while retaining React Context, split state along two axes: **Domain Independence** and **Change Frequency**:

1. **Split by Domain**: Separate unrelated domains into discrete contexts (`ThemeContext`, `AuthContext`, `NotificationContext`).
2. **Split State from Dispatch**: State values update frequently, but dispatch functions (like actions or setters) are referentially stable.

```tsx
// Pattern: Separating State from Dispatch
interface CartState {
  items: CartItem[];
  total: number;
}

type CartDispatch = (action: CartAction) => void;

const CartStateContext = createContext<CartState | null>(null);
const CartDispatchContext = createContext<CartDispatch | null>(null);

export function CartProvider({ children }: { children: React.ReactNode }) {
  const [state, dispatch] = useReducer(cartReducer, initialCartState);

  return (
    <CartStateContext.Provider value={state}>
      <CartDispatchContext.Provider value={dispatch}>
        {children}
      </CartDispatchContext.Provider>
    </CartStateContext.Provider>
  );
}
```

Components that only dispatch actions (such as an `AddToCartButton`) consume `CartDispatchContext`. When items are added, `AddToCartButton` does not re-render because its context value never changes.

### Atomic External Stores
When fine-grained reactivity across scalar values is required, external state libraries (such as Zustand, Jotai, or Redux Toolkit) provide selective subscription mechanisms via React's official `useSyncExternalStore` API.

```tsx
// Granular subscription: re-renders ONLY when `itemCount` changes
const itemCount = useCartStore((state) => state.items.length);
```

Here, the component subscribes to a derived selector. Changes to other parts of the cart store do not trigger a render cycle in this component.

## Render Performance & The Fiber Reconciliation Tree

Understanding how React's Fiber reconciler processes component trees allows developers to optimize rendering behavior cleanly without overusing memoization.

### React's Default Render Propagation Invariant
In standard React operation:

> **When a parent component renders, all of its descendant components render unconditionally.**

This occurs because React models rendering as functional evaluation: $V = f(S)$. React cannot assume a child component is a pure function unless explicitly instructed. If a parent re-evaluates, React recursively executes the render functions of every child component down that subtree.

### The "Children-as-Props" (Slot) Optimization Mechanics
One of the most effective and underutilized performance patterns in React avoids `React.memo` entirely by leveraging the properties of JSX compilation:

```text
Default Propagation (Monolithic Parent)
  [ Parent (State Changes) ] ──(triggers render)──► Re-evaluates JSX
              │
              ├──► [ Child A ] ──► Re-rendered unconditionally
              │
              └──► [ Expensive Subtree ] ──► Re-rendered unconditionally!
                   ↳ React evaluates entire VDOM branch recursively.


Slot Pattern via `children` (Scoped Isolation)
  [ Grandparent Scope ] ──► Instantiates <ExpensiveSubtree /> once
              │
              ▼
  [ Parent Wrapper (State Changes) ]
              │
              ├──► [ Internal Local UI ] ──► Re-rendered
              │
              └──► {props.children}
                   ↳ Reconciliation check: prevProps.children === nextProps.children (True)
                   ↳ Reconciler bails out: Subtree reconciliation skipped entirely!
```

When JSX is written as `<Parent><Child /></Parent>`, the `<Child />` element is instantiated in the *outer* scope. It is passed into `Parent` as `props.children`.

When `Parent` updates its internal state and re-renders:
1. `Parent` re-executes its body.
2. `props.children` is an existing object reference created during the grandparent's render pass.
3. React's reconciler performs a reference check: `oldProps.children === newProps.children`.
4. Because the reference is identical, React skips re-rendering the entire `children` subtree.

### Concrete Comparison Code

The following example demonstrates how isolating stateful behavior into a slot wrapper shields expensive child trees from re-renders without memoization wrappers:

```tsx
import React, { useState, type ReactNode } from "react";

// ---------------------------------------------------------------------------
// An expensive data grid simulation
// ---------------------------------------------------------------------------
export function HeavyDataTable({ rows }: { rows: string[] }) {
  // In a real application, this might map thousands of table cells.
  return (
    <div className="rounded border border-slate-200 bg-white p-4">
      <h4 className="font-semibold text-slate-800">Records ({rows.length})</h4>
      <ul className="mt-2 space-y-1">
        {rows.map((row, idx) => (
          <li key={idx} className="text-sm text-slate-600">
            {row}
          </li>
        ))}
      </ul>
    </div>
  );
}

// ---------------------------------------------------------------------------
// Anti-Pattern: Monolithic Parent Managing Dynamic State
// Updating `filterText` forces <HeavyDataTable> to re-render on every keystroke!
// ---------------------------------------------------------------------------
export function MonolithicDashboard() {
  const [filterText, setFilterText] = useState("");
  const records = ["Record Alpha", "Record Beta", "Record Gamma"];

  return (

      <h3 className="font-medium text-red-900">Unoptimized Layout</h3>
```

### Deliberate Memoization vs. Cargo-Culting
Applying `React.memo`, `useMemo`, and `useCallback` indiscriminately across an entire codebase is a common architectural anti-pattern.

Memoization carries distinct operational trade-offs:
- **Memory Overhead**: Every `useMemo` and `useCallback` call requires allocating memory for cache storage and previous dependency arrays.
- **Comparison Cost**: On every render, React must execute an $O(k)$ shallow equality comparison across all entries in the dependency array. If dependencies change frequently, the application pays the cost of the comparison *plus* the execution cost.
- **Maintenance Drag**: Stale closure bugs frequently arise from improperly declared dependencies.

#### When Memoization Is Justified
1. **Reference Stability for Downstream Hooks**: When an object or callback is passed as a dependency to a `useEffect`, `useCallback`, or custom hook where reference changes trigger side effects or network requests.
2. **Heavy Computational Filters**: Transforming, sorting, or filtering large client-side data sets ($O(n \log n)$ operations) when the inputs change infrequently.
3. **High-Frequency Update Trees**: Wrapping pure leaf components (such as rows in an editable table or nodes in a real-time monitoring graph) that receive props from a rapidly changing parent.

#### Profiling Over Assumptions
Never apply memoization based on intuition alone. Use the **React DevTools Profiler**:
- Record user interactions and inspect the **Flamegraph**.
- Check the **"Why did this render?"** diagnostic flag.
- Verify whether component execution time actually impacts the 60fps / 120fps display refresh cycle before adding memoization complexity.

## Scaling the Codebase: Feature-Driven Vertical Slicing

As frontends expand to multiple cross-functional teams, directory organization dictates architecture.

### The Failure of Horizontal Layering
Early-stage applications typically arrange code horizontally by technical type:

```text
src/
├── components/       # Hundreds of miscellaneous components
├── hooks/            # Dozens of unrelated hooks
├── services/         # API clients
└── types/            # Global TypeScript definitions
```

In large systems, horizontal layering fails because:
- **No Conceptual Boundaries**: A change to the billing system requires jumping between `components/BillingCard.tsx`, `hooks/useBilling.ts`, and `services/billingApi.ts`.
- **High Risk of Circular Dependencies**: With all components cohabiting one directory, developers easily introduce circular imports between features.
- **Unclear Ownership**: Removing a retired feature requires detective work to verify which hooks and helper functions can be safely deleted.

### Feature-Driven Vertical Slicing
Modern architectures group code vertically by **Business Domain Slices**:

```text
src/
├── components/                 # Tier 1 Design System & Primitives
│   ├── button/
│   ├── modal/
│   └── accordion/
├── features/                   # Vertical Feature Slices
│   ├── billing/
│   │   ├── components/         # Tier 2 Domain Primitives
│   │   │   ├── InvoiceBadge.tsx
│   │   │   └── CardBrandIcon.tsx
│   │   ├── views/              # Tier 3 Composite Containers
│   │   │   └── BillingOverviewPanel.tsx
│   │   ├── hooks/              # Feature-scoped headless controllers
│   │   │   └── useInvoices.ts
│   │   ├── types/              # Domain schemas
│   │   │   └── billing.types.ts
│   │   └── index.ts            # Public API contract
│   └── team-management/
│       ├── components/
│       ├── views/
│       └── index.ts
└── app/                        # Tier 4 Route Layouts & Pages
    └── (dashboard)/
        └── billing/
            └── page.tsx
```

### Enforcing Module Boundaries via Public API Barrels
Each feature slice maintains a root `index.ts` file acting as its public boundary. Internal subcomponents, helper routines, and transient types remain unexported.

```typescript
// features/billing/index.ts
// Explicit Public API
export { BillingOverviewPanel } from "./views/BillingOverviewPanel";
export type { Invoice, PaymentPlan } from "./types/billing.types";

// Internal subcomponents (e.g. InvoiceTableRow, CardCvvInput) are NOT exported!
```

To enforce these boundaries mechanically, enterprise teams configure ESLint (e.g., using `eslint-plugin-import` with `no-restricted-paths` or project-level TypeScript path mapping boundaries):

```json
// Example ESLint constraint preventing cross-feature private imports
{
  "rules": {
    "import/no-restricted-paths": [
      "error",
      {
        "zones": [
          {
            "target": "./src/features/team-management",
            "from": "./src/features/billing",
            "except": ["./index.ts"],
            "message": "Features may only import from another feature's public barrel file (index.ts)."
          }
        ]
      }
    ]
  }
}
```

## Resilient Error Handling, Suspense, and Concurrent React

In a large application, minor failures in secondary widgets must never compromise the entire user interface.

### Granular Error Boundaries
By default, an uncaught JavaScript runtime error thrown during rendering unmounts the entire React component tree, presenting the user with an empty white screen.

To protect user experience, wrap **Tier 3 Composite Views** in granular Error Boundaries:

```tsx
import React, { Component, type ReactNode, type ErrorInfo } from "react";

interface Props {
  fallback: (error: Error, reset: () => void) => ReactNode;
  children: ReactNode;
}

interface State {
  error: Error | null;
}

export class GranularErrorBoundary extends Component<Props, State> {
  public state: State = { error: null };

  public static getDerivedStateFromError(error: Error): State {
    return { error };
  }

  public componentDidCatch(error: Error, errorInfo: ErrorInfo) {
    // Forward to observability pipeline (e.g. Sentry, Datadog)
    console.error("Uncaught widget error:", error, errorInfo);
  }

  public reset = () => {
    this.setState({ error: null });
  };

  public render() {
    if (this.state.error) {
      return this.props.fallback(this.state.error, this.reset);
    }
    return this.props.children;
  }
}
```

Placing this boundary around an isolated feature widget (such as a currency exchange graph) allows the rest of the dashboard, navigation bar, and user profile to remain interactive if that graph fails.

### Non-Blocking Transitions with `useTransition`
In complex applications, UI updates often compete for main-thread CPU time. When a user types into an input field while filtering a large list, synchronous rendering can cause perceptible input lag.

React's `useTransition` hook allows engineers to differentiate between **Urgent Updates** (immediate feedback, like keyboard typing and button clicks) and **Non-Urgent Transitions** (rendering heavy filtered views or switching tabs):

```tsx
import React, { useState, useTransition } from "react";

export function SearchableMemberDirectory({ members }: { members: Member[] }) {
  const [inputValue, setInputValue] = useState("");
  const [filteredMembers, setFilteredMembers] = useState(members);
  const [isPending, startTransition] = useTransition();

  const handleSearchChange = (e: React.ChangeEvent<HTMLInputElement>) => {
    const query = e.target.value;
    
    // 1. Urgent update: update input immediately to avoid typing lag
    setInputValue(query);

    // 2. Non-urgent transition: defer heavy list filtering
    startTransition(() => {
      const results = members.filter((m) =>
        m.name.toLowerCase().includes(query.toLowerCase())
      );
      setFilteredMembers(results);
    });
  };

  return (
    <div className="space-y-4">
      <div className="relative">
        <input
          type="text"
          value={inputValue}
          onChange={handleSearchChange}
          placeholder="Search team members..."
          className="w-full rounded border px-4 py-2"
        />
        {isPending && (
          <span className="absolute right-3 top-2.5 text-xs text-slate-400">
            Filtering...
          </span>
        )}
      </div>

      <MemberList members={filteredMembers} />
    </div>
  );
}
```

If the user types a new character before the previous transition finishes rendering, React interrupts the in-progress render pass to handle the keypress immediately, keeping the interface responsive.

## Production Component Architecture Checklist

Before approving front-end architectures for production deployment, review the component system against this operational checklist:

### 1. Component Taxonomy & Hierarchy
- [ ] Are design primitives (Tier 1) free of domain data models and API references?
- [ ] Do domain primitives (Tier 2) receive structured data strictly via props rather than invoking data-fetching hooks directly?
- [ ] Are state orchestration, queries, and mutations isolated to composite views (Tier 3)?
- [ ] Are route layouts and page shells (Tier 4) handling route param extraction and metadata configuration?

### 2. Composition & Inversion of Control
- [ ] Have boolean prop flags (`hasHeader`, `isCompact`, `showAction`) been evaluated for replacement via `children` or named slots?
- [ ] Are multi-part interactive widgets (accordions, tabs, dropdowns) implemented using the compound components pattern?
- [ ] Do compound component sub-elements provide invariant guards that throw clear development errors when rendered outside their parent provider?

### 3. State Management & Colocation
- [ ] Is local UI state colocated at the lowest possible ancestor rather than stored in global state?
- [ ] Are React Contexts split between state and dispatch to prevent unnecessary re-render cascades?
- [ ] Are high-frequency or cross-feature state updates managed via external stores with selector-based subscriptions (`useSyncExternalStore`)?

### 4. Render Performance & Reconciliation
- [ ] Have static or expensive subtrees been extracted and passed via `children` slots to take advantage of Fiber reference equality checks?
- [ ] Is memoization (`React.memo`, `useMemo`, `useCallback`) applied based on React DevTools Profiler data rather than speculative assumptions?
- [ ] Are dependency arrays in hooks containing only necessary scalar or referentially stable primitives?

### 5. Resilience & Accessibility
- [ ] Are composite feature containers wrapped in localized Error Boundaries with retry actions to prevent page-level crashes?
- [ ] Do interactive elements include complete WAI-ARIA roles, states (`aria-expanded`, `aria-controls`), and keyboard navigation support?
- [ ] Are long-running CPU calculations or filtering routines wrapped in `useTransition` or `useDeferredValue` to preserve main-thread responsiveness?

### 6. Codebase Structure & Boundaries
- [ ] Is feature code structured vertically by business domain (`features/<name>/`) rather than horizontally by technical type?
- [ ] Are module boundaries enforced through public barrel exports (`index.ts`) with linting rules to prevent cross-feature internal coupling?

## Conclusion: Designing for Evolution

Component architecture in React is fundamentally about managing change. Small applications can afford loose boundaries and informal conventions, but enterprise software requires structures that protect developers from accidental complexity.

By organizing components into clear architectural tiers, replacing boolean flag explosion with inversion of control, colocating state as close to leaves as possible, and aligning with React's Fiber reconciler, engineering teams build frontends that remain responsive, testable, and maintainable over years of continuous deployment.
