# Authentication vs Authorization: Understanding the Difference

In backend software engineering, few boundaries are as critical—or as frequently conflated—as the line between **authentication** (AuthN) and **authorization** (AuthZ). 

Teams often treat access control as a monolithic concern, grouping identity verification, token validation, and permission checks under a generic "auth" label. When these systems are small, the distinction feels academic: a single middleware validates a session cookie, reads a `role` column from a user record, and grants or denies access.

However, as systems evolve into distributed services, multi-tenant architectures, and complex data-sharing environments, conflating AuthN and AuthZ creates severe architectural debt and security vulnerabilities. Authentication failures expose systems to credential stuffing, session hijacking, and identity spoofing. Authorization failures yield the most pervasive vulnerabilities in modern APIs: Broken Object Level Authorization (BOLA/IDOR), Broken Function Level Authorization (BFLA), and tenant data leaks.

This guide provides a rigorous engineering treatment of both disciplines. We examine the fundamental boundaries between identity and entitlement, evaluate stateful sessions against stateless tokens, trace the evolution from RBAC to ABAC and ReBAC, analyze the decoupling of policy enforcement (PEP) from policy decisions (PDP), and review production failure modes with defensive code implementations.

## 1. The Core Distinction: Identity vs. Permissions

At its simplest architectural level, the boundary between authentication and authorization answers two fundamentally different questions at different stages of the request lifecycle:

- **Authentication (AuthN): "Who are you?"**  
  Authentication is the verification of an asserted identity. An actor (human user, service account, background worker, or external client) presents credentials to prove they are the entity associated with a given identifier. AuthN produces an authenticated identity context: a validated subject identifier (`sub`), proof of authentication timestamp (`auth_time`), authentication method assurance (MFA, password, WebAuthn), and tenant association.
- **Authorization (AuthZ): "What are you allowed to do?"**  
  Authorization is the determination of permissions and access rights. Given a verified identity context, an authorization engine evaluates whether that subject is permitted to perform a specific action (`read`, `write`, `delete`, `approve`) on a specific target resource (`document:1042`, `billing_account:acct_99`) within a specific environment (source IP, current time, device security posture).

```text
Incoming Request
  │
  ▼
[Transport Layer: TLS Termination]
  │
  ▼
[Authentication: AuthN] ────────────► 401 Unauthorized
  │ Validates: "Who is making the request?"
  │ Output: Verified Subject Context (ID, Tenant, Assurance)
  │
  ▼
[Coarse Authorization: AuthZ Gate] ──► 403 Forbidden
  │ Validates: "Can this subject access this endpoint/action?"
  │ (e.g., Role checks, Scopes)
  │
  ▼
[Fine-Grained Authorization: AuthZ] ─► 403 Forbidden / 404 Not Found
  │ Validates: "Can this subject access this specific entity?"
  │ (e.g., Object ownership, Tenant boundary, Relationship graph)
  │
  ▼
[Business Logic & Data Mutation]
```

### AuthN vs. AuthZ: Architectural Comparison

| Dimension | Authentication (AuthN) | Authorization (AuthZ) |
| :--- | :--- | :--- |
| **Primary Question** | *Who is the caller?* (Proof of identity) | *What is the caller permitted to do?* (Evaluation of rights) |
| **Input** | Credentials (passwords, TOTP, FIDO2/WebAuthn assertions, TLS client certificates, signed assertions). | Verified subject context, target resource identifier, requested action, contextual attributes. |
| **Output** | Validated identity context (subject ID, issuer, session key, tenant ID). | Boolean decision (`Allow` / `Deny`) or constraint filter (e.g., SQL `WHERE` clause). |
| **HTTP Status Code on Failure** | `401 Unauthorized` (semantically "Unauthenticated"). | `403 Forbidden` (or `404 Not Found` to prevent resource enumeration). |
| **Primary Protocols & Standards** | OpenID Connect (OIDC), SAML 2.0, FIDO2 / WebAuthn, RFC 7519 (JWT), RFC 6238 (TOTP). | OAuth 2.0 scopes (delegation), NIST SP 800-162 (ABAC), Google Zanzibar (ReBAC), OPA / Rego, Cedar. |
| **Evaluation Point** | Edge gateway, reverse proxy, or early API middleware. | Decentralized across service boundaries, controllers, data-access layers, and policy engines. |
| **State Dependencies** | Session store (Redis/DB) or public key set (JWKS) for signature validation. | Domain data model, resource ownership records, organization hierarchies, tenant mappings. |

### The "AuthN ≠ AuthZ" Fallacy

The most dangerous assumption in backend engineering is that verifying identity confers permission. 

Consider this sequence:
1. A client authenticates with the identity provider and receives a valid, cryptographically signed JSON Web Token (JWT).
2. The client sends a request: `GET /api/v1/invoices/inv_98412` with the header `Authorization: Bearer <valid_jwt>`.
3. An API gateway validates the token's cryptographic signature against the public JWKS, confirms that `exp` is in the future, and passes the request to the internal invoice service.

If the invoice service assumes that a valid token means the request is authorized, any authenticated user in the system can read every invoice in the database simply by guessing or iterating invoice IDs. Validating identity proves only who the user is; it provides zero information about whether that user owns or is entitled to view `inv_98412`.

## 2. Authentication Architecture & State Management

Authentication architecture determines how an application verifies credentials and maintains proof of that identity across subsequent stateless HTTP requests.

### Stateful Server-Side Sessions vs. Stateless Tokens

The debate between stateful sessions and stateless tokens is fundamentally a trade-off between **revocation latency** and **horizontal scalability**.

```text
Stateful Sessions (Reference-Based):
Client  ──[ Session ID Cookie ]──►  API Gateway / App Server
                                          │
                                          ▼ O(1) Lookup
                                    [ Central Session Store: Redis ]
                                    (Session payload, user ID, metadata)

Stateless Tokens (Value-Based):
Client  ──[ Bearer JWT ]──────────►  API Gateway / App Server
                                          │
                                          ▼ Local CPU Validation
                                    Verify Signature with Public Key (JWKS)
                                    (Claims embedded directly in token)
```

#### 1. Stateful Sessions (Opaque Reference Tokens)
In a stateful model, the client authenticates once. The server generates a cryptographically secure, high-entropy random string (e.g., 256 bits from a CSPRNG), stores session state (user ID, tenant ID, device metadata, creation time) in a fast key-value store (such as Redis), and returns the session ID to the client inside an `HttpOnly`, `Secure`, `SameSite=Lax` (or `Strict`) cookie.

- **Advantages:**
  - **Immediate, Deterministic Revocation:** Terminating a session requires an $O(1)$ key deletion (`DEL session:<id>`). If a user resets their password, changes permissions, or flags a stolen device, sessions are invalidated instantly across all nodes.
  - **Payload Minimization:** The network overhead is minimal (a small cookie identifier).
  - **Security Boundary:** Internal claims, permissions, and tenant metadata are never exposed to the client filesystem or browser memory.
- **Trade-offs:**
  - Every authenticated request requires a fast network hop to the central session store.
  - If the session store fails or experiences elevated latency, all API authentication degrades.
  - Multi-region replication requires distributed caching topologies (e.g., Redis Enterprise active-active CRDTs or regional session pinning).

#### 2. Stateless Tokens (Self-Contained Value Tokens: RFC 7519 JWT / PASETO)
In a stateless model, after authentication, the server mints a token containing identity claims (e.g., `sub`, `org_id`, `email`, `exp`, `iss`, `aud`) and signs it using an asymmetric key pair (e.g., RS256, Ed25519) or symmetric secret (HS256).

- **Advantages:**
  - **Zero Database Lookups on the Critical Path:** Any service holding the public verification key (often fetched periodically via a JSON Web Key Set / JWKS endpoint) can independently verify the token using CPU cycles alone.
  - **Microservice Portability:** The token travels across internal RPCs without forcing downstream services to query a centralized session registry.
- **The Stateless Revocation Paradox:**
  - By definition, a purely stateless token cannot be unilaterally revoked before its expiration (`exp`) timestamp without re-introducing centralized state.
  - If a user's account is compromised, their role is downgraded, or their email changes, a valid JWT remains accepted by every service until `exp` elapses.
  - Attempting to fix this by checking a central "token denylist" or "revocation list" in Redis on every request completely defeats the original purpose of using stateless tokens: you are paying the maintenance and payload cost of JWTs while still making a centralized database hop on every request.

#### The Production Compromise: Short-Lived Access Tokens + Refresh Token Rotation
To balance decoupled verification with revocation control, production systems deploy short-lived access tokens (5 to 15 minutes) paired with stateful, rotating refresh tokens (OAuth 2.1 / RFC 6749 / RFC 6819).

```text
[Client]                      [Authorization Server]                 [Resource Server]
   │                                     │                                   │
   │── 1. POST /token (User/Pass) ──────►│                                   │
   │◄── 2. Access Token (TTL: 10m) ──────│                                   │
   │       Refresh Token (RT_1)          │                                   │
   │                                     │                                   │
   │── 3. GET /resource (Bearer AT) ────────────────────────────────────────►│
   │                                                                         │ (Local Signature Check)
   │◄── 4. 200 OK (Data) ────────────────────────────────────────────────────│
   │                                     │                                   │
   │   ... 10 minutes pass (AT expires) ...                                  │
   │                                     │                                   │
   │── 5. POST /token (Refresh: RT_1) ──►│                                   │
   │                                     │ (Invalidates RT_1, stores RT_2)   │
   │◄── 6. Access Token (New) ───────────│                                   │
   │       Refresh Token (RT_2)          │                                   │
   │                                     │                                   │
   │── 7. REPLAY ATTACK: Attacker presents RT_1 again ──────────────────────►│
   │                                     │ (Replay Detected!)                │
   │                                     │ Revokes RT_2 & Family Sessions!   │
   │◄── 8. 400 Bad Request (Compromised) │                                   │
```

1. **Access Token (JWT):** Valid for 5 to 15 minutes. Validated statelessly by downstream APIs using public keys. Exposure window is strictly bounded.
2. **Refresh Token (Opaque):** Stored in a secure database table alongside a family identifier (`family_id`), user identifier, and rotation sequence.
3. **Rotation & Reuse Detection:** When the client exchanges `RT_1` for a new access token, the server atomically marks `RT_1` as used and issues `RT_2`. If an attacker intercepted `RT_1` and attempts to use it later, the server detects that an already-invalidated token from that family was presented. The authorization server immediately revokes all refresh tokens associated with that entire family and forces a full re-authentication.

### Credential Assurance: Passkeys vs. TOTP vs. SMS

Not all authentication mechanisms provide equal cryptographic guarantees. Production architectures must categorize credentials by their resistance to phishing and interception:

1. **FIDO2 / WebAuthn (Passkeys):**
   - **Mechanism:** Asymmetric public-key cryptography backed by secure hardware (TPM, Secure Enclave, YubiKey).
   - **Security Properties:** Origin-bound challenge-response. The browser signs a cryptographic challenge using the private key associated specifically with the exact web origin (domain).
   - **Phishing Resistance:** Absolute resistance to credential harvesting and reverse-proxy MitM attacks (e.g., Modlishka, Evilginx). Even if a user is tricked into visiting `evil-openstair.com`, the authenticator refuses to sign challenges for that domain using the `openstair.com` credential.
2. **Time-Based One-Time Passwords (TOTP - RFC 6238):**
   - **Mechanism:** Symmetric secret key shared between server and authenticator app, evaluated using HMAC-SHA1/SHA256 across 30-second time steps.
   - **Security Properties:** Protects against credential reuse from database breaches.
   - **Vulnerabilities:** Susceptible to real-time reverse-proxy phishing. If the user types their 6-digit TOTP into a phishing proxy, the attacker forwards it to the genuine server within the 30-second window and establishes a session.
3. **SMS / Voice OTP:**
   - **Vulnerabilities:** Vulnerable to SIM-swapping, SS7 telecom routing exploits, carrier employee social engineering, and plain-text lockscreen preview interception.
   - **Standard Guidance:** Explicitly deprecated for high-assurance systems under NIST SP 800-63B (Digital Identity Guidelines).

### Identity vs. Delegation: OpenID Connect (OIDC) vs. OAuth 2.0

A frequent architecture mistake is attempting to use OAuth 2.0 directly as an authentication protocol.

- **OAuth 2.0 (RFC 6749):** An **authorization delegation framework**. It allows a user (resource owner) to grant a third-party application (client) delegated access to their resources hosted on an API (resource server) without sharing their password. The output of OAuth 2.0 is an **Access Token** (`access_token`). The access token is opaque to the client and represents authorization to call specific endpoints with defined `scopes` (e.g., `read:reports`). It does not specify who authenticated the user or how.
- **OpenID Connect (OIDC):** An **identity layer built directly on top of OAuth 2.0**. OIDC extends the OAuth authorization code flow by introducing a dedicated identity token: the **ID Token** (`id_token`). The ID token is a signed JWT formatted according to an explicit schema containing profile claims (`sub`, `iss`, `aud`, `exp`, `auth_time`). OIDC also standardizes a discovery document (`/.well-known/openid-configuration`) and a `/userinfo` endpoint.

**Rule of Thumb:** Use OIDC to log a user in and know who they are. Use OAuth 2.0 access tokens to authorize API requests made by applications.

## 3. The Evolution of Authorization Models

Once identity is established, the authorization layer determines what that identity is allowed to do. Over the past three decades, backend architectures have evolved through three primary paradigms.

### 1. Role-Based Access Control (RBAC)

RBAC assigns permissions to named **Roles** (e.g., `Admin`, `Editor`, `BillingManager`, `Viewer`), and subjects are assigned to one or more roles.

```text
Subject (Alice) ──► Assigned Role (Editor) ──► Granted Permissions (document:read, document:write)
```

- **Strengths:** Intuitive mental model, simple database schema (`users`, `roles`, `permissions`, `user_roles`, `role_permissions`), and straightforward caching.
- **The Role Proliferation (Role Explosion) Anti-Pattern:**  
  Pure RBAC breaks down when permissions depend on context or data ownership. Consider a SaaS product with the following requirements:
  - An Editor can edit their own drafts.
  - An Editor cannot edit another user's drafts unless they are in the same department.
  - A regional compliance reviewer can view documents only in the EMEA region during regional working hours.
  
  In a pure RBAC system, accommodating these requirements forces teams to invent new roles: `EMEA_Compliance_Reviewer`, `Marketing_Editor_DraftOnly`, `Sales_Editor_ApprovedOnly`. The role table grows combinatorially ($O(N \times M)$), making permission audits and user administration virtually impossible.

### 2. Attribute-Based Access Control (ABAC - NIST SP 800-162)

ABAC resolves role proliferation by evaluating dynamic policies against attributes associated with four entities:

1. **Subject Attributes:** Roles, department, clearance level, organization ID, employment status.
2. **Resource Attributes:** Owner ID, department, classification (`confidential`, `public`), current lifecycle status (`draft`, `archived`), tenant ID.
3. **Action Attributes:** `read`, `create`, `update`, `delete`, `export`, `approve`.
4. **Environment Attributes:** Current timestamp, request IP CIDR, device management status, geolocation.

```text
Policy Rule:
ALLOW Action: document:update
WHERE
  Subject.org_id == Resource.org_id AND
  (
    Subject.id == Resource.owner_id OR
    (Subject.role == "Editor" AND Subject.department == Resource.department)
  ) AND
  Resource.status != "archived" AND
  Environment.is_trusted_network == true;
```

- **Strengths:** Tremendous expressive power. A single declarative policy replaces dozens of specialized roles.
- **Trade-offs:** High computational complexity. Evaluating complex boolean logic across external attributes on every request can degrade latency. Furthermore, answering inverse audit questions ("*Enumerate every document Alice can read across the enterprise*") requires scanning all resources against the policy engine rather than inspecting a simple join table.

### 3. Relationship-Based Access Control (ReBAC & Google Zanzibar)

Pioneered by Google's Zanzibar paper (2019) and popularized by modern engines like Ory Keto and SpiceDB, ReBAC models authorization as a **directed graph of relations between entities**.

Instead of assigning attributes or roles in isolated tables, authorization state is stored as a set of relational tuples:

$$\langle\text{object}\rangle\#\langle\text{relation}\rangle@\langle\text{user}\rangle$$

```text
// Zanzibar Relation Tuples
document:q4_roadmap#owner@user:alice
document:q4_roadmap#parent@folder:strategy_2026
folder:strategy_2026#viewer@group:engineering#member
group:engineering#member@user:bob
```

Authorization checks evaluate graph reachability: *"Can `user:bob` reach `document:q4_roadmap` via the `viewer` relation?"*

```text
[user:bob]
    │ member of
    ▼
[group:engineering]
    │ viewer of
    ▼
[folder:strategy_2026]
    │ parent of
    ▼
[document:q4_roadmap] ──► Result: ALLOW (Bob has inherited viewer access)
```

- **Strengths:** Naturally models hierarchical structures, team memberships, file system trees, and Google Docs-style user sharing. Enables fine-grained, recursive permission inheritance across large datasets with sub-millisecond graph index traversals.
- **Trade-offs:** Requires dedicated graph storage and indexing infrastructure. Overhead is unwarranted for simple applications that only require basic organizational boundaries.

### Authorization Models Compared

| Dimension | RBAC | ABAC | ReBAC |
| :--- | :--- | :--- | :--- |
| **Core Entity** | Static Roles (`Admin`, `Editor`) | Contextual Attributes (Subject, Resource, Action, Env) | Entity Relation Tuples (`object#relation@user`) |
| **Best Suited For** | Internal administration tools with static user categories. | Complex enterprise compliance, conditional access, dynamic attributes. | Multi-tenant B2B SaaS, document management, social networks, nested team hierarchies. |
| **Complexity Growth** | $O(N)$ roles multiply into role explosion. | Constant number of policies, but individual policy complexity increases. | Tuples scale with data entities; evaluation complexity depends on graph depth. |
| **Audit Question: "Who can access Resource X?"** | Trivial (read user-role mappings). | Expensive (requires evaluating policy across all subjects). | Fast graph index inversion (traversing incoming edges). |
| **Performance Profile** | Negligible CPU (indexed SQL join or in-memory bitmask). | CPU-bound policy logic; may require fetching external attributes. | Fast indexed key-value/graph lookups; requires distributed caching. |

## 4. Decoupled Architecture: PEP vs. PDP

In naive architectures, authorization logic is scattered across application code: hard-coded `if (user.role === 'admin')` checks inside Express/Fastify route handlers, nested authorization filters in ORM repositories, and conditional UI components.

This fragmentation creates critical operational issues:
- Security policies cannot be audited in one place.
- Updating a business rule requires modifying and deploying dozens of application services.
- Microservices written in different languages implement subtly conflicting authorization rules.

Modern security architectures solve this by formally separating the **Policy Enforcement Point (PEP)** from the **Policy Decision Point (PDP)**.

```text
                        ┌─────────────────────────────────────────┐
                        │   Policy Decision Point (PDP)           │
                        │   (OPA / Cedar / Embedded Engine)       │
                        │                                         │
                        │   Evaluates: Context vs Declarative     │
                        │              Policy Rules               │
                        └────────────────────▲────────────────────┘
                                             │
                        1. Query:            │  2. Decision:
                        Can Subject perform  │     Allow / Deny
                        Action on Resource?  │     (with constraints)
                                             │
┌────────────────────────┐                   ▼
│ Client Request         │        ┌───────────────────────────────┐
│                        ├───────►│ Policy Enforcement Point      │
│ GET /docs/104          │        │ (PEP: Middleware / Gateway)   │
│ Bearer <token>         │        └──────────────┬────────────────┘
└────────────────────────┘                       │
                                                 │ 3. If ALLOW: Dispatch
                                                 ▼
                                  ┌───────────────────────────────┐
                                  │ Business Service & Database   │
                                  │ (Applies Scoped Data Access)  │
                                  └───────────────────────────────┘
```

1. **Policy Enforcement Point (PEP):**  
   The interceptor located directly on the traffic path (API gateway, service mesh sidecar, HTTP middleware, or gRPC interceptor). The PEP does not make authorization decisions. It extracts the authenticated subject context, identifies the target resource and requested action, constructs a standardized authorization query, dispatches it to the PDP, and strictly enforces the outcome (`200 OK` or `403 Forbidden`).
2. **Policy Decision Point (PDP):**  
   The specialized policy engine (such as Open Policy Agent running Rego, AWS Cedar, or an in-process evaluation library). The PDP holds compiled, declarative authorization policies. Given a tuple of `(Subject, Resource, Action, Environment)`, it executes a deterministic evaluation and returns an unambiguous decision: `{ "allow": true }` or `{ "allow": false, "reason": "TENANT_MISMATCH" }`.

## 5. Hands-On Implementation: Decoupled ABAC Engine in TypeScript

To demonstrate these principles in practice, the following self-contained TypeScript implementation establishes a decoupled PEP/PDP architecture. It enforces multi-tenant boundary checks, role permissions, dynamic resource ownership, and environmental context without external dependencies.

```ts
/**
 * Core Domain Interfaces for Decoupled Authorization
 */

export type Action = "document:read" | "document:write" | "document:delete" | "document:publish";

export interface Subject {
  id: string;
  orgId: string;
  roles: string[];
  department: string;
}

export interface Resource {
  id: string;
  type: "document";
  orgId: string;
  ownerId: string;
  department: string;
  isArchived: boolean;
}

export interface Environment {
  timestamp: Date;
  isCorporateNetwork: boolean;
}

export interface PolicyContext {
  subject: Subject;
  resource: Resource;
  action: Action;
  environment: Environment;
}

export interface PolicyDecision {
  allowed: boolean;
  reason: string;
}

export type PolicyRule = (context: PolicyContext) => PolicyDecision | null;

/**
 * Policy Decision Point (PDP)
 * Encapsulates declarative rules and evaluates access decisions.
 */
export class PolicyDecisionPoint {
  private rules: PolicyRule[] = [];

  constructor() {
    this.registerDefaultRules();
  }

  public addRule(rule: PolicyRule): void {
    this.rules.push(rule);
  }

  /**
   * Evaluates the context against all registered policies.
   * Employs a strict "Default Deny" posture.
   */
  public evaluate(context: PolicyContext): PolicyDecision {
    for (const rule of this.rules) {
      const result = rule(context);
      if (result !== null) {
        return result;
      }
    }

    return {
      allowed: false,
      reason: "DEFAULT_DENY: No policy rule explicitly granted access.",
    };
  }

  private registerDefaultRules(): void {
    // 1. Invariant: Strict Multi-Tenant Boundary
    this.addRule((ctx) => {
      if (ctx.subject.orgId !== ctx.resource.orgId) {
        return {
          allowed: false,
          reason: "TENANT_ISOLATION_VIOLATION: Cross-tenant access is strictly prohibited.",
        };
      }
      return null; // Proceed to subsequent rules
    });

    // 2. Lifecycle Boundary: Archived resources are read-only
    this.addRule((ctx) => {
      if (ctx.resource.isArchived && ctx.action !== "document:read") {
        return {
          allowed: false,
          reason: "LIFECYCLE_RESTRICTION: Archived resources cannot be modified or deleted.",
        };
      }
      return null;
    });

    // 3. Admin Override: Organization admins have full access within their tenant
    this.addRule((ctx) => {
      if (ctx.subject.roles.includes("admin")) {
        return {
          allowed: true,
          reason: "ROLE_OVERRIDE: Tenant admin granted full access.",
        };
      }
      return null;
    });

    // 4. Resource Ownership: Owners can read, write, and delete their own active resources
    this.addRule((ctx) => {
      if (ctx.subject.id === ctx.resource.ownerId) {
        return {
          allowed: true,
          reason: "RESOURCE_OWNERSHIP: Subject is the explicit owner of this resource.",
        };
      }
      return null;
    });

    // 5. Departmental Collaboration: Editors in the same department can read and edit
    this.addRule((ctx) => {
      const isEditor = ctx.subject.roles.includes("editor");
      const isSameDept = ctx.subject.department === ctx.resource.department;
      const isAllowedAction = ctx.action === "document:read" || ctx.action === "document:write";

      if (isEditor && isSameDept && isAllowedAction) {
        return {
          allowed: true,
          reason: "DEPARTMENTAL_ABAC: Editor granted collaboration access within department.",
        };
      }
      return null;
    });
  }
}

/**
 * Policy Enforcement Point (PEP) Middleware
 * Intercepts requests, constructs context, and enforces PDP decisions.
 */
export interface AuthenticatedRequest {
  user?: Subject;
  params: { documentId: string };
  headers: Record<string, string>;
}

export interface HttpResponse {
  statusCode: number;
  body: Record<string, unknown>;
}

export interface ResourceRepository {
  findById(id: string): Promise<Resource | null>;
}

export class PolicyEnforcementPoint {
  constructor(
    private pdp: PolicyDecisionPoint,
    private repository: ResourceRepository
  ) {}

  public async handleRequest(
    req: AuthenticatedRequest,
    action: Action
  ): Promise<HttpResponse> {
    // 1. Verify Authentication Context (AuthN Check)
    if (!req.user) {
      return {
        statusCode: 401,
        body: { error: "UNAUTHORIZED: Valid authentication credentials required." },
      };
    }

    // 2. Fetch the target resource
    const resource = await this.repository.findById(req.params.documentId);
    if (!resource) {
      return {
        statusCode: 404,
        body: { error: "NOT_FOUND: The requested resource does not exist." },
      };
    }

    // 3. Assemble complete context for the PDP
    const context: PolicyContext = {
      subject: req.user,
      resource,
      action,
      environment: {
        timestamp: new Date(),
        isCorporateNetwork: req.headers["x-network-zone"] === "corp-internal",
      },
    };

    // 4. Query Policy Decision Point
    const decision = this.pdp.evaluate(context);

    // 5. Enforce Decision
    if (!decision.allowed) {
      return {
        statusCode: 403,
        body: {
          error: "FORBIDDEN: Insufficient entitlements to perform this action.",
          diagnosticReason: decision.reason,
        },
      };
    }

    // 6. Proceed to business logic execution
    return {
      statusCode: 200,
      body: { message: "Access granted.", resourceId: resource.id },
    };
  }
}
```

## 6. Critical Security Vulnerabilities & Failure Modes

When developers misunderstand the boundary between AuthN and AuthZ, specific vulnerability classes inevitably emerge.

### 1. Broken Object Level Authorization (BOLA / IDOR - OWASP API1:2023)

BOLA remains the number one vulnerability in production APIs. It occurs when an application exposes an endpoint that takes an object identifier (e.g., `/api/documents/:id`) and relies solely on authentication without validating that the authenticated user has rights to that specific entity.

#### The Vulnerable Anti-Pattern (Fetch-Then-Check or Blind Fetch):
```ts
// INSECURE: Relies solely on successful authentication middleware
app.get("/api/documents/:id", authenticateToken, async (req, res) => {
  const doc = await db.document.findUnique({
    where: { id: req.params.id }
  });

  if (!doc) return res.status(404).json({ error: "Not found" });
  
  // VULNERABILITY: An authenticated user from Org B can fetch documents belonging to Org A
  res.json(doc);
});
```

#### The Resilient Defensive Pattern (Scoped Query + Domain Check):
Do not fetch records blindly from the database and attempt to verify ownership in application memory. Instead, **enforce tenant and ownership boundaries directly at the data access layer**:

```ts
// SECURE: Enforces organization and identity scope at the database query level
app.get("/api/documents/:id", authenticateToken, async (req, res) => {
  const subject = req.user; // Derived strictly from verified AuthN context

  const doc = await db.document.findFirst({
    where: {
      id: req.params.id,
      orgId: subject.orgId, // Prevents cross-tenant leaks unconditionally
    }
  });

  // Return 404 rather than 403 to prevent resource ID enumeration across tenants
  if (!doc) {
    return res.status(404).json({ error: "Document not found" });
  }

  // Run fine-grained authorization for non-owners (e.g. via PDP)
  const isAuthorized = pdp.evaluate({ subject, resource: doc, action: "document:read", ... });
  if (!isAuthorized.allowed) {
    return res.status(403).json({ error: "Access denied" });
  }

  res.json(doc);
});
```

### 2. Broken Function Level Authorization (BFLA - OWASP API5:2023)

BFLA occurs when sensitive administrative endpoints rely on UI hiding or route obscurity rather than explicit permission checks at the controller level.

- **Failure Scenario:** A developer hides the "Delete Account" button in the frontend for non-admin users. However, the backend endpoint `DELETE /api/users/:id` only checks if the caller possesses a valid JWT, failing to verify that the user's role contains `user:delete`. A standard user who discovers the endpoint via network tools can delete any user in the system.
- **Defensive Rule:** Every mutating endpoint must declare an explicit permission dependency enforced by middleware:

```ts
// Declarative endpoint entitlement guard
router.delete(
  "/api/users/:id",
  authenticateToken,
  requirePermission("user:delete"),
  userController.deleteUser
);
```

### 3. The Confused Deputy Attack in Multi-Tenant Architectures

A **Confused Deputy** problem occurs when a service with elevated privileges is tricked by a less-privileged caller into performing an unauthorized action on their behalf.

```text
[User Alice] ──► [Service A: Public API] ──► [Service B: Internal Storage API]
(Unprivileged)   (Validates Alice AuthN)     (Receives Service A's System Credentials)
                 (Calls Service B using      (Executes operation using elevated
                  ambient service token)      Service A authority!)
```

In microservice architectures, developers often authenticate external users at an API Gateway (Service A), but then make internal RPC calls to downstream services (Service B) using a shared system-level service account token. 

Because Service B only inspects the caller's service identity (`Service A`), it executes the request with full administrative authority. If Alice asks Service A to process a file path belonging to Bob, Service B fulfills it because it trusts Service A.

#### Remediation Strategies:
1. **End-to-End Context Propagation:** Downstream services must never rely solely on caller service identity. Downstream RPCs must forward the original, cryptographically signed end-user identity assertion (or an OAuth 2.0 Token Exchange token via RFC 8693) alongside mutual TLS (mTLS) service identities.
2. **Dual-Subject Authorization:** Downstream services evaluate policies requiring both:
   - *Is Service A authorized to invoke this storage endpoint?* AND
   - *Is User Alice authorized to read the targeted file?*

### 4. HTTP Status Code Discipline: 401 vs. 403 vs. 404

Using incorrect HTTP status codes leaks internal architecture and creates authentication loops in client applications:

- **`401 Unauthorized`:** Semantically means **Unauthenticated**. The client has provided either no credentials or invalid/expired credentials. The response must include a `WWW-Authenticate` header indicating the required challenge. Returning 401 tells client libraries to clear tokens or trigger a login redirect.
- **`403 Forbidden`:** Semantically means **Unauthorized**. The server understands who the caller is, but the caller's entitlements are insufficient to perform the action. Re-authenticating with the same credentials will not change the outcome. Client libraries should display an access error, not redirect to the login page.
- **`404 Not Found` (Security Masking):** When a user requests an object belonging to a different tenant in a multi-tenant application, returning `403 Forbidden` confirms to an attacker that the resource ID exists. Returning `404 Not Found` completely masks the existence of the resource, defeating enumeration attacks.

## 7. Production Readiness & Security Checklist

Before approving an authentication and authorization architecture for production deployment, verify compliance across four primary operational areas:

### 1. Authentication (AuthN) Assurance
- [ ] **Credential Storage:** Passwords hashed using memory-hard, salt-backed algorithms (Argon2id or bcrypt with appropriate work factors).
- [ ] **Session Security:** Session cookies configured with `HttpOnly`, `Secure`, and `SameSite=Lax` (or `SameSite=Strict`).
- [ ] **Token Expiry:** Stateless access tokens have short lifespans (maximum 15 minutes).
- [ ] **Rotation & Replay:** Refresh tokens rotate on every exchange, and reuse detection invalidates the entire token family upon replaying expired tokens.
- [ ] **Phishing-Resistant MFA:** Critical actions (step-up authentication, credential resets) require FIDO2/WebAuthn hardware-backed challenges rather than SMS OTP.

### 2. Authorization (AuthZ) & Policy Enforcement
- [ ] **Default Deny Posture:** Policy engines and routing middleware deny requests unless an explicit rule grants access.
- [ ] **Decoupled Enforcement:** Endpoint controllers do not evaluate raw role strings; access is mediated by declarative PEP middleware.
- [ ] **Tenant Isolation in Queries:** Every data-access query for tenant-scoped resources includes `org_id` / `tenant_id` directly in the database query predicates.
- [ ] **BFLA Guards:** Every administrative and internal API route possesses an explicit, automated permission test ensuring non-privileged callers receive `403 Forbidden`.

### 3. Distributed Architecture & Microservices
- [ ] **Identity Propagation:** Internal microservice calls pass verified end-user context (JWT or RFC 8693 exchange token) rather than relying on ambient service-to-service trust.
- [ ] **Dual-Auth Verification:** Internal gateways verify both service identity (mTLS) and subject entitlement.

### 4. Observability & Audit Trails
- [ ] **Structured Security Logging:** Authentication failures, authorization denials, and token rotation anomalies emit structured JSON events with `subject_id`, `requested_resource`, `action`, `tenant_id`, and `ip_address`.
- [ ] **Credential Redaction:** Passwords, bearer tokens, API keys, and session cookies are scrubbed from application logs at the logger formatter level.
- [ ] **Rate Limiting by Identity:** Sensitive auth endpoints (`/login`, `/token`, `/password-reset`) enforce rate limits keyed on both client IP and attempted username/tenant to defeat distributed brute-force attacks.

---

## 8. Conclusion

Authentication and authorization represent two distinct, interdependent pillars of backend security:

- **Authentication establishes identity.** It transforms raw, untrusted network requests into a verified subject context.
- **Authorization enforces boundaries.** It evaluates that verified subject context against resource hierarchies, data ownership, organizational rules, and environmental factors.

High-performance, secure architectures keep these two concerns strictly decoupled. By selecting appropriate state models (sessions vs. short-lived tokens with refresh rotation), migrating away from fragile role-name checks toward declarative ABAC/ReBAC policies, enforcing data access at the query layer to defeat BOLA, and deploying automated PEP/PDP boundaries, engineering teams build systems that scale safely across millions of requests without exposing critical customer data.
