# Flutter Repository Pattern: When and How to Use It

In small Flutter prototypes, executing an HTTP `get` request directly inside a `StatefulWidget` or a state management controller feels harmless. A user taps a button, an asynchronous function triggers `http.get(Uri.parse(...))`, parses raw JSON into a map, and invokes `setState()` to update the view.

As applications scale into multi-feature production products, this direct data access pattern becomes an architectural liability. Business logic becomes tangled with transport protocols, network payloads leak directly into rendering trees, and testing a single screen requires mocking full HTTP servers or SQLite databases. When a backend team renames a single JSON attribute, changes cascade across dozens of widget files.

The **Repository Pattern** resolves this coupling. Originally formulated by Martin Fowler and Eric Evans, the pattern mediates between the domain and data mapping layers, presenting an in-memory collection-like interface of domain objects. In Flutter, it acts as the definitive boundary separating UI presentation and business logic from the mechanics of REST APIs, GraphQL endpoints, local disk databases, and hardware caches.

This guide provides a comprehensive, production-oriented breakdown of implementing the Repository Pattern in modern Flutter and Dart 3. We examine architectural topologies, data transfer object (DTO) boundaries, multi-source caching strategies, functional error handling using Dart 3 sealed classes, complete unit test patterns, and pragmatic anti-patterns to avoid.

## The Architectural Problem: Direct Data Coupling

To understand why repositories are valuable, examine what happens when an application queries data infrastructure directly from its state management or presentation layer:

```text
┌─────────────────────────────────────────────────────────────┐
│  Presentation Layer (StatefulWidget / ChangeNotifier / Bloc) │
└──────────────────────────────┬──────────────────────────────┘
                               │
               Direct, tightly coupled calls
                               │
         ┌─────────────────────┴─────────────────────┐
         ▼                                           ▼
┌──────────────────┐                       ┌──────────────────┐
│  Raw REST Client │                       │  SQLite / Drift  │
│  - http / dio    │                       │  - Raw SQL queries│
│  - JSON parsing  │                       │  - Table rows    │
│  - Status codes  │                       │  - DB migrations │
└──────────────────┘                       └──────────────────┘
```

This direct wiring introduces several critical failure modes:

1. **Wire Format Leaks**: If your UI consumes raw `Map<String, dynamic>` payloads or generated JSON serializable objects directly, backend API schema changes break widget rendering code across the codebase.
2. **Duplicated Caching Logic**: When two distinct screens require the same entity (such as user account details), each screen either refetches from the network redundantly or implements its own ad-hoc memory cache, leading to state desynchronization.
3. **Impaired Testability**: You cannot verify widget layout states or business logic workflows without mocking low-level socket connections, SQLite drivers, or global singleton clients.
4. **Scattered Error Handling**: Low-level infrastructure exceptions like `SocketException`, `HttpException`, and `TimeoutException` escape into UI presentation code, forcing developers to duplicate defensive `try/catch` blocks across numerous controllers.

A repository establishes a resilient abstraction boundary that isolates these concerns. For architectural teams implementing layered systems, understanding this boundary is foundational to [Flutter Clean Architecture for Maintainable Mobile Apps](/blog/flutter-clean-architecture).

## What is a Repository? (And What It Isn't)

A repository is an explicit mediator that encapsulates the logic required to access data sources. It centralizes common data access functionality, provides caching policies, and maps raw storage models to domain entities.

### Core Responsibilities of a Repository

- **Domain Model Provider**: Exposes clean, immutable domain entities to the application layer.
- **Data Source Orchestrator**: Coordinates between remote endpoints (HTTP, GraphQL, gRPC) and local persistence (SQLite, Drift, SharedPreferences, Hive).
- **Caching & Synchronization Policy Enforcer**: Determines whether to serve local cached data, fetch from the network, or implement a reactive cache invalidation strategy.
- **Exception Translator**: Catches raw transport and database exceptions and translates them into domain-level failures.

### What a Repository Is NOT

- **It is not an API Client**: A repository should not contain endpoint URL strings, HTTP header configurations, or query parameters. Those belong in a remote data source.
- **It is not a State Store**: A repository does not replace state management. It manages *data persistence and lifecycle*, while controllers (BLoCs, Riverpod notifiers, Cubits) manage *ephemeral UI state*. See our detailed comparison in [Flutter State Management: Choosing the Right Approach for Your App](/blog/flutter-state-management-guide).
- **It is not a 1:1 API Mirror**: A repository should reflect the domain needs of the application, not duplicate the exact REST endpoints exposed by a backend microservice.

## Component Boundaries: Data Source vs. Repository vs. Service

To maintain clean separation of concerns, production architectures distinguish between four primary roles in the data layer:

```text
┌─────────────────────────────────────────────────────────┐
│                   Presentation Layer                    │
│        (Widgets, Notifiers, BLoCs, Riverpod)            │
└────────────────────────────┬────────────────────────────┘
                             │ consumes Domain Entities
                             │ handles UI State
                             ▼
┌─────────────────────────────────────────────────────────┐
│                    Domain Contract                      │
│        abstract interface class UserRepository          │
└────────────────────────────┬────────────────────────────┘
                             │ implemented by
                             ▼
┌─────────────────────────────────────────────────────────┐
│               Data Layer: Repository                    │
│               UserRepositoryImpl                        │
│                                                         │
│  - Enforces Caching Policy (Cache-First / SWR)          │
│  - Catches I/O Exceptions → Maps to Domain Failures     │
│  - Invokes DTO.toDomain() Mappers                       │
└──────────────┬───────────────────────────┬──────────────┘
               │                           │
               ▼                           ▼
┌──────────────────────────────┐ ┌────────────────────────┐
│   Remote Data Source         │ │   Local Data Source    │
│   UserRemoteDataSource       │ │   UserLocalDataSource  │
│                              │ │                        │
│  - Dio / http client         │ │  - Drift / SQLite / DB │
│  - Auth headers & URLs       │ │  - SharedPreferences   │
│  - Parses JSON to DTOs       │ │  - Reads/writes DTOs   │
└──────────────────────────────┘ └────────────────────────┘
```

The table below contrasts the specific responsibilities of each layer:

| Dimension | Remote Data Source | Local Data Source | Repository Implementation | Presentation / State Layer |
| :--- | :--- | :--- | :--- | :--- |
| **Primary Responsibility** | Communicate with external network APIs | Read/write local disk persistence | Coordinate data sources, enforce caching, map models | Render UI, bind user inputs, manage view state |
| **Data Representation** | Raw JSON, DTOs (`UserDto`) | Database tables, local DTOs, key-value entries | Domain Entities (`User`) | Domain Entities, ViewModels, UI state classes |
| **Error Handling** | Throws `SocketException`, `HttpException` | Throws `SqliteException`, cache misses | Catches exceptions, returns typed `Result<T, Failure>` | Renders snackbars, error dialogs, empty views |
| **Caching Knowledge** | None (stateless transport) | Storage mechanics (table queries, key retrieval) | High-level caching policies (TTL, SWR, offline sync) | None (consumes emitted data stream or future) |
| **Dependencies** | `package:http`, `package:dio` | `drift`, `sqflite`, `shared_preferences` | Abstract data source interfaces, mappers | Flutter framework, Riverpod, BLoC, widgets |

## The DTO vs. Domain Entity Boundary

One of the most frequent architectural mistakes in Flutter applications is using the same model class for JSON serialization, database storage, and UI widget rendering.

### Why Separate DTOs from Entities?

A **Data Transfer Object (DTO)** is an external wire contract representation. It mirrors the exact structure returned by a REST API or database query. It accommodates backend naming conventions (e.g., `snake_case`), nullability quirks, and schema migrations.

A **Domain Entity** represents a core business model within your application. It contains only the fields your application requires, enforces business invariants, and remains completely decoupled from external serialization libraries.

```text
Backend Wire Payload (JSON)
          │
          ▼
┌───────────────────────────┐
│ UserProfileDto (DTO)      │ ──> Handles fromJson, toJson, null safety defaults
└─────────────┬─────────────┘
              │ .toDomain() explicit mapping
              ▼
┌───────────────────────────┐
│ UserProfile (Entity)      │ ──> Pure Dart, immutable, business invariants
└───────────────────────────┘
```

### Implementing DTO to Entity Mapping in Dart 3

Notice how the DTO handles missing backend values and type conversions, shielding the domain entity from serialization concerns:

```dart
// 1. Pure Domain Entity (Immutable, zero framework/serialization dependencies)
class UserProfile {
  final String id;
  final String email;
  final String displayName;
  final bool isVerified;

  const UserProfile({
    required this.id,
    required this.email,
    required this.displayName,
    required this.isVerified,
  });

  @override
  bool operator ==(Object other) =>
      identical(this, other) ||
      other is UserProfile &&
          runtimeType == other.runtimeType &&
          id == other.id &&
          email == other.email &&
          displayName == other.displayName &&
          isVerified == other.isVerified;

  @override
  int get hashCode => Object.hash(id, email, displayName, isVerified);
}

// 2. Data Transfer Object (DTO) handling serialization and schema quirks
class UserProfileDto {
  final String id;
  final String email;
  final String? fullName;
  final int? verificationStatus; // Backend returns 1 for verified, 0 for unverified

  const UserProfileDto({
    required this.id,
    required this.email,
    this.fullName,
    this.verificationStatus,
  });

  factory UserProfileDto.fromJson(Map<String, dynamic> json) {
    return UserProfileDto(
      id: json['id'] as String,
      email: json['email'] as String,
      fullName: json['full_name'] as String?,
      verificationStatus: json['verification_status'] as int?,
    );
  }

  Map<String, dynamic> toJson() {
    return {
      'id': id,
      'email': email,
      'full_name': fullName,
      'verification_status': verificationStatus,
    };
  }

  // Explicit translation from wire representation to domain entity
  UserProfile toDomain() {
    return UserProfile(
      id: id,
      email: email,
      displayName: (fullName != null && fullName!.trim().isNotEmpty)
          ? fullName!.trim()
          : 'Anonymous User',
      isVerified: verificationStatus == 1,
    );
  }
}
```

By decoupling these models:
- If the backend renames `full_name` to `display_name`, you update only `UserProfileDto.fromJson`. Zero widget files or domain use cases are altered.
- Domain entities remain pure Dart classes that can be instantiated instantly during testing without crafting mock JSON maps.

## Caching and Synchronization Topologies

The repository orchestrates multiple data sources by applying a deliberate caching policy. The choice of policy directly influences network consumption, battery usage, perceived performance, and offline resilience.

### 1. Cache-First (Offline-First)

The repository queries local storage first. If valid cached data exists, it returns immediately without initiating any network activity. If the cache is missing or explicitly expired according to a time-to-live (TTL) policy, it fetches from the remote source, persists the result locally, and returns.

- **Best Used For**: Static configuration, localized catalogs, lookup tables, and offline-heavy applications.
- **Limitation**: The user may see stale data until a forced refresh or expiration cycle occurs.

### 2. Network-First with Cache Fallback

The repository attempts to fetch fresh data from the remote API. Upon success, it updates the local cache and returns the new entity. If the remote request fails due to a timeout or network outage, it falls back to the locally cached data.

- **Best Used For**: Financial account balances, real-time ticket availability, or mission-critical transactions where data freshness is prioritized over instant render latency.
- **Limitation**: Introduces network latency on every read, slowing down screen rendering on poor mobile connections.

### 3. Stale-While-Revalidate (SWR / Reactive Stream)

The repository immediately emits cached local data via a reactive Dart `Stream`, allowing the UI to render content instantly. Concurrently, it initiates an asynchronous background network request. Once the fresh network payload arrives, the repository writes it to local persistence, which automatically emits the updated entity through the stream to refresh the UI.

```text
UI Presentation          Repository                  Local DB              Remote API
      │                       │                          │                       │
      │── watchProfile() ────>│                          │                       │
      │                       │── query cached DTO ─────>│                       │
      │                       │<── return cached DTO ────│                       │
      │<─ emit cached Entity ─│ (instant render)         │                       │
      │                       │                                                  │
      │                       │── background HTTP request ──────────────────────>│
      │                       │                                                  │
      │                       │<── return 200 OK + payload ──────────────────────│
      │                       │                                                  │
      │                       │── persist fresh DTO ────>│                       │
      │                       │<── write confirmed ──────│                       │
      │<─ emit fresh Entity ──│ (seamless update)        │                       │
      ▼                       ▼                          ▼                       ▼
```

- **Best Used For**: Social media feeds, user profiles, dashboards, and messaging lists where responsive time-to-content is vital.
- **Limitation**: Requires reactive state management capable of handling multiple emissions without triggering jarring layout shifts or resetting user scroll positions.

### Policy Comparison Matrix

| Strategy | Read Latency | Offline Resilience | Data Freshness | Complexity | Ideal Use Case |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Cache-First** | Low (instant local read) | High (works seamlessly offline) | Lower (bounded by TTL) | Moderate | Catalogs, settings, reference datasets |
| **Network-First** | High (waits for network) | Medium (fallback on error) | High (always fresh if online) | Moderate | Banking, inventory, checkout verification |
| **Stale-While-Revalidate** | Low (instant first emission) | High (cached read succeeds) | High (background refresh) | Higher | Activity feeds, user profile screens, dashboards |

Maintaining disciplined memory and caching behaviors directly supports smooth rendering. For practical techniques on optimizing frame budgets, consult our guide on [Flutter Performance Habits for Production Apps](/blog/flutter-performance-production-apps).

## Typed Error Modeling with Dart 3 Sealed Classes

In naive architectures, repositories let low-level transport exceptions (`SocketException`, `HttpException`, `TimeoutException`) bubble directly into UI presentation code. Alternatively, they catch everything and return `null`, obscuring the cause of failure.

A production repository translates infrastructure exceptions into typed domain failures. Using Dart 3 sealed classes, we can model operation results as a functional algebraic data type, guaranteeing that callers exhaustively handle all success and failure branches at compile time.

### Defining Typed Failures and Results

```dart
// Sealed class hierarchy for domain-level failures
sealed class Failure {
  final String message;
  const Failure(this.message);
}

final class NetworkFailure extends Failure {
  final int? statusCode;
  const NetworkFailure(super.message, {this.statusCode});
}

final class CacheFailure extends Failure {
  const CacheFailure(super.message);
}

final class ServerFailure extends Failure {
  final int? statusCode;
  const ServerFailure(super.message, {this.statusCode});
}

final class UnauthorizedFailure extends Failure {
  const UnauthorizedFailure(super.message);
}

// Sealed result type enforcing compile-time exhaustive matching
sealed class Result<T> {
  const Result();

  factory Result.success(T data) = Success<T>;
  factory Result.failure(Failure failure) = FailureResult<T>;
}

final class Success<T> extends Result<T> {
  final T data;
  const Success(this.data);
}

final class FailureResult<T> extends Result<T> {
  final Failure failure;
  const FailureResult(this.failure);
}
```

### Consuming Results in Presentation Code

With Dart 3 pattern matching, presentation controllers handle outcomes cleanly without fragile `try/catch` blocks:

```dart
// Example consuming pattern in a presentation controller or notifier
void handleProfileResult(Result<UserProfile> result) {
  final viewState = switch (result) {
    Success(:final data) => 'Profile loaded for ${data.displayName}',
    FailureResult(:final failure) => switch (failure) {
      NetworkFailure(:final message) => 'Offline: showing local data. ($message)',
      UnauthorizedFailure() => 'Session expired. Redirecting to login.',
      ServerFailure(:final message) => 'Server error: $message',
      CacheFailure(:final message) => 'Storage read failure: $message',
    },
  };
  
  // Update state or notify listeners
  debugPrint(viewState);
}
```

If a developer introduces a new `Failure` subtype (such as `ValidationFailure`), the Dart compiler immediately flags any unhandled `switch` expressions across the codebase, preventing unhandled runtime exceptions.

## Production Implementation in Dart 3

Here is a complete, self-contained implementation demonstrating how the abstract contract, data sources, and concrete repository orchestrate caching and typed errors.

### 1. The Abstract Contracts

```dart
import 'dart:async';
import 'dart:io';

// Abstract contract for Remote Data Source
abstract interface class UserProfileRemoteDataSource {
  Future<UserProfileDto> fetchUserProfile(String userId);
  Future<UserProfileDto> updateUserProfile(UserProfileDto dto);
}

// Abstract contract for Local Persistence Data Source
abstract interface class UserProfileLocalDataSource {
  Future<UserProfileDto?> getCachedUserProfile(String userId);
  Future<void> saveUserProfile(UserProfileDto dto);
  Future<void> clearCache(String userId);
}

// Abstract contract for Domain Repository
abstract interface class UserProfileRepository {
  Future<Result<UserProfile>> getUserProfile(
    String userId, {
    bool forceRefresh = false,
  });

  Stream<Result<UserProfile>> watchUserProfile(String userId);

  Future<Result<UserProfile>> updateUserDisplayName(
    String userId,
    String newDisplayName,
  );
}
```

### 2. The Concrete Repository Implementation

```dart
class UserProfileRepositoryImpl implements UserProfileRepository {
  final UserProfileRemoteDataSource remoteDataSource;
  final UserProfileLocalDataSource localDataSource;

  UserProfileRepositoryImpl({
    required this.remoteDataSource,
    required this.localDataSource,
  });

  @override
  Future<Result<UserProfile>> getUserProfile(
    String userId, {
    bool forceRefresh = false,
  }) async {
    // 1. Check local cache first unless explicit refresh is requested
    if (!forceRefresh) {
      try {
        final cached = await localDataSource.getCachedUserProfile(userId);
        if (cached != null) {
          return Result.success(cached.toDomain());
        }
      } catch (e) {
        // Cache read failure is non-fatal; proceed to remote source
      }
    }

    // 2. Fetch from remote data source
    try {
      final remoteDto = await remoteDataSource.fetchUserProfile(userId);

      // 3. Persist fresh data to local cache asynchronously
      try {
        await localDataSource.saveUserProfile(remoteDto);
      } catch (_) {
        // Cache write errors do not invalidate remote success
      }

      return Result.success(remoteDto.toDomain());
    } on SocketException catch (e) {
      // 4. On connection error, attempt fallback to local cache
      final fallback = await _safeGetCached(userId);
      if (fallback != null) {
        return Result.success(fallback.toDomain());
      }
      return Result.failure(NetworkFailure('No network connection: ${e.message}'));
    } on TimeoutException catch (e) {
      final fallback = await _safeGetCached(userId);
      if (fallback != null) {
        return Result.success(fallback.toDomain());
      }
      return Result.failure(NetworkFailure('Request timed out: ${e.message}'));
    } on FormatException catch (e) {
      return Result.failure(ServerFailure('Malformed server response: ${e.message}'));
    } catch (e) {
      return Result.failure(ServerFailure('Unexpected infrastructure error: $e'));
    }
  }

  @override
  Stream<Result<UserProfile>> watchUserProfile(String userId) async* {
    // Stale-While-Revalidate: Emit cached state first if present
    final cached = await _safeGetCached(userId);
    if (cached != null) {
      yield Result.success(cached.toDomain());
    }

    // Revalidate against remote backend
    try {
      final remoteDto = await remoteDataSource.fetchUserProfile(userId);
      await localDataSource.saveUserProfile(remoteDto);
      yield Result.success(remoteDto.toDomain());
    } catch (e) {
      // If we already emitted cached data, the user has readable content.
      // If no cached data existed, emit the network failure.
      if (cached == null) {
        yield Result.failure(NetworkFailure('Failed to load profile: $e'));
      }
    }
  }

  @override
  Future<Result<UserProfile>> updateUserDisplayName(
    String userId,
    String newDisplayName,
  ) async {
    try {
      // Retrieve current record to preserve unmodified fields
      final cached = await _safeGetCached(userId);
      final current = cached ?? await remoteDataSource.fetchUserProfile(userId);

      final updatedDto = UserProfileDto(
        id: current.id,
        email: current.email,
        fullName: newDisplayName,
        verificationStatus: current.verificationStatus,
      );

      final remoteResult = await remoteDataSource.updateUserProfile(updatedDto);
      await localDataSource.saveUserProfile(remoteResult);

      return Result.success(remoteResult.toDomain());
    } on SocketException catch (e) {
      return Result.failure(NetworkFailure('Cannot update while offline: ${e.message}'));
    } catch (e) {
      return Result.failure(ServerFailure('Profile update failed: $e'));
    }
  }

  Future<UserProfileDto?> _safeGetCached(String userId) async {
    try {
      return await localDataSource.getCachedUserProfile(userId);
    } catch (_) {
      return null;
    }
  }
}
```

> [!NOTE]
> **Platform Compatibility**: `SocketException` is part of `dart:io` and is standard across Flutter mobile (iOS, Android), desktop, and server targets. On Flutter Web, where `dart:io` is unavailable, HTTP clients (such as `package:http` or `package:dio`) throw client-specific exceptions like `ClientException` or `DioException`. In a production web-compatible codebase, the remote data source intercepts package-specific exceptions and rethrows standard exceptions or passes domain failures directly.

## Testing Repositories with Test Doubles

Because the repository interacts exclusively with abstract data source interfaces, writing unit tests requires no network mocking servers, no external processes, and no brittle integration setup.

We can implement lightweight in-memory test doubles (`Fakes`) that execute predictably in pure Dart unit tests:

```dart
import 'dart:async';
import 'dart:io';
import 'package:test/test.dart';

// 1. Lightweight Test Doubles (Fakes)
class FakeRemoteDataSource implements UserProfileRemoteDataSource {
  UserProfileDto? responseToReturn;
  Exception? exceptionToThrow;
  int fetchCallCount = 0;

  @override
  Future<UserProfileDto> fetchUserProfile(String userId) async {
    fetchCallCount++;
    if (exceptionToThrow != null) throw exceptionToThrow!;
    if (responseToReturn != null) return responseToReturn!;
    throw StateError('FakeRemoteDataSource: No response or exception configured');
  }

  @override
  Future<UserProfileDto> updateUserProfile(UserProfileDto dto) async => dto;
}

class FakeLocalDataSource implements UserProfileLocalDataSource {
  final Map<String, UserProfileDto> _storage = {};

  @override
  Future<UserProfileDto?> getCachedUserProfile(String userId) async => _storage[userId];

  @override
  Future<void> saveUserProfile(UserProfileDto dto) async => _storage[dto.id] = dto;

  @override
  Future<void> clearCache(String userId) async => _storage.remove(userId);
}

// 2. Comprehensive Repository Unit Tests
void main() {
  late FakeRemoteDataSource fakeRemote;
  late FakeLocalDataSource fakeLocal;
  late UserProfileRepository repository;

  setUp(() {
    fakeRemote = FakeRemoteDataSource();
    fakeLocal = FakeLocalDataSource();
    repository = UserProfileRepositoryImpl(
      remoteDataSource: fakeRemote,
      localDataSource: fakeLocal,
    );
  });

  test('returns cached profile without calling remote when cache exists and forceRefresh is false', () async {
    const cachedDto = UserProfileDto(
      id: 'usr_001',
      email: 'alex@example.com',
      fullName: 'Alex River',
      verificationStatus: 1,
    );
    await fakeLocal.saveUserProfile(cachedDto);

    final result = await repository.getUserProfile('usr_001', forceRefresh: false);

    switch (result) {
      case Success(:final data):
        expect(data.id, equals('usr_001'));
        expect(data.displayName, equals('Alex River'));
        expect(data.isVerified, isTrue);
        expect(fakeRemote.fetchCallCount, equals(0)); // Remote was never contacted
      case FailureResult():
        fail('Expected Success result but received Failure');
    }
  });

  test('falls back to local cache when remote fetch throws SocketException', () async {
    const cachedDto = UserProfileDto(
      id: 'usr_002',
      email: 'jordan@example.com',
      fullName: 'Jordan Lee',
      verificationStatus: 0,
    );
    await fakeLocal.saveUserProfile(cachedDto);

    fakeRemote.exceptionToThrow = const SocketException('Connection refused');

    // Forcing refresh forces an attempt on remote, which fails and triggers fallback
    final result = await repository.getUserProfile('usr_002', forceRefresh: true);

    switch (result) {
      case Success(:final data):
        expect(data.displayName, equals('Jordan Lee'));
        expect(data.isVerified, isFalse);
        expect(fakeRemote.fetchCallCount, equals(1)); // Remote was attempted
      case FailureResult():
        fail('Expected fallback to cached entity upon network failure');
    }
  });

  test('returns NetworkFailure when both remote and local cache fail', () async {
    fakeRemote.exceptionToThrow = const SocketException('No route to host');

    final result = await repository.getUserProfile('usr_999', forceRefresh: true);

    switch (result) {
      case Success():
        fail('Expected failure result but received Success');
      case FailureResult(:final failure):
        expect(failure, isA<NetworkFailure>());
        expect(failure.message, contains('No network connection'));
    }
  });
}
```

These unit tests execute in milliseconds, require zero Flutter widget bindings, and exercise all branch conditions (cache hit, cache miss, network fallback, total failure) deterministically.

## Common Anti-Patterns and Pragmatic Traps

While the repository pattern offers significant structural benefits, misapplying it can introduce unnecessary ceremony or subtle bugs.

### 1. The 1:1 Pass-Through Repository

An anemic repository that merely forwards method calls to an HTTP client without adding value:

```dart
// ANTI-PATTERN: Zero abstraction value
class ProductRepository {
  final ApiClient api;
  ProductRepository(this.api);

  Future<dynamic> getProducts() => api.get('/products');
}
```

If a repository does not map wire formats, manage a local cache, translate errors, or coordinate data sources, it is merely indirection masquerading as architecture. If an endpoint is truly a one-off stateless call, calling the data source directly or using a simple service wrapper is more honest.

### 2. Leaking Wire Types or Database Cursors

Allowing SQL cursors, Drift query objects, or `http.Response` instances to escape across the repository interface breaches the boundary. When presentation code relies on raw database types, changing your persistence layer from SQLite to an encrypted key-value store forces an invasive refactoring of your UI.

### 3. Confusing Repositories with UI State Management

A repository coordinates data access; it does not track whether a specific button is showing a loading spinner. Storing UI variables such as `bool isLoading` or `String? formValidationError` inside a singleton repository creates race conditions when multiple widgets observe the same repository simultaneously. UI state belongs in controllers (Cubit, Riverpod, BLoC); persistence state belongs in the repository.

### 4. The Monolithic "God Repository"

Consolidating unrelated domain operations into a single massive `AppRepository` (handling authentication, shopping carts, push notification tokens, product catalogs, and chat messages). Decompose repositories by domain aggregates: `AuthRepository`, `CartRepository`, and `CatalogRepository`.

## When NOT to Use the Repository Pattern

Architecture must serve the product, not abstract purity. Building a complete repository layer with DTOs, mappers, and local SQLite caches is unnecessary in several common scenarios:

1. **Prototypes and Proof-of-Concept Apps**: In early exploratory phases where validation speed outweighs long-term maintenance, direct service calls in controllers reduce initial overhead.
2. **Purely Static or Content-Only Apps**: An informational application displaying bundled asset data (such as a documentation reader or terms-of-service viewer) gains little from repository caching orchestration.
3. **Dedicated SDKs with Built-in Offline Engines**: Services like Google Firebase Firestore and Supabase provide native client SDKs that already include local disk caching, offline mutation queuing, and real-time streaming listeners. Wrapping Firestore in a custom repository often creates an unnecessary secondary caching layer that fights with Firestore's internal synchronization engine.
4. **Real-time Ephemeral Data Channels**: WebSocket feeds (such as live stock tickers or gaming telemetry) operate on streaming packets where disk caching and CRUD operations are irrelevant. A dedicated socket service or channel client is more appropriate.

For business stakeholders evaluating architectural investments, these trade-offs are explored further in [Why Flutter Works for Business Mobile Products](/blog/why-flutter-for-businesses).

## Production Verification Checklist

Before deploying a repository implementation to production, audit your code against this practical engineering checklist:

- [ ] **Contract Independence**: Does the repository interface return pure Domain Entities, without exposing DTOs, `http.Response`, or SQL cursor types?
- [ ] **Decoupled Data Sources**: Are Remote and Local data sources injected via abstract interfaces, allowing effortless test double substitution?
- [ ] **Explicit Mapping**: Are DTOs mapped to Domain Entities via explicit functions (`toDomain()`) rather than casting raw dynamic maps?
- [ ] **Typed Error Handling**: Are all infrastructure exceptions (`SocketException`, `TimeoutException`, `SqliteException`, `HttpException`) caught and translated into typed `Failure` classes?
- [ ] **Exhaustive Matching**: Are results modeled via Dart 3 sealed classes (`Result<T>`) enabling compile-time exhaustive checks in presentation code?
- [ ] **Defined Caching Policy**: Does the repository explicitly document whether it follows Cache-First, Network-First, or Stale-While-Revalidate semantics?
- [ ] **Cache Failure Resilience**: If local disk persistence fails (e.g., full disk or database corruption), does the repository log the failure and continue serving remote data gracefully?
- [ ] **State Separation**: Is the repository free from transient UI presentation state (`isLoading`, widget focus, form errors)?
- [ ] **Focused Scope**: Is the repository focused on a single domain aggregate rather than acting as a catch-all god object?
- [ ] **Unit Test Coverage**: Are both cache-hit and network-fallback code paths verified using fast, in-memory test doubles without invoking real I/O?

## Conclusion

The Repository Pattern in Flutter is not about adding boilerplate or blindly following enterprise dogma. It is an investment in long-term application stability and team velocity.

By drawing a clean boundary between domain entities and wire DTOs, your UI remains immune to backend API migrations. By coordinating local storage and remote APIs behind a single interface, you deliver resilient offline experiences and instant-render caching strategies. And by modeling errors as typed Dart 3 sealed classes, you convert unpredictable runtime exceptions into compiler-verified workflows.

Start by identifying the high-churn data sources in your application. Extract their contracts into clean abstract interfaces, isolate your network and database mechanics, and build a testing suite that proves your fallback behaviors work before your users encounter them in the field.
