# Mobile App Performance: Finding and Fixing Real Bottlenecks

Mobile applications run in an unforgiving operating environment. Unlike cloud servers with elastic compute, persistent high-speed power connections, and gigabytes of memory headroom, a mobile device is constrained by thermal limits, battery chemistry, shared physical memory, and aggressive operating system daemons designed to terminate misbehaving processes.

In development, performance problems are frequently obscured. Engineers test debug builds on flagship devices tethered to high-speed workstations, with thermal throttling disabled by constant airflow and power replenished through USB. In production, those same applications encounter low-tier hardware, thermal throttling under direct sunlight, fragmented carrier networks, and operating systems that kill background tasks without warning.

Achieving sustained performance on mobile devices requires moving past superficial remedies—such as sprinkling asynchronous keywords or restructuring UI trees—and understanding the physical boundaries of the device. This guide examines the four major runtime bottlenecks in mobile software engineering: rendering pipelines, memory pressure, cellular radio management, and application startup latency.

## 1. Display Physics, Frame Budgets, and the Rendering Pipeline

Mobile user experience is governed by the physical refresh cycle of the display panel. To present the illusion of continuous, fluid motion, the application and operating system must calculate, layout, rasterize, and swap display buffers before the hardware fires its vertical synchronization pulse (VSYNC).

### The Mathematical Reality of Frame Budgets

When a display refreshes at a fixed frequency, each frame has an absolute time ceiling. If the system fails to deliver a completed framebuffer before the hardware VSYNC deadline, the display controller must re-display the previous frame. This missed deadline is **jank** (a dropped frame), observed by the user as a visual stutter or hitched scroll.

The available budget is calculated directly from the refresh frequency:

$$\text{Frame Budget} = \frac{1000\text{ ms}}{\text{Refresh Rate (Hz)}}$$

On standard 60Hz displays:

$$\frac{1000\text{ ms}}{60} \approx 16.67\text{ ms}$$

On modern high-refresh panels (such as Apple ProMotion or 120Hz Android flagships):

$$\frac{1000\text{ ms}}{120} \approx 8.33\text{ ms}$$

| Refresh Rate | Frame Interval | Operating System Overhead | Target App Execution Budget | Primary Failure Mode |
| :--- | :--- | :--- | :--- | :--- |
| **60Hz (Standard)** | $16.67\text{ ms}$ | $\approx 2.0\text{--}3.5\text{ ms}$ | $\approx 13.0\text{--}14.5\text{ ms}$ | Dropped frames during rapid scrolling |
| **90Hz (Mid-tier)** | $11.11\text{ ms}$ | $\approx 1.5\text{--}2.5\text{ ms}$ | $\approx 8.5\text{--}9.5\text{ ms}$ | Micro-stutters during view transitions |
| **120Hz (ProMotion/Flagship)** | $8.33\text{ ms}$ | $\approx 1.0\text{--}2.0\text{ ms}$ | $\approx 6.3\text{--}7.3\text{ ms}$ | Visible hitching in gesture tracking |

Because the operating system compositor (such as Android SurfaceFlinger or iOS Render Server) requires a portion of every window to composite system overlays and status bars, the application's actual computation window is even narrower than the theoretical interval.

### The Dual-Thread Rendering Pipeline

Modern mobile frameworks—whether native Android (Kotlin/Java), native iOS (Swift/Objective-C), Flutter, or React Native—rely on a pipelined, multi-threaded execution model to prepare visual content:

```text
VSYNC Pulse
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│ UI Thread (Main Thread / Dart Isolate / JS Thread)          │
│  - Touch input dispatching                                  │
│  - Event loop processing                                    │
│  - Widget / View hierarchy build                            │
│  - Layout measurement & constraint propagation              │
│  - Text shaping & font metric calculations                  │
│  - Display list / Draw command recording                    │
└─────────────────────────────┬───────────────────────────────┘
                              │ Recorded Draw Commands
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ Render / Raster Thread (GPU Worker Thread)                  │
│  - Scene graph traversal                                    │
│  - Shader compilation & pipeline binding                    │
│  - Draw command translation (Skia, Impeller, Metal, Vulkan) │
│  - GPU command buffer dispatch                              │
└─────────────────────────────┬───────────────────────────────┘
                              │ GPU Execution
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ Display Hardware                                            │
│  - Framebuffer swap                                         │
│  - Panel scan-out                                           │
└─────────────────────────────────────────────────────────────┘
```

The UI thread and Render thread operate concurrently in a pipelined fashion. While the Render thread is rasterizing frame $N$ to submit to the GPU, the UI thread is processing input and building draw commands for frame $N+1$.

If work on the **UI Thread** exceeds the frame budget, the Render thread is starved of instructions and the frame drops. If the UI thread completes on time but the **Render Thread** stalls (due to excessive overdraw, un-cached complex paths, or expensive shader compilations), the GPU cannot complete the frame buffer in time for VSYNC, producing the identical user-facing jank.

### Main Thread Starvation and Watchdog Terminations

Because the UI thread also owns the platform event loop, freezing it does not merely drop frames—it halts all user interaction handling. 

Common causes of main thread starvation include:
- **Synchronous JSON Deserialization**: Decoding large payload strings (such as a 10MB API response) into structured heap models synchronously blocks the event loop for tens or hundreds of milliseconds.
- **Cryptographic Operations**: Asymmetric key exchange, token signature verification, and symmetric payload decryption.
- **Blocking Disk I/O**: Accessing disk storage synchronously, such as querying SQLite databases without background dispatch or calling synchronous preference stores (`SharedPreferences.apply()` vs `.commit()` on Android, or excessive `UserDefaults` synchronization on iOS).

When the main thread is blocked, host operating systems deploy watchdog daemons to kill unresponsive applications:

1. **Android Application Not Responding (ANR)**: Triggered when the main thread does not respond to an input dispatch event within $5\text{ seconds}$, or fails to process a BroadcastReceiver within $10\text{ seconds}$ (foreground) or $20\text{ seconds}$ (background). Android records a stack trace in `/data/anr/traces.txt` and presents a system dialog prompting the user to force-close the app.
2. **iOS Apple Watchdog (`0x8badf00d`)**: If an iOS application fails to check in with the `backboardd` or `SpringBoard` daemon during critical lifecycle transitions (such as taking longer than the allotted time during cold launch or scene state changes), the kernel terminates the process with exception code `0x8badf00d` ("ate bad food").

## 2. Memory Management, Image Decoding, and Host OS Killers

Mobile operating systems do not utilize swap partitions or swap files on flash storage due to wear-leveling constraints and flash drive endurance limits. When physical RAM is exhausted, the operating system cannot page anonymous memory out to disk. Instead, it aggressively reclaims resources by terminating active processes.

### The Decoded Bitmap Memory Formula

The single largest consumer of transient RAM in mobile applications is image handling. Developers often mistake compressed image file size (the bytes stored on disk or transferred over HTTP) for the runtime memory footprint of that image.

When an image format such as JPEG, PNG, or WebP is loaded, the operating system must fully decompress the compressed payload into an uncompressed raster bitmap buffer before the GPU can sample it into a display texture.

The memory occupied by a decoded image in RAM is independent of its compressed on-disk file size. It is determined solely by pixel dimensions and color depth:

$$\text{RAM Usage (bytes)} = \text{Width (pixels)} \times \text{Height (pixels)} \times \text{Bytes Per Pixel}$$

For standard 32-bit `RGBA_8888` color depth, each pixel requires 4 bytes (8 bits each for Red, Green, Blue, and Alpha channels):

$$\text{RAM Usage (bytes)} = \text{Width} \times \text{Height} \times 4$$

Consider a modern smartphone photo taken at a standard resolution of $4000 \times 3000$ pixels. On disk, efficient JPEG compression might compress this image into a modest **3 MB** file:

$$\text{Decoded RAM} = 4000 \times 3000 \times 4\text{ bytes} = 48,000,000\text{ bytes} \approx 45.78\text{ MiB} \approx 48\text{ MB}$$

```text
On-Disk / Over-the-Air: 3 MB (Compressed JPEG)
                       │
                       │ [CPU Decompression / Codec]
                       ▼
In-Memory Raw Bitmap:   48 MB (Uncompressed RGBA_8888)
```

Displaying just four such full-resolution images simultaneously in a scrolling list without downsampling allocates nearly **200 MB** of raw bitmap memory, quickly triggering system-level memory pressure.

| Image Source / Asset | Pixel Dimensions | Disk Size (Compressed) | Decoded RAM (RGBA_8888) | Impact on Low-Tier Device |
| :--- | :--- | :--- | :--- | :--- |
| **User Avatar (Thumbnail)** | $100 \times 100$ | $15\text{ KB}$ | $\approx 40\text{ KB}$ | Negligible |
| **Feed Card (Viewport)** | $800 \times 600$ | $180\text{ KB}$ | $\approx 1.92\text{ MB}$ | Manageable with pool recycling |
| **High-Resolution Header** | $1920 \times 1080$ | $650\text{ KB}$ | $\approx 8.29\text{ MB}$ | High; requires prompt disposal |
| **Unscaled Camera Capture** | $4000 \times 3000$ | $3.2\text{ MB}$ | $\approx 48.00\text{ MB}$ | Severe; triggers memory warnings |
| **4K Full-Bleed Asset** | $3840 \times 2160$ | $4.5\text{ MB}$ | $\approx 33.18\text{ MB}$ | Severe; high risk of background termination |

### Downsampling Mitigations

To prevent memory bloat, images must be downsampled during the decode step directly into the physical dimensions of the target viewport, rather than decoding full-resolution buffers and scaling them down in the layout tree.

- **Flutter**: Use `ResizeImage` or set `cacheWidth` and `cacheHeight` on `Image.network` or `Image.asset`. This instructs the underlying engine to decode the image into a smaller bitmap buffer before allocating texture memory.
- **Android**: Configure `BitmapFactory.Options.inSampleSize` to decode a sub-sampled version of the source bitmap into memory, or use `inDensity` and `inTargetDensity`.
- **iOS**: Use Image I/O framework APIs (`CGImageSourceCreateThumbnailAtIndex`) with `kCGImageSourceThumbnailMaxPixelSize` to create a downsampled thumbnail directly from the data stream without decompressing the full image into memory.

### Host OS Memory Pressure Daemons

When an application's resident memory grows, host operating systems do not quietly degrade. They dispatch background daemons that enforce hard memory ceilings:

#### iOS Jetsam Daemon
iOS manages memory pressure through the `memorystatus` subsystem and the **Jetsam** kernel daemon. Jetsam categorizes memory into **clean** (read-only file mappings that can be discarded and re-read from disk) and **dirty** (heap allocations, decoded bitmaps, and unwritten caches that cannot be discarded).

When available system RAM drops below critical thresholds:
1. Jetsam broadcasts `UIApplicationDidReceiveMemoryWarningNotification` to active apps.
2. If memory is not immediately freed, Jetsam terminates background processes in priority order, followed by the active foreground process if it crosses its per-process high-water mark.
3. The crash report records an `EXC_RESOURCE` exception with reason `per-process-limit` or `highwater`.

Background applications have significantly lower memory thresholds. An application that leaks memory while running in the foreground will frequently be killed by Jetsam seconds after the user switches to another app.

#### Android Low Memory Killer Daemon (`lmkd`)
Modern Android systems utilize the userspace Low Memory Killer Daemon (`lmkd`), which monitors memory pressure by reading Linux kernel **Pressure Stall Information (PSI)** and memory zone metrics (`/proc/zoneinfo`).

Processes are scored using an `oom_score_adj` integer ranking between `-1000` (system processes and active foreground applications) and `+1000` (cached background processes). When memory stalls cross critical pressure boundaries, `lmkd` issues a `SIGKILL` to the process with the highest `oom_score_adj` to reclaim physical memory pages.

### Common Memory Leak Vectors

1. **Retaining UI Contexts Across Asynchronous Gaps**: Holding a reference to an `Activity`, `UIViewController`, or `BuildContext` inside a long-running background asynchronous task or closure. If the user navigates away before the task completes, the entire view hierarchy and its associated drawables remain pinned in RAM.
2. **Unclosed Stream and Event Subscriptions**: Subscribing to global notification centers, event buses, or reactive streams without un-subscribing in `dispose()` or `deinit`. The singleton publisher retains a strong reference to the listener closure.
3. **Un-disposed Controllers and Timers**: Active `AnimationController` instances or repeating `Timer.periodic` loops hold continuous tick listeners on the framework scheduler, preventing garbage collection of their enclosing state objects.

## 3. Network Optimization and Radio Resource Control (RRC)

In mobile engineering, networking performance is not merely a question of data transfer speed; it directly controls device battery longevity. Mobile cellular modems (LTE, 5G NR) do not behave like wired network cards. They operate according to telecommunications state machines governed by **Radio Resource Control (RRC)**.

### The RRC State Machine and the Tail Energy Trap

To preserve battery life while maintaining network responsiveness, the cellular baseband modem transitions between discrete power states:

```text
         Data Transfer Initiated
    ┌───────────────────────────────┐
    │                               │
    ▼                               │
┌────────────────────────┐          │
│ Idle State             ├──────────┘
│  - Minimal power       │
│  - No dedicated RF     │
│  - ~10 - 20 mW         │
└────────────────────────┘
    ▲
    │ Inactivity Timer Expires (e.g., 5 - 15s)
    │ (Tail State Energy Drain)
┌───┴────────────────────┐          Data Transfer Required
│ Connected / Tail State ├─────────────────────────────────┐
│  - Dedicated channel   │                                 │
│  - Waiting for packets │                                 │
│  - ~1000 - 2500 mW     │◄────────────────────────────────┘
└────────────────────────┘
```

1. **Idle State**: The modem's radio frequency (RF) circuits are powered down. It periodically listens to paging channels with minimal battery impact (typically 10 to 20 mW).
2. **Connected / Active State (High Power)**: When an app initiates a network request, the modem negotiates with the cellular tower to allocate dedicated high-speed radio channels. The transmitter and power amplifier draw maximum energy (frequently 1,000 to 2,500 mW).
3. **Tail State (Inactivity Timer)**: When the data transfer completes, the radio **does not drop immediately to Idle**. Doing so would introduce a high latency penalty (often 100 to 500 ms) if another packet arrived a moment later. Instead, the network holds the radio in a high-power or intermediate state for an inactivity duration (the "tail time," typically 5 to 15 seconds depending on carrier network configuration).

### The Peril of Periodic Network Pings

If an application dispatches an isolated network request—such as a 200-byte analytics ping—every 15 seconds, it forces the cellular modem into the high-power state, and before the tail timer can elapse to power down the radio, the next ping arrives:

```text
Ping 1 (0.2s) ───► Tail State (10s active) ──► (Radio about to idle)
Ping 2 (15s)  ───► Tail State (10s active) ──► (Radio about to idle)
Ping 3 (30s)  ───► Tail State (10s active) ...
```

The modem remains energized in a high-power state continuously, consuming significant battery energy while transferring a negligible volume of data.

| RRC State | Average Power Consumption | Transition Latency to Transfer | Engineering Optimization Rule |
| :--- | :--- | :--- | :--- |
| **Idle** | $\approx 10\text{--}20\text{ mW}$ | $100\text{--}500\text{ ms}$ (channel setup) | Allow modem to sleep whenever possible |
| **Connected (Active)** | $\approx 1000\text{--}2500\text{ mW}$ | $0\text{ ms}$ (immediate transmit) | Saturate connection; burst all data at once |
| **Tail (Inactivity)** | $\approx 600\text{--}1200\text{ mW}$ | $0\text{--}50\text{ ms}$ | Batch requests to avoid repeatedly restarting tail timers |

### Practical Network Mitigations

- **Request Batching**: Group non-urgent network operations (analytics pings, user activity logs, background sync) into batched payloads dispatched together, allowing the radio to burst data and promptly return to Idle.
- **Background Job Schedulers**: Use platform-aware schedulers (`WorkManager` on Android, `BGAppRefreshTask` on iOS) that align background network activity with system maintenance windows when the radio is already active for other tasks.
- **Conditional HTTP Caching**: Utilize `ETag` and `If-None-Match` headers alongside explicit `Cache-Control: max-age` policies. A `304 Not Modified` response consumes significantly fewer radio transmission frames than re-downloading unchanged payload bodies.
- **Payload Compression and Field Trimming**: Serve data using Gzip, Brotli, or modern Zstandard compression. Remove unused object properties at the API gateway or Backend-for-Frontend (BFF) level to minimize total transmission time.

## 4. Startup Latency: Cold, Warm, and Hot Starts

Application launch speed is the user's initial perception of performance. Mobile operating systems define three distinct startup states, each with different operational constraints:

| Startup Type | Process State | OS Memory State | Typical Duration Target | Primary Architectural Bottleneck |
| :--- | :--- | :--- | :--- | :--- |
| **Cold Start** | Must be created from scratch | No memory mapped; clean process | $< 1.5\text{--}2.0\text{ seconds}$ | Dynamic linking, synchronous SDK init, DI creation |
| **Warm Start** | Process exists in RAM | View state cleared; activity recreated | $< 500\text{--}800\text{ ms}$ | View re-inflation, state reconstruction |
| **Hot Start** | Process and views alive | Entire state resident in memory | $< 200\text{--}300\text{ ms}$ | Bringing window to foreground, frame swap |

### The Anatomy of a Cold Start

A cold start represents the longest path to interactivity because the system must initialize every layer from hardware process isolation up to UI rendering:

```text
[1. Kernel / OS Fork]
  ├── Fork process from Zygote (Android) or launch executable via posix_spawn (iOS)
  └── Allocate initial process address space and paging tables
        │
        ▼
[2. Dynamic Linking & Runtime Init]
  ├── dyld (iOS) or Android linker resolves dynamic libraries (.dylib / .so)
  ├── Objective-C / Swift runtime setup or ART / JVM runtime initialization
  └── Execute static class initializers and framework bootstrap
        │
        ▼
[3. Application Class Lifecycle]
  ├── Application.onCreate() (Android) / didFinishLaunchingWithOptions (iOS)
  ├── Initialize Dependency Injection graph (Dagger, Hilt, GetIt, etc.)
  └── Initialize core logging, telemetry, and crash handling SDKs
        │
        ▼
[4. Initial Screen Creation]
  ├── Instantiate root Activity / UIViewController / Root Widget
  ├── Measure, layout, and shape initial UI tree
  └── Render First Frame (Time to Initial Display / TTID)
        │
        ▼
[5. Interactive Content Loaded]
  ├── Fetch local cached data from database
  └── Settle animations (Time to Interactive / TTI)
```

### Eliminating Synchronous Launch Bloat

The most prevalent architectural flaw during cold start is **synchronous SDK bloat**. Development teams frequently treat `Application.onCreate()` or `didFinishLaunchingWithOptions` as an initialization dump for third-party libraries: analytics, push notification SDKs, advertising frameworks, crash uploaders, in-app messaging, and feature flag services.

Every third-party SDK initialized synchronously on the main thread adds directly to the time before the user sees the first frame.

Mitigation strategies:
1. **Define the Critical Launch Path**: The critical launch path consists *only* of operations required to render the initial screen (crash logging, critical feature flags, security authentication). Everything else must be deferred.
2. **Staged and Background Initialization**: Push non-critical SDK initialization (marketing attribution, non-blocking telemetry, secondary analytics) to a background thread or schedule them after the first frame has been rendered to the display.
3. **Lazy Dependency Injection**: Instantiate service singletons on first access rather than eagerly binding every domain service during application creation.
4. **Android Baseline Profiles**: Utilize Android Baseline Profiles to pre-compile critical startup classes into native machine code Ahead-Of-Time (AOT), avoiding JIT compilation overhead during the first launch.

## 5. Production Implementations: Concrete Code Patterns

The following clean, self-contained Dart implementations illustrate the core engineering principles discussed: calculating bitmap memory, offloading heavy compute from the UI thread, and managing lifecycles safely.

### Pattern 1: Image Memory & Downsampling Calculator

This utility demonstrates the exact mathematical calculations required to evaluate bitmap footprint and determine safe target dimensions before allocating memory buffers:

```dart
/// Pure utility for calculating bitmap memory footprint and downsampling dimensions.
class ImageMemoryCalculator {
  /// Assumes standard 32-bit RGBA_8888 bitmap encoding (4 bytes per pixel).
  static const int bytesPerPixel = 4;

  /// Calculates raw uncompressed bitmap RAM requirement in bytes.
  /// Throws [ArgumentError] if dimensions are non-positive.
  static int calculateDecodedBytes(int width, int height) {
    if (width <= 0 || height <= 0) {
      throw ArgumentError('Width and height must be positive integers');
    }
    return width * height * bytesPerPixel;
  }

  /// Calculates target physical dimensions and memory savings when downsampling
  /// an original source image for display in a target viewport.
  static DownsampleResult calculateDownsampledDimensions({
    required int originalWidth,
    required int originalHeight,
    required double logicalTargetWidth,
    required double logicalTargetHeight,
    required double devicePixelRatio,
  }) {
    if (originalWidth <= 0 || originalHeight <= 0) {
      throw ArgumentError('Original dimensions must be positive');
    }
    if (logicalTargetWidth <= 0 || logicalTargetHeight <= 0 || devicePixelRatio <= 0) {
      throw ArgumentError('Target viewport dimensions and DPR must be positive');
    }

    // Physical pixels required on the hardware display
    final int physicalTargetWidth = (logicalTargetWidth * devicePixelRatio).ceil();
    final int physicalTargetHeight = (logicalTargetHeight * devicePixelRatio).ceil();

    // Guard against upscaling: if original is smaller than target, keep original
    final int targetWidth = originalWidth > physicalTargetWidth ? physicalTargetWidth : originalWidth;
    final int targetHeight = originalHeight > physicalTargetHeight ? physicalTargetHeight : originalHeight;

    final int originalBytes = calculateDecodedBytes(originalWidth, originalHeight);
    final int downsampledBytes = calculateDecodedBytes(targetWidth, targetHeight);
    final double savingsPercentage = ((originalBytes - downsampledBytes) / originalBytes) * 100.0;

    return DownsampleResult(
      targetWidth: targetWidth,
      targetHeight: targetHeight,
      originalBytes: originalBytes,
      downsampledBytes: downsampledBytes,
      savingsPercentage: savingsPercentage,
    );
  }
}

/// Immutable data class holding the result of downsampling calculations.
class DownsampleResult {
  final int targetWidth;
  final int targetHeight;
  final int originalBytes;
  final int downsampledBytes;
  final double savingsPercentage;

  const DownsampleResult({
    required this.targetWidth,
    required this.targetHeight,
    required this.originalBytes,
    required this.downsampledBytes,
    required this.savingsPercentage,
  });

  double get originalMegabytes => originalBytes / (1024 * 1024);
  double get downsampledMegabytes => downsampledBytes / (1024 * 1024);
}
```

### Pattern 2: Safe Background Isolate Offloading for Heavy Payloads

Parsing a multi-megabyte JSON response synchronously on the main thread will cause dropped frames or trigger OS watchdog timers. In modern Dart, `Isolate.run()` spawns a dedicated worker isolate, executes the computation, transfers the result back via message passing or shared memory pointers, and closes the worker automatically:

```dart
import 'dart:convert';
import 'dart:isolate';

/// Model representing a sanitized record parsed from raw network data.
class FeedRecord {
  final String id;
  final String title;
  final int timestamp;

  const FeedRecord({
    required this.id,
    required this.title,
    required this.timestamp,
  });

  factory FeedRecord.fromMap(Map<String, dynamic> map) {
    return FeedRecord(
      id: map['id'] as String? ?? '',
      title: map['title'] as String? ?? '',
      timestamp: map['timestamp'] as int? ?? 0,
    );
  }
}

/// Offloads JSON parsing and domain mapping entirely off the main UI isolate.
/// Prevents main thread starvation and maintains a consistent 60/120fps event loop.
Future<List<FeedRecord>> parseFeedPayloadInBackground(String rawJsonString) async {
  // Isolate.run spawns a separate worker isolate, executes the closure,
  // and returns the evaluated result without blocking the UI thread.
  return await Isolate.run<List<FeedRecord>>(() {
    final dynamic decoded = jsonDecode(rawJsonString);

    if (decoded is! List) {
      throw const FormatException('Payload root must be a JSON array');
    }

    // Process and cast records inside the background isolate
    return decoded
        .whereType<Map<String, dynamic>>()
        .map((Map<String, dynamic> item) => FeedRecord.fromMap(item))
        .toList(growable: false);
  });
}
```

### Pattern 3: Lifecycle-Aware Resource Management and Subscription Cleanup

A common cause of memory pressure terminations (such as iOS Jetsam kills) is retaining references to unmounted views and active event streams. This pattern demonstrates structured teardown:

```dart
import 'dart:async';
import 'package:flutter/widgets.dart';

/// Demonstrates lifecycle-safe stream subscription and resource disposal.
/// Prevents memory leaks, uncollected view closures, and unmounted state updates.
class PerformanceFeedWidgetState extends State<StatefulWidget> {
  final Stream<List<String>> inputStream;

  StreamSubscription<List<String>>? _subscription;
  List<String> _items = const [];
  bool _isLoading = false;

  PerformanceFeedWidgetState({required this.inputStream});

  @override
  void initState() {
    super.initState();
    _attachSubscription();
  }

  void _attachSubscription() {
    // Cancel any pre-existing subscription before establishing a new one
    _subscription?.cancel();

    setState(() {
      _isLoading = true;
    });

    _subscription = inputStream.listen(
      (List<String> data) {
        // Essential guard: verify the widget remains in the tree before updating state
        if (!mounted) return;

        setState(() {
          _items = data;
          _isLoading = false;
        });
      },
      onError: (Object error, StackTrace stackTrace) {
        if (!mounted) return;
        setState(() {
          _isLoading = false;
        });
      },
      cancelOnError: false,
    );
  }

  @override
  void dispose() {
    // 1. Explicitly cancel active stream subscription to break the closure retain cycle
    _subscription?.cancel();
    _subscription = null;

    // 2. Perform base cleanup
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    if (_isLoading) {
      return const Directionality(
        textDirection: TextDirection.ltr,
        child: Text('Loading feed...'),
      );
    }

    return Directionality(
      textDirection: TextDirection.ltr,
      child: Text('Rendered ${_items.length} items'),
    );
  }
}
```

## 6. Production Verification and Diagnostics Checklist

Before releasing a mobile feature to production, evaluate it against this verification checklist using platform-specific profiling tools (such as Xcode Instruments, Android Studio Profiler, or Flutter DevTools):

### Rendering & Frame Budget
- [ ] **Profile-Mode Verification**: Has the application been profiled exclusively in **Profile / Release Mode** on physical low-to-mid-tier target hardware? (Debug builds with JIT compilation yield invalid frame timings).
- [ ] **VSYNC Adherence**: Does the UI thread execute within $\le 16.67\text{ ms}$ (60Hz) or $\le 8.33\text{ ms}$ (120Hz) during active list flings and view transitions?
- [ ] **Overdraw Analysis**: Has the screen been inspected with "Show GPU Overdraw" (Android) or "Color Blended Layers" (iOS) to eliminate redundant nested backgrounds?

### Memory & Bitmaps
- [ ] **Explicit Downsampling**: Are all remote and local image assets decoded directly to their physical display dimensions (`cacheWidth`/`cacheHeight`, `inSampleSize`, or `CGImageSourceCreateThumbnailAtIndex`) rather than raw capture dimensions?
- [ ] **Clean Heap Traversal**: When navigating back and forth across a feature ten consecutive times, does heap memory stabilize back to baseline, or does it ratchet continuously upward?
- [ ] **Background Memory Footprint**: Does the application release transient cache memory upon transitioning to the background to protect against iOS Jetsam and Android `lmkd` kills?

### Networking & Baseband
- [ ] **Batching Non-Urgent Traffic**: Are telemetry events and non-urgent analytics batched together rather than dispatched as isolated pings that continually restart cellular RRC tail timers?
- [ ] **HTTP Caching**: Are API endpoints configured with `Cache-Control` and `ETag` headers to prevent redundant full-payload transfers?

### Cold Start & Launch Path
- [ ] **Critical Path Exclusivity**: Are only components required for the initial screen initialized in `Application.onCreate` or `didFinishLaunchingWithOptions`?
- [ ] **Deferred SDK Boot**: Are non-critical analytics, secondary tracking libraries, and heavy singletons deferred until after the first frame has rendered?

---

## Conclusion

Mobile application performance is fundamentally a discipline of managing shared physical constraints. A smooth user interface is not produced by guessing or applying superficial tricks—it is the direct outcome of respecting the hardware refresh cycle, treating memory as a scarce resource without a swap file, coordinating network traffic with cellular baseband physics, and keeping the critical launch path minimal.

By measuring performance using profile-mode builds on representative target devices and adopting architectural patterns that separate heavy computation from the UI thread, teams can build applications that remain responsive, reliable, and durable in production.
