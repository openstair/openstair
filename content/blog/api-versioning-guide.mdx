# API Versioning: How to Evolve APIs Without Breaking Clients

Every production API that achieves adoption faces an inevitable dilemma: software systems must evolve to support new capabilities, but deployed clients cannot be upgraded simultaneously. Unlike monolithic internal applications where refactoring a function signature involves updating its call sites within the same commit, distributed HTTP APIs operate across trust and deployment boundaries. Mobile applications remain installed on user devices for months without updates; third-party enterprise integrations run on scheduled batch servers with frozen dependencies; and microservices owned by disparate squads deploy on independent release cadences.

API versioning is the operational and architectural discipline of introducing schema, behavioral, and structural changes without breaking existing consumers. It is not merely a question of URL formatting or HTTP header selection. A resilient versioning strategy dictates how services route network traffic, how intermediate content delivery networks (CDNs) cache responses, how data models migrate in underlying databases, and how platform engineering teams retire obsolete code without causing service outages.

This guide examines the core mechanics of API versioning for backend engineers and distributed systems architects. It establishes the technical criteria that distinguish breaking from non-breaking modifications, evaluates the four primary versioning strategies and their caching implications, breaks down the canonical internal representation adapter pattern, and details standards-compliant deprecation workflows using RFC 8594.

## 1. Defining the Contract Boundary: Breaking vs. Non-Breaking Changes

Before choosing a versioning mechanism, an engineering team must formalize what constitutes a contract break. An API contract comprises the complete set of expectations shared between client and server, including transport semantics, serialization formats, schema constraints, status codes, and error payloads.

A change is classified as **breaking** if an existing, unmodified client executing valid requests against the API experiences runtime deserialization failures, unintended validation rejections, logic divergence, or semantic data corruption. Conversely, a change is **non-breaking (backward-compatible)** if existing clients continue processing requests and responses identically to their baseline behavior.

```text
Incoming Change Proposal
  │
  ├─► Removing / renaming a field or endpoint? ──────────────► BREAKING (New Version Required)
  ├─► Narrowing constraints (e.g. string len, new required)? ─► BREAKING (New Version Required)
  ├─► Changing primitive type (e.g. number -> string)? ──────► BREAKING (New Version Required)
  ├─► Changing nullability guarantees (non-null -> nullable)? ─► BREAKING (New Version Required)
  │
  ├─► Adding optional request query/body parameter? ─────────► NON-BREAKING (In-Place Compatible)
  ├─► Adding new response field (with tolerant clients)? ─────► NON-BREAKING (In-Place Compatible)
  └─► Introducing a completely new independent resource? ────► NON-BREAKING (In-Place Compatible)
```

### Breaking Changes
The following modifications invariably demand a new API version or an explicit opt-in contract:

1. **Field Removal or Renaming**: Deleting a response property (e.g., removing `user.postal_code`) or renaming a field (e.g., changing `user.first_name` to `user.given_name`) breaks any client deserializer expecting that property.
2. **Data Type and Format Mutations**: Changing a scalar representation, such as converting an identifier from an integer (`1042`) to a string (`"usr_1042"`) or an ISO 8601 string to a Unix millisecond timestamp, triggers type errors in strongly typed languages (e.g., Go, Rust, Java, TypeScript).
3. **Narrowing Validation Constraints**: Making an optional request field mandatory, lowering the maximum allowed length of an input string, or tightening a regex validator rejects payloads that previously succeeded.
4. **Altering Nullability Guarantees**: Returning `null` for an attribute that was previously documented and guaranteed as non-nullable leads to `NullPointerException` or undefined variable panics in client runtimes.
5. **Changing Semantic Status Codes or Envelopes**: Shifting an error condition from `400 Bad Request` to `422 Unprocessable Entity`, or restructuring the error envelope (e.g., moving from `{ "error": "message" }` to `{ "errors": [{ "code": 101, "detail": "message" }] }`), breaks client-side error dispatchers.
6. **Modifying Authentication and Security Schemes**: Changing token schemes (e.g., moving from `Authorization: Bearer <jwt>` to custom signed HMAC headers) immediately invalidates gateway authentication for un-updated clients.

### Non-Breaking Changes
When designed with backward compatibility in mind, the following modifications can be deployed in-place without releasing a new major version:

1. **Adding Optional Request Parameters**: Introducing query parameters or request body properties with sensible server-side defaults preserves existing callers.
2. **Adding New Response Fields**: Introducing additive fields to JSON response payloads is non-breaking, provided client consumers adhere to the Tolerant Reader pattern.
3. **Adding New Resource Endpoints**: Introducing `/v1/subscriptions` alongside `/v1/users` does not alter the behavior of existing routes.
4. **Relaxing Validation Constraints**: Widening a parameter's acceptable values (e.g., expanding supported enum values on an incoming request, or increasing allowed character limits) accepts all legacy inputs while accommodating new use cases.

### The Tolerant Reader Pattern and Postel's Law
In distributed architectures, API stability relies as much on client consumption hygiene as on server discipline. Martin Fowler's **Tolerant Reader Pattern** dictates that client deserializers should extract only the fields necessary for their immediate operation, ignoring unrecognized keys in the response payload. In languages with strict JSON parsers (such as Jackson in Java or `serde` in Rust), this requires explicitly configuring deserializers to ignore unknown properties (`@JsonIgnoreProperties(ignoreUnknown = true)` in Jackson, or omitting `deny_unknown_fields` in `serde`).

This principle aligns with **Postel's Law (The Robustness Principle)**, formulated in RFC 761 and RFC 1122:

> *"Be conservative in what you send, be liberal in what you accept."*

In modern API gateway design, teams apply a critical nuance to Postel's Law: while servers should be liberal in ignoring benign unknown fields in outgoing client expectations, they must strictly validate incoming request payloads at the security boundary to guard against parameter pollution, injection attacks, and malformed state transitions.

## 2. The Four Primary API Versioning Strategies

When breaking changes cannot be avoided, teams must expose distinct contract variants. Four standard architectural strategies exist in production HTTP systems, each carrying specific tradeoffs regarding developer ergonomics, routing complexity, and edge caching behavior.

### Strategy 1: URI Path Versioning
URI path versioning embeds the major version identifier directly into the resource's path segment.

```http
GET /v1/organizations/org_429/members HTTP/1.1
Host: api.example.com
```

#### Operational Characteristics
- **Routing & Gateways**: Reverse proxies (NGINX, Envoy, Traefik) and API gateways can match and route traffic using simple prefix rules (e.g., path prefix `/v1/` routes to Service Cluster A, while `/v2/` routes to Service Cluster B).
- **Edge Caching**: Fully compatible with HTTP caching standards. Because the URI is the primary cache key in RFC 9111, CDNs (Cloudflare, Fastly, AWS CloudFront) partition cache entries automatically without requiring specialized header normalization.
- **Developer Usability**: High. Engineers can paste URLs directly into web browsers, documentation portals, and terminal `curl` invocations without configuring request headers.
- **Architectural Tradeoffs**: Purists note that embedding version numbers into URIs violates the REST principle of Uniform Resource Identifiers, as the identity of an entity (an organization) is conflated with the schema representation used to retrieve it. Additionally, path versioning can lead to route proliferation if teams attempt to version individual endpoints independently rather than grouping them into coarse-grained releases.

### Strategy 2: Custom Request Header Versioning
Custom header versioning decouples the version identifier from the URI path, passing it via a dedicated HTTP header.

```http
GET /organizations/org_429/members HTTP/1.1
Host: api.example.com
X-API-Version: 2
```

#### Operational Characteristics
- **Routing & Gateways**: Intermediate gateways inspect incoming headers to direct traffic to appropriate upstreams.
- **Edge Caching Complexity**: Requires origin servers to emit `Vary: X-API-Version`. CDNs must incorporate this header into their custom cache key configuration. If a client fails to supply the header, or if intermediaries strip custom headers, cache pollution or unintended fallback responses can occur.
- **Developer Usability**: Moderate. Cannot be tested directly via standard browser address bars without browser extensions or command-line tooling.
- **Architectural Tradeoffs**: Preserves clean, canonical URIs for resources across versions. Enables global version configuration in API client SDKs without changing route path constants.

### Strategy 3: Content Negotiation (Accept Header Versioning)
Content negotiation uses standard MIME type parameters in the `Accept` header to specify the desired schema representation, often termed "vendor-specific media types."

```http
GET /organizations/org_429/members HTTP/1.1
Host: api.example.com
Accept: application/vnd.mycompany.v2+json
```

Alternatively, standard parameters can be appended:

```http
Accept: application/json; version=2
```

#### Operational Characteristics
- **Routing & Gateways**: Requires edge gateways to parse the `Accept` header's complex media type structure and parameter weights ($q$-values) to extract the version indicator.
- **Edge Caching Complexity**: Origin servers must return `Vary: Accept`. Because HTTP `Accept` headers vary widely across clients (e.g., standard browsers append wildcard values like `text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8`), intermediate caches suffer high cache key fragmentation unless the edge layer explicitly normalizes the header before hashing.
- **Developer Usability**: Lower for casual exploration. Tooling, mock servers, and interactive documentation require explicit header manipulation.
- **Architectural Tradeoffs**: The most architecturally compliant with strict REST principles (HATEOAS and content negotiation as defined in RFC 9110), treating versioning as an evolution of representation rather than resource location.

### Strategy 4: Account-Pinned Date-Based Versioning (The Stripe Pattern)
Pioneered by platforms like Stripe, date-based versioning pins an API client or organization account to an immutable release snapshot date (e.g., `2024-04-15`) stored in database configuration.

```http
GET /v1/customers/cus_982 HTTP/1.1
Host: api.example.com
Stripe-Version: 2024-06-20
```

#### Operational Characteristics
- **Default Resolution**: If the caller omits the version header, the gateway looks up the account's pinned registration date and applies that exact contract snapshot. Existing production callers never experience breaking changes when the API publisher deploys new functionality.
- **Per-Request Overrides**: Developers can test newer or older contracts on a per-call basis by explicitly supplying the version header (`Stripe-Version: 2024-06-20`).
- **Edge Caching Complexity**: Cache partitioning must incorporate both the authenticated account's default version and any request-level override header, requiring specialized edge computation (e.g., Cloudflare Workers or Lambda@Edge).
- **Architectural Tradeoffs**: Exceptional developer experience and enterprise stability, but requires substantial internal transformation infrastructure (an automated chain of event mutations or schema upcasters/downcasters) to avoid maintaining dozens of monolithic service forks.

### Architectural Strategy Comparison

| Dimension | URI Path (`/v1/...`) | Custom Header (`X-API-Version`) | Content Negotiation (`Accept`) | Date-Based Pinned (`2024-06-20`) |
| :--- | :--- | :--- | :--- | :--- |
| **URI Stability** | Changes per version | Stable across versions | Stable across versions | Stable across versions |
| **CDN Cache Setup** | Trivial (URI is cache key) | Requires `Vary: X-API-Version` | Complex (`Vary: Accept` normalization) | Requires account-level cache keys |

| **Browser / Curl Exploration** | Direct URL access | Requires custom headers | Requires custom headers | Default resolves to pinned date |
| **OpenAPI / Swagger Tooling** | Out-of-the-box support | Requires custom plugin/params | Requires media type definitions | Complex multi-version spec trees |
| **Primary Production Use** | Public & B2D SaaS APIs | Enterprise internal APIs | Strict RESTful enterprise systems | High-velocity developer platforms |

## 3. Internal Architecture: The Canonical Domain and Adapter Pipeline

A common anti-pattern in teams adopting API versioning is **Controller Duplication**. In this anti-pattern, the engineering team copies an entire controller, service layer, and persistence query to create a distinct `v2` codebase:

```text
// ANTI-PATTERN: Duplicate controller and service trees
src/
├── controllers/
│   ├── v1/
│   │   └── UserController.ts    // 80% identical code
│   └── v2/
│       └── UserController.ts    // 80% identical code
└── services/
    ├── v1/
    │   └── UserService.ts       // Divergent bug fixes
    └── v2/
        └── UserService.ts       // Divergent bug fixes
```

This fork creates severe long-term liabilities:
- Critical bug fixes and security patches applied to `v2` must be manually backported to `v1`.
- Database query optimizations diverge, causing unexpected performance regressions on older versions.
- Domain logic drifts over time, making it impossible to guarantee that `v1` and `v2` enforce identical business invariants.

### The Canonical Model and Bidirectional Adapter Pattern
The scalable alternative is maintaining a single **Canonical Internal Domain Model** representing the current state of business logic, paired with an ingress and egress transformation pipeline.

```text
                        ┌──────────────────────────────────────────────┐
                        │              API Gateway / Ingress            │
                        └──────────────────────┬───────────────────────┘
                                               │
                                       Resolve Version
                                               │
                         ┌─────────────────────┴─────────────────────┐
                         ▼                                           ▼
                   Version: "v1"                               Version: "v2"
                         │                                           │
                         ▼                                           ▼
             ┌───────────────────────┐                               │
             │  Request Upcaster v1  │                               │
             │ (Maps v1 -> Canonical)│                               │
             └───────────┬───────────┘                               │
                         │                                           │
                         └─────────────────────┬─────────────────────┘
                                               │
                                               ▼
                              ┌─────────────────────────────────┐
                              │    Canonical Domain Service     │
                              │    (Latest Business Logic)      │
                              └────────────────┬────────────────┘
                                               │
                                     Canonical Entity Result
                                               │
                         ┌─────────────────────┴─────────────────────┐
                         ▼                                           ▼
             ┌───────────────────────┐                   ┌───────────────────────┐
             │ Response Downcaster v1│                   │ Response Downcaster v2│
             │ (Canonical -> v1 DTO) │                   │ (Canonical -> v2 DTO) │
             └───────────┬───────────┘                   └───────────┬───────────┘
                         │                                           │
                         ▼                                           ▼
                 v1 JSON Response                            v2 JSON Response
```

Under this pattern:
1. **Request Upcasters**: When a legacy request arrives (e.g., `v1`), an upcaster function translates the legacy payload into the canonical input structure before business execution begins.
2. **Canonical Execution**: The core domain service, validation layer, and database interactions execute exclusively against the canonical model. Only one business implementation exists in the codebase.
3. **Response Downcasters**: When the domain service returns the canonical result, a downcaster serializes the internal entity into the exact schema layout requested by that specific client version.

This keeps maintenance focused: adding a new version requires writing a new adapter layer rather than cloning an entire application tier.

## 4. Database Schema Coordination: The Expand-Contract Pattern

API contracts do not exist in isolation; they are tightly coupled to persistent database storage. If an API evolves from storing a single full name to distinct first and last names, a naive database migration will immediately break all legacy API versions.

To evolve persistence layers without breaking older API contracts running concurrently in production, teams employ the **Expand-Contract Pattern** (also called the Parallel Run or Phased Transition pattern).

```text
Phase 1: Expand                Phase 2: Backfill & Dual-Read     Phase 3: Contract
┌──────────────────────────┐   ┌──────────────────────────┐      ┌──────────────────────────┐
│ Table: users             │   │ Table: users             │      │ Table: users             │
│ - id                     │   │ - id                     │      │ - id                     │
│ - full_name (active)     │   │ - full_name (read legacy)│      │                          │
│ - first_name (new, null) │   │ - first_name (backfilled)│      │ - first_name (not null)  │
│ - last_name  (new, null) │   │ - last_name  (backfilled)│      │ - last_name  (not null)  │
└──────────────────────────┘   └──────────────────────────┘      └──────────────────────────┘
 Dual-write on write paths       Asynchronous backfill jobs        Drop legacy column after
                                 Read switch to new columns        v1 API sunset completes
```

### Phase 1: Expand (Additive Schema Rollout)
The new database structure is introduced without removing or altering existing columns.
- Columns are created as nullable or with safe defaults:
  ```sql
  ALTER TABLE users ADD COLUMN first_name VARCHAR(100) DEFAULT NULL;
  ALTER TABLE users ADD COLUMN last_name VARCHAR(100) DEFAULT NULL;
  ```
- The application is updated to perform **dual-writes**: whenever a user update occurs via either `v1` or `v2`, the application writes both `full_name` and (`first_name`, `last_name`).

### Phase 2: Backfill and Transition
- A background worker incrementally scans historical rows, parsing existing `full_name` values into `first_name` and `last_name`.
- Once backfill completion is verified, internal application queries are updated to read from the new columns.
- The `v1` adapter downcaster derives `full_name` on-the-fly by concatenating `${first_name} ${last_name}` for legacy consumers.

### Phase 3: Contract (Legacy Teardown)
- After the `v1` API has completed its deprecation and sunset window (receiving zero production traffic), the code writing to the legacy column is removed.
- The database schema is formally cleaned up:
  ```sql
  ALTER TABLE users DROP COLUMN full_name;
  ALTER TABLE users ALTER COLUMN first_name SET NOT NULL;
  ALTER TABLE users ALTER COLUMN last_name SET NOT NULL;
  ```

## 5. Deprecation, Sunsetting, and Brownouts

Versioning APIs without a formal sunsetting process produces perpetual technical debt. Teams accumulate dozens of obsolete routes, bloating operational overhead and preventing structural refactoring.

### The RFC 8594 `Sunset` HTTP Header
The Internet Engineering Task Force (IETF) formalized sunset signalling in **RFC 8594: The Sunset HTTP Header Field**. The `Sunset` header provides an explicit, machine-readable HTTP timestamp indicating when the requested resource or version will become completely unresponsive.

```http
HTTP/1.1 200 OK
Content-Type: application/json
Sunset: Wed, 11 Nov 2026 00:00:00 GMT
Link: <https://api.example.com/docs/migrations/v1-sunset>; rel="sunset"; type="text/html"
```

The header value must conform to the IMF-fixdate format specified in RFC 9110 (e.g., `Wed, 11 Nov 2026 00:00:00 GMT`).

### The IETF `Deprecation` Header
Complementing RFC 8594, the IETF draft standard for API deprecation defines the `Deprecation` header to signal that an endpoint is currently deprecated, even if the final sunset date has not yet been locked:

```http
Deprecation: @1762819200
Link: <https://api.example.com/docs/migrations/v1-to-v2>; rel="deprecation"; type="text/html"
```

The value can be an explicit Unix timestamp (prefixed with `@`), a boolean flag, or an HTTP date. Accompanying `Link` headers with `rel="sunset"` and `rel="deprecation"` provide human-readable migration guides and machine-parseable OpenAPI definitions for client SDK generators.

### Telemetry and Consumer Attribution
Engineers cannot safely decommission an API version without visibility into who is calling it. Production API gateways must tag every request metric with the resolved client identity and requested API version:

```text
api_http_requests_total{
  version="v1",
  route="/users",
  client_id="client_enterprise_99",
  status="200"
}
```

By querying Prometheus or Datadog metrics, the platform team can generate real-time leaderboards of the top consumers of deprecated versions and proactively reach out to specific engineering teams before schedules lapse.

### Scheduled Brownouts (Synthetic Degradation)
Static deprecation emails and documentation announcements are frequently overlooked by third-party developers. To ensure that stale consumers notice deprecation schedules well before permanent termination, teams execute **brownouts**: scheduled, temporary simulated outages of the deprecated version in production.

A standard brownout progression spans multiple phases prior to the permanent sunset date:
1. **Brownout Phase 1 (60 days before sunset)**: 15-minute scheduled window during off-peak hours where deprecated endpoints return `410 Gone` or `503 Service Unavailable` with explanatory headers.
2. **Brownout Phase 2 (30 days before sunset)**: 1-hour scheduled window during peak business hours.
3. **Brownout Phase 3 (7 days before sunset)**: 4-hour scheduled window.
4. **Permanent Sunset**: The endpoint is decommissioned permanently, returning `410 Gone` with a link to current documentation.

```text
Production Brownout Timeline
  │
  ├─► T - 60 Days: 15-Minute Brownout (Triggers early monitoring alerts in stale clients)
  ├─► T - 30 Days: 1-Hour Brownout    (Escalates visibility to active development teams)
  ├─► T - 7 Days:  4-Hour Brownout    (Final verification of client migration completion)
  └─► T - 0 Days:  Permanent Decommission (Route disabled; returns HTTP 410 Gone)
```

Brownouts intentionally trigger automated client alerting and on-call paging during supervised maintenance windows, preventing uncoordinated crisis incidents on the actual decommission date.

## 6. Production Implementation: Type-Safe Versioned Dispatcher in TypeScript

The following TypeScript implementation demonstrates a self-contained, type-safe versioned dispatch pipeline. It showcases canonical domain isolation, bidirectional request/response adapters, RFC 8594 sunset header injection, and client usage telemetry.

```typescript
import { IncomingHttpHeaders } from "node:http";

// --- Domain Definitions ---

// Canonical internal representation: latest system domain model
export interface CanonicalUser {
  id: string;
  firstName: string;
  lastName: string;
  email: string;
  createdAt: Date;
  updatedAt: Date;
}

// V1 Legacy DTO: monolithic name field, no timestamps
export interface UserResponseV1 {
  id: string;
  name: string;
  email: string;
}

// V2 Modern DTO: granular names, ISO timestamp strings
export interface UserResponseV2 {
  id: string;
  first_name: string;
  last_name: string;
  email: string;
  created_at: string;
}

// Supported version identifiers
export type ApiVersion = "v1" | "v2";

export interface VersionMetadata {
  version: ApiVersion;
  deprecated: boolean;
  deprecationDate?: string;
  sunsetDate?: string; // RFC 8594 HTTP-date format
  migrationUrl?: string;
}

export const VERSION_REGISTRY: Record<ApiVersion, VersionMetadata> = {
  v1: {
    version: "v1",
    deprecated: true,
    deprecationDate: "2025-01-15T00:00:00Z",
    sunsetDate: "Wed, 11 Nov 2026 00:00:00 GMT",
    migrationUrl: "https://api.example.com/docs/migrations/v1-to-v2",
  },
  v2: {
    version: "v2",
    deprecated: false,
  },
};

// --- Ingress & Egress Adapters ---

export class UserVersionAdapter {
  /**
   * Downcaster: Transforms Canonical entity into V1 legacy format.
   */
  public static downcastToV1(entity: CanonicalUser): UserResponseV1 {
    return {
      id: entity.id,
      name: `${entity.firstName} ${entity.lastName}`.trim(),
      email: entity.email,
    };
  }

  /**
   * Downcaster: Transforms Canonical entity into V2 modern format.
   */
  public static downcastToV2(entity: CanonicalUser): UserResponseV2 {
    return {
      id: entity.id,
      first_name: entity.firstName,
      last_name: entity.lastName,
      email: entity.email,
      created_at: entity.createdAt.toISOString(),
    };
  }

  /**
   * Upcaster: Translates incoming V1 creation input into canonical creation attributes.
   */
  public static upcastV1Input(payload: { name: string; email: string }): {
    firstName: string;
    lastName: string;
    email: string;
  } {
    const segments = (payload.name || "").trim().split(/\s+/);
    const firstName = segments[0] || "Unknown";
    const lastName = segments.slice(1).join(" ") || "";

    return {
      firstName,
      lastName,
      email: payload.email,
    };
  }
}

// --- Dispatcher & Middleware Pipeline ---

export interface HttpRequestContext {
  path: string;
  headers: IncomingHttpHeaders;
  clientId?: string;
}

export interface HttpResponsePayload<T> {
  statusCode: number;
  headers: Record<string, string>;
  body: T;
}

export class VersionedApiDispatcher {
  /**
   * Extracts API version from URI path (/v1/users) or fallback header (X-API-Version).
   */
  public static resolveVersion(context: HttpRequestContext): ApiVersion {
    const pathMatch = context.path.match(/^\/(v1|v2)\b/);
    if (pathMatch && (pathMatch[1] === "v1" || pathMatch[1] === "v2")) {
      return pathMatch[1];
    }

    const headerVal = context.headers["x-api-version"];
    if (typeof headerVal === "string" && (headerVal === "v1" || headerVal === "v2")) {
      return headerVal;
    }

    // Default fallback to v2 for unversioned modern calls
    return "v2";
  }

  /**
   * Formulates RFC 8594 Sunset and Deprecation headers based on version metadata.
   */
  public static generateLifecycleHeaders(meta: VersionMetadata): Record<string, string> {
    const headers: Record<string, string> = {};

    if (meta.deprecated) {
      headers["Deprecation"] = "true";
    }

    if (meta.sunsetDate) {
      headers["Sunset"] = meta.sunsetDate;
    }

    if (meta.migrationUrl) {
      const linkDirectives: string[] = [];
      if (meta.deprecated) {
        linkDirectives.push(`<${meta.migrationUrl}>; rel="deprecation"; type="text/html"`);
      }
      if (meta.sunsetDate) {
        linkDirectives.push(`<${meta.migrationUrl}>; rel="sunset"; type="text/html"`);
      }
      headers["Link"] = linkDirectives.join(", ");
    }

    return headers;
  }

  /**
   * Executes request dispatch with canonical domain execution and downcasting.
   */
  public async handleGetUser(
    userId: string,
    context: HttpRequestContext
  ): Promise<HttpResponsePayload<UserResponseV1 | UserResponseV2>> {
    const version = VersionedApiDispatcher.resolveVersion(context);
    const meta = VERSION_REGISTRY[version];

    // Emit operational metrics for traffic monitoring
    this.recordVersionMetric(version, context.clientId || "anonymous");

    // Execute Canonical Domain Logic (Single source of business truth)
    const userEntity = await this.fetchUserFromDatabase(userId);
    if (!userEntity) {
      return {
        statusCode: 404,
        headers: { "Content-Type": "application/json" },
        body: null as unknown as UserResponseV1,
      };
    }

    // Generate RFC lifecycle headers
    const lifecycleHeaders = VersionedApiDispatcher.generateLifecycleHeaders(meta);

    // Downcast based on negotiated version
    let responseBody: UserResponseV1 | UserResponseV2;
    if (version === "v1") {
      responseBody = UserVersionAdapter.downcastToV1(userEntity);
    } else {
      responseBody = UserVersionAdapter.downcastToV2(userEntity);
    }

    return {
      statusCode: 200,
      headers: {
        "Content-Type": "application/json",
        "Vary": "Accept, X-API-Version",
        ...lifecycleHeaders,
      },
      body: responseBody,
    };
  }

  private async fetchUserFromDatabase(id: string): Promise<CanonicalUser | null> {
    // Illustrative canonical persistence retrieval
    return {
      id,
      firstName: "Jane",
      lastName: "Doe",
      email: "jane.doe@example.com",
```

## 7. Practical API Versioning Production Checklist

Before rolling out schema changes or initiating a version deprecation lifecycle, verify your service readiness against this operational checklist:

### Contract Evaluation & Schema Linting
- [ ] **Contract Breaking Audit**: Ensure no response fields were deleted, renamed, or converted into incompatible primitive types without a new major version.
- [ ] **Tolerant Reader Verification**: Verify that client SDKs and internal consumers are configured to ignore unknown fields during JSON deserialization.
- [ ] **Automated Breaking Change Detection**: Integrate automated schema comparison tools (such as `oasdiff` for OpenAPI, `buf breaking` for Protocol Buffers, or GraphQL Inspector) into the continuous integration (CI) pipeline.

### Edge Routing and Caching
- [ ] **CDN Cache Key Integrity**: When using headers (`X-API-Version` or `Accept`), verify that intermediate CDNs and caching proxies include appropriate `Vary` headers or custom normalized cache keys.
- [ ] **Route Regex Isolation**: Ensure edge gateways explicitly bound path version matchers (e.g., matching `/v1/` specifically rather than matching unintended prefixes like `/v10/`).

### Architectural Implementation
- [ ] **Canonical Domain Model Purity**: Verify that domain entities and business rules are implemented once in the core domain service, rather than duplicated across controller files.
- [ ] **Upcaster/Downcaster Test Coverage**: Unit tests must validate that bidirectional adapters map legacy payloads accurately to and from the canonical representation across all boundary states.

### Database Migration Safety
- [ ] **Expand-Contract Phased Rollout**: Schema updates must follow the three-phase expand-contract workflow, writing to both structures before removing deprecated columns.
- [ ] **Lock-Free Migrations**: Ensure database DDL updates do not acquire long-lived exclusive table locks on production tables with active client traffic.

### Deprecation & Decommissioning
- [ ] **RFC 8594 Sunset Header Compliance**: Deprecated endpoints must emit valid `Sunset: <HTTP-date>` and `Link: <url>; rel="sunset"` headers.
- [ ] **Client Attribution Dashboard**: An active observability dashboard must display real-time request volumes grouped by version and `client_id` / API key.
- [ ] **Scheduled Brownout Plan**: Execute scheduled temporary simulated outages (15-minute, 1-hour, 4-hour) in advance of hard sunset dates to ensure stale clients are remediated without production crises.

## Conclusion: Engineering APIs for Sustainable Evolution

API versioning is not a cosmetic syntax decision; it is a fundamental architectural boundary between independent distributed systems. Treating versioning as an afterthought results in brittle controller duplication, silent client deserialization crashes, and permanent database technical debt.

To build durable APIs:
1. **Differentiate strictly between breaking and additive changes**, encouraging tolerant consumption while rigorously validating inputs at security perimeters.
2. **Select the versioning transport that aligns with your operational infrastructure**: leverage URI path versioning when edge CDN caching and public developer discoverability are paramount; leverage header or date-based pinning when supporting complex B2B workflows.
3. **Isolate domain logic into a single canonical model**, maintaining lightweight bidirectional adapters for legacy contracts.
4. **Coordinate database schema changes via the expand-contract pattern**, decoupling persistence deployments from API availability.
5. **Enforce transparent deprecation lifecycles using RFC 8594 `Sunset` headers and scheduled brownouts**, ensuring obsolete versions can be retired safely and predictably.
